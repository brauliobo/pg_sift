# Sizing and operating a large pg_sift index

Disk, memory and time an index costs beyond its steady-state size, and the settings that matter. *(changes)* marks 1.3.1 behavior that 2.0.0 altered (figures are the 1.3.1 baseline). Since 2.0.0 ([CHANGELOG.md](../CHANGELOG.md)):

- the memory of a merge no longer grows with the segments (4 segments of 3M documents, 690 MB, at 16MB of `maintenance_work_mem`: 140 MB of anonymous memory and 17.4 s before, 16 MB and 8.3 s after);
- the worker runs each step in a transaction of its own and reuses what the previous step freed (60 small segments merged by the worker: the file was 2.6 times the live segments, now 1.6);
- a merge stages only the dictionary index and the postings of large terms in temporary files.

## Disk

- **Merge and promotion need room beside the old segments.** A segment is written whole before the segments it replaces are freed, so a merge holds the inputs and the output (2x of the segments being merged), and blocks freed by earlier merges wait for old snapshots (next item). In churn tests the file reached 3.3x the live data, 6x under heavy churn: plan for about 3x the index as free space. `sift.merge(index, true)` forces a merge of every immutable segment. *(changes: a streaming merge writes the output while it reads and stages less.)*
- **Freed blocks are reused only after every transaction that could read them is gone.** Blocks released by a merge, a promotion or VACUUM carry the releasing xid and are reused once every snapshot that may hold the old directory has ended. An idle `REPEATABLE READ` or long transaction stops reuse: in a test the file grew 41 to 135 MB for 21 MB of live data while one transaction sat idle. The file shrinks only at its end, when `VACUUM` truncates the free blocks there (see [USAGE](USAGE.md#maintenance-and-operations)); free space in front of live segments waits for reuse and only `REINDEX` compacts it. The maintenance worker keeps one snapshot for its whole run, so a long run holds back its own frees. `sift.index_info(index)` shows `free_blocks` and how many are `reusable_blocks` now. *(changes: the worker releases its snapshot and recycles after each step.)*
- **A primary with a streaming standby: the index file, the WAL and the lag of a sustained write load.** Measured on a `sift_col` index over six columns, PostgreSQL 18.6, x86-64, one primary and one hot standby (standby `shared_buffers` of 64 MB, `fsync` on, `synchronous_commit` off), the primary on four cores shared with other work; the load is 4,000 transactions a second for 300 s (50% updates of a covered column, 20% of a key column, 10% deletes, 20% inserts), with autovacuum and the maintenance worker at their defaults. **Disk:** with the standby streaming and `hot_standby_feedback = on` the file ended at 4.4x and 6.4x its live size on 1,000,000 rows (78.2 and 115.6 MB against 17.6 and 18.1 MB for a fresh index; with and without a long query on the standby) and 2.3x on 3,000,000 rows (112.4 against 49.6 MB), and no `VACUUM` or merge shrank it in the 600 s after the load (10,515 of 12,618 blocks free and reusable in the 103 MB case); with feedback off 2.1x, the merge output written before its inputs are freed; without a standby 1.1 to 1.2x. Plan the disk of the primary for about 2x the live index, and for up to 6x for an index under about 32 MB (the first merge tier: its segments are folded into one at every eighth promotion, 13 to 16 MB every 75 to 80 s here) when the standby lags; the space is reused, and returned by `REINDEX` ([USAGE](USAGE.md#maintenance-and-operations)). **WAL:** 571 to 650 bytes a transaction at 1,000,000 rows with a standby (a table with three btree indexes: 577), 730 without one; 1,119 at 3,000,000 rows with the standby (1,590 without one, a longer run at a higher rate). **Replay lag:** the standby fell behind by 103 to 594 MB at 1,000,000 rows and 741 MB at 3,000,000 (the table with btree indexes: 488 MB), whether it shared cores or had its own, because its replay of random page writes is the limit at this rate, not the index; an earlier run at 1,500 and 4,000 transactions a second (`fsync` off) held 15.5 MB (8.8 s) and 29.3 MB (11.4 s).
- **`REINDEX INDEX` of a `sift_col` index** that takes its rows from the index it replaces (docs/USAGE.md, maintenance) writes no temporary file for the rows: 285,000 live rows of a key_cut index wrote 18.7 MB of files and read the table twice (43,266 blocks) from the heap, and 0 bytes and 0 blocks from the index.
- **Temporary files.** A merge reads its input segments into temporary files first (117 MB of segments wrote 224 MB, about 1.9x), and `CREATE INDEX` writes its sorted runs there too: `temp_file_limit` and the free space of the `temp_tablespaces` must cover them. A build of the test corpus wrote 206 MB with `maintenance_work_mem` of 64MB, 1127 MB with 1MB (and left 11 segments instead of 1). *(changes: the streaming merge stages nothing.)*

## Temporary space of a key_cut build

A `CREATE INDEX` or `REINDEX` of a `sift_col` index takes its rows from one of three sources, prices them before it reads a row, and says which it took and what the others would have cost in a NOTICE (`sift.col_build_source = heap` skips the choice and reads the heap, as releases before 5.1 did):

| source | when | temporary files | heap blocks read |
|---|---|---|---|
| the index it replaces | `REINDEX` (not `CONCURRENTLY`, not a rewrite of the table) of an index with the same layout, key and options, no scope, no connection and no value store: any bloat, overlap, write buffer or option change | none | none |
| through a btree on the key | `key_cut` on a table of more than a run, a valid btree whose first column is the key (ascending, NULLs last; the later columns may be anything), and the cost chooser says it is cheaper | none (`temp_files` of the database does not move) | the blocks of the table once when the heap follows the key; again for each entry whose block the cache no longer holds when it does not |
| the heap (key ranges) | no other source, or the chooser says it is cheaper | with `key_cut`: the rows as columnar chunks, written once and read once (2 to 40% of the heap, by what the index holds of each row; the build reads the heap through a btree instead, or is refused, when `temp_file_limit` or the temporary tablespaces cannot take them) | the table once, and a sample of 512 superblocks |

300,000 rows of 13 columns, key in heap order, 64 MB of `maintenance_work_mem` (3 alternating rounds, `perf stat -e instructions:u` of the backend, spread under 0.02%): `CREATE INDEX` through the key ranges 29.66 G instructions, 4.3 MB of files, 42,010 heap block accesses; through the btree 17.02 G, no file, 33,839 accesses (-42.6%); `REINDEX` from the heap 29.58 G, from the old index 8.20 G, no file, no heap block (-72.3%); the indexes are 14.70, 14.44 and 14.31 MB. The peak memory of the build is 20.8, 16.9 and 15.7 MB above the start, whatever the rows. At 474 million rows (a 337 GB heap, 15.6 GB of index) these rates are 67, 38 and 18.5 minutes of CPU for one process (the lab host, heap in memory) and, for the key ranges, files of 6.8 GB (values that repeat) to 43 GB (hash-like values); a btree reads at least the 337 GB once and as many times more as the heap is out of the order of the key (a sorted heap once, an uncorrelated one up to 10.7 rows a block, hence the cost the NOTICE prints against the cost of a random read of the disk); the old index reads its 15.6 GB and no block of the heap. Arithmetic from the measured rates, not a run at that size.

A parallel build reads the btree in disjoint ranges of the key, one stream for each participant, and divides the time of the reads among them; the old index is merged by one process. A `CREATE INDEX CONCURRENTLY` and a `REINDEX CONCURRENTLY` read the heap through a btree under the snapshot rules of a concurrent build (the index is not offered to older snapshots, `indcheckxmin`, and the validation pass adds what the writers did meanwhile) and never take the rows of an index, which writers change while it is read. An index with a scope takes its entities through the path chosen, but the second pass of its scopes files and sorts its own rows (`col_scope_build`), and its old index is not read. A key that is not a number cannot be cut by (`key_cut` refuses text, as the order of a collation is not the order the runs are cut in), so no btree on a text column is read.

The chooser walks the leaf level of every usable btree (only for a btree under an eighth of the heap in size) and plays the heap blocks of its entries through a cache of `shared_buffers`. It costs the reads at what a read costs on the disk of the table, measured at the start of the build: 512 blocks of the heap at random and a stretch of 512 in order, read through a stream made as the build's (as many reads in flight as `maintenance_io_concurrency`), the time divided by the blocks that came from the disk and not from shared buffers (a local NVMe answers in some 10 microseconds, a network disk in some hundreds; a heap the system's cache holds is read faster by the build too, and the probe sees that). The paths cost, besides their reads, the CPU of a row (8.4, 4.8 and 2.3 microseconds for the heap with the key ranges, the heap through a btree and the old index: 98.9 k, 56.7 k and 27.3 k instructions a row of 13 columns, perf stat, 11.7 G instructions a second), and the key ranges 2 ms for each MB of the files (written and read back). The files are priced from rows of superblocks spread over the table, as the build's first run will price them. The participants of a parallel build divide the time of the reads. The page costs of the planner are not used: a role may set them to anything. The NOTICE prints both predicted times and the cost of a random read at which they are equal (the btree is cheaper below it), so the decision can be checked against the disk. When the files of the key ranges would not fit `temp_file_limit` or half of what the temporary tablespaces have free, which refuses the build, and a btree on the key serves, the build reads the heap through it whatever it costs and says so; without such a btree the refusal stays. A heap whose key correlates at 0.96 (a key updated in place all day) reads about the heap once but in no order, and the chooser prefers the key ranges unless the reads are cheaper than the files; a key at 0.3 reads six to nine times the heap and always takes the key ranges.

## Memory

- **Maintenance work is not bounded by `maintenance_work_mem`.** Promotion, merge and a VACUUM segment rewrite keep about 50 bytes per document in memory besides the budget: rewriting a segment of 2.88M documents peaked at 150 MB of resident memory; 500M documents would need about 25 GB, in the background worker or an autovacuum worker. *(changes: the streaming merge bounds it.)*
- **The decision of the automatic `key_cut`** (CREATE INDEX, REINDEX, `sift.key_cut_decision`) reads the rows of 16 to 256 superblocks (a quarter of the heap at most), at most 74,496 rows of each and 400,000 in all (17 units of rows when 16 superblocks hold more), and models the layouts of the index from them. Its memory is `maintenance_work_mem` and a constant, whatever the rows of the table, and it decides the same key: the rows of the sample are records of 8 bytes of address and 8 for each of at most 8 leaves, in a spool kept in memory up to `maintenance_work_mem` and on a temporary file past it, and the model reads them a superblock or a unit of the cut at a time. The cells of a leaf (the distinct values of each sampled superblock with their rows) are made from the rows sorted by value, in one buffer when the memory allows (the sample is read where it is kept) and as runs merged in the order of the values past it, once, for the equality and range tests and the most common value; a layout sorts the keys of the rows of its trial, in one buffer when it fits and as runs merged past it, and cuts the units from that order, holding a unit and the rows the cut looks ahead (149,000 at the most). Nothing is thinned, so the verdicts, reads, ideal units and predicted growth are those of the model that held the sample: 12 table shapes with 7 indexes each, with and without statistics and at 1 MB of `maintenance_work_mem`, and the 42 regress tests of the decision, give the same lines, to the last digit. The exact bytes of the contexts of its stages (the scopes `col_key_cut_decision` for the sample, `col_key_cut_cells` and `col_key_cut_layout`, below), by `col_key_cut_sample_small` on 8-page superblocks at 1 MB of `maintenance_work_mem` and 148,992 to 293,328 sampled rows of 3 leaves: the sample 1,185,320 bytes at every size, the cells of a leaf 16,432 bytes for each of the 64 to 126 runs merged and 57,512 to 65,704 besides, the layouts 16,432 for each of the at most 48 superblocks of the trial and 231,688 to 239,880 besides (a fitted term of 0 to 0.07 bytes a row); the materialized sample held 7,720,672 to 14,136,800 bytes there (44 bytes a row), and 534 MB at the most. At 2 and 4 MB the sample stage holds 2,236,968 and 4,249,792: the memory it may keep and up to 0.14 MB. The rows past it are written to temporary files (10.6 to 17.5 MB for those samples, in 6 files counted by `temp_files` of the database), which the sample, a layout and a leaf's cells each create and close; a rewrite that decides the key again does the same.
- **`CREATE INDEX`** gives every participant (the leader and each parallel worker, `max_parallel_maintenance_workers`) its own `maintenance_work_mem`. Any value from 1MB works; a smaller one is slower (up to 1.5x at 1MB) and leaves more, smaller segments for `sift.merge` to join. Many segments slow queries (a ranked AND took 4.0 ms on 11 segments, 1.8 ms merged), so run `SELECT sift.merge('idx')` or `VACUUM` after a low-memory build. At default settings a build writes one segment.
- **The memory of a `sift_col` build** is what its participants' runs hold, about `maintenance_work_mem` in all (half for the rows of a segment or run, and the sort, the cut and the merge of a run in its own context, freed when it ends), whatever the rows (`sift.test_col_build_peak_kb`, test `col_build_memory`). A build holds at least the working set of a superblock of rows and a run budget of 64 MB (16 MB for the participants of a parallel build); below that `maintenance_work_mem` does not lower it. The sidecar of a scope index is made from the finished entity segments (the second pass of `CREATE INDEX CONCURRENTLY`; the pass at the end of `CREATE INDEX` and `REINDEX`): it reads the pairs of the scope relation once, holds the rows of one run (at most 131,072 rows of one scope key) and the sidecar of the segment in memory until the segment is written, and writes no temporary file; its peak is not yet proven by exact bytes. The build of the entities takes the whole half of `maintenance_work_mem` for a run, and the merge that follows it, whose writer fills its budget, is about 1.03 times `maintenance_work_mem`. The entries of the order arrays of a segment writer (a build, a merge, a VACUUM) wait on temporary files in sorted runs and are read back in order when its segment ends (`col/spool.h`): the writer holds a buffer of `SIFT_ESET_ROWS` (16,384) entries of 16 bytes for each region of a leaf (values, NULL rows), a state of about 29 kB for each of those that spilled, and a reader block of 8 kB for each of at most 64 runs while it merges or builds one (524 kB), whatever the rows; the scopes `col_writer_spool` and `col_writer_order` assert it, and test `col_writer_spool_mem` shows the same bytes at 20,000 as at 36,000 rows. The dictionaries of the text leaves and the arrays of the point directories and grouped orders (16 bytes a row, 33 to 51 held at the end of a segment) are held per segment, not per table: a segment is cut when its writer holds its budget (a build: (`maintenance_work_mem` less 30 MB) / 1.4, at least 16 MB) and the writer is freed with it (scopes `col_writer_dict` and `col_writer_points`, test `col_writer_terms_mem`: the same bytes at 16,000 as at 32,000 rows while the segments grow from 8 to 32, in a build and in a merge). The bound of a context is the budget times the ratio of what it holds to what the writer estimates (a dictionary of unique 32-byte strings holds 57 to 105 bytes a string against 44 estimated); a table that needs more segments than the directory holds (121 for a build) raises the budget to its rows over the segments left (the rows its heap pages have given so far over the pages of the heap, not the planner's estimate: a table never analyzed or with a `reltuples` 5 times too high or too low is cut into the same segments, test `col_build_row_estimate`), and then the two contexts follow the rows of a segment (57 and 51 bytes a row at 3 segments): about 30 to 50 million rows at the default `maintenance_work_mem`, 20 times that at 1 GB. Spilling them past that point is open.
- **The memory of a merge** (`sift.merge`, `sift.col_merge`, the rewrite after a build, the rewrite of a VACUUM). A merge takes the rows of one superblock of every input, folds them into one batch (as many inputs at a time as fit a quarter of `maintenance_work_mem`, at least two: the earlier input still wins a key a later one holds) and writes it through the writer of its partition, which keeps the point arrays of its rows (77 to 90 bytes a row) until the segment ends and ends it at its budget (`maintenance_work_mem` less 36 MB, at least 16 MB, the batches of the inputs counted in it). A batch given back (`sift_cbatch_release`) kept the dictionary of the largest unit it had decoded, so an index with many segments held a dictionary for each of them: the batches of a merge of 1,600,000 rows at 1 MB held 33 MB and now 14.7 MB, 13.8 MB at 800,000 rows (the contexts of the backend, `sift_col merge`). The peak of a forced merge above its start, after two updates that touch 20% of the rows each (the `merge_flat` rows of `scripts/mem-slope.py`, since replaced by `test/t/col_merge_exact_memory.sh`, one `sift_col` index with `key_cut` off, 400,000 / 800,000 / 1,600,000 rows, 20 segments at the largest): 1 MB 45 / 46 / 67 MB (45 / 57 / 84 before), 4 MB 48 / 61 / 62 (55 / 74 / 88), 64 MB 71 / 78 / 86 to 99 (71 / 81 / 125); the runs differ by up to 20 MB at the same size: a resident peak is not a proof, and `test/t/col_merge_exact_memory.sh` replaces those rows with the exact bytes of the `col_merge` scope at 8,000 to 40,000 rows (the same in every run: 1 byte a row, 407 with `key_cut`; the decoded units of the inputs are the scope `col_merge_window`). What grew with the rows next was the parsed dictionaries of the inputs, which a merge pinned in the cache until it ended (2 MB each for the 1,000,000 distinct strings of one column of the fixture, at most 64 MB cached and 32 MB each: 19 bytes a row); a merge now reads each input front to back (`sift_cseg_dict_stream`), parses its dictionary into a context of the segment, outside the cache and the shared ring, and deletes it at the input's last unit: the contexts of the backend of a forced merge at 1,600,000 rows and 1 MB held 35 MB of dictionaries and now 9 MB, the peak above the start at 400,000 / 800,000 / 1,600,000 rows of `merge_flat_1mb` 50 / 63 / 84 MB before and 45 to 48 / 50 to 54 / 59 to 60 MB after (4 MB 50 / 63 / 82 before, 47 to 49 / 52 / 58 to 60 after; 64 MB 68 / 75 / 103 before, 66 to 70 / 68 to 70 / 75 to 78 after: one cluster, the shared ring off, five runs of the gate, 7 to 13 bytes a row between the two largest sizes against 25 to 36 before, so the flat rows now fail above 16); the instructions of the merge at 800,000 rows are 16,306 against 16,309 million at 1 MB and 15,816 against 15,818 million at 64 MB (user space, one backend). What grows with the rows still is the dictionaries of inputs that are all read at once (a merge by key reads every input until its end), the rounding of the partitions at 64 MB (a partition is a share of the live bytes of the inputs, 36 MB of point arrays at 400,000 rows and 48 MB at 533,000), and the sample of the heap that decides `key_cut` again at every rewrite (up to 400,000 rows, 6 to 23 MB, freed before the merge starts: left out by `key_cut = 'off'`). At 800,000 rows the index after a forced merge is 48.2 MB (47.8 to 48.7 over three runs) against 48.2 (48.1 to 48.2) before the change, 58.0 (57.9 to 58.3) against 57.9 with `key_cut`; the instructions of the merge 17.3 against 16.6 thousand million (+4%, noise 5%) at 64 MB, 16.2 against 16.1 with `key_cut`, 17.2 against 17.5 at 1 MB, and the answers of the two queries run after the merge (20,000 rows by md5, and an aggregate) are those of the merge before the change, with `sift.col_verify` clean. The model of a merge: peak = P + D + C, P the writer of the partition (its budget, with the batches of the inputs inside it, or the rows of a partition times their 83 bytes when the directory cap makes the partitions larger than that), D the dictionaries the inputs pin, C the backend and its caches and the sample (about 25 MB). At `maintenance_work_mem` of 4 GB, 460,000,000 rows: P 4.06 GB (a segment ends at 49,000,000 rows, ten segments), C 0.03 GB, D at most 0.1 GB for inputs of millions of rows (a dictionary over 32 MB is read in place from the shared ring, not parsed) but up to 2 GB for 64 small inputs that each hold high-cardinality dictionaries: **4.2 GB (1.04 times)** to 6 GB. It is a prediction from the runs above (1, 4 and 64 MB at 1,600,000 rows), not a measurement at that size; the open terms are the dictionaries and the point arrays of the writer, which a spill to temporary files would bound.
- **Maintenance steady state.** A backend that runs VACUUM, a merge, a promotion, `sift.col_maintain` or `sift.table_maintain` again and again holds nothing that grows with the repetitions (`mem_slope`, kind `leakx`: 25 repeats at 50,000 rows, the 25th within 512 kB of the 10th). What it keeps is bounded: the parsed dictionaries, zones and bisections of the segments of the index (64 MB a backend, and a directory version that no longer lists a segment drops them), 4 spare unit buffers of at most 4 MB, and the lookup keys of the open write buffer (4 million rows, 24 bytes each; the keys of a sealed buffer are freed when the next one is read). A VACUUM that deletes most rows of a `sift_col` index still holds the scratch of its merge, 53 bytes a row (the merge, build-memory lane).
- **Maintenance workers and shared memory.** A maintenance worker that ran 24 consecutive VACUUM-driven runs (promotion and merge) of a 50,000-row index held 12 to 28 MB of anonymous memory, flat across its steps (a first worker that caught up 71 segments peaked at 250 MB: the merge); 60 s of inserts (2,000 rows each) with a rewrite pending left the shared memory at 93.6 MB, the temp files and dynamic shared memory files at 0 and the rollup queue empty. A bm25 merge holds about 11 B per row of the index at `maintenance_work_mem` of 1MB and 24 at 4MB or 64MB (50,000 to 200,000 rows), flattening to 10 between 100,000 and 400,000 rows.
- **A merge of segments** is written by the backend and up to `max_parallel_maintenance_workers` workers when its segments are large enough to cut (about 1 MB of postings); each participant gets `maintenance_work_mem` divided by their number. `max_parallel_maintenance_workers = 0` merges in one process.
- **Wide prefixes** (`ab*` over a large vocabulary) gather their postings in the backend: `sift.prefix_cache_size` (default 8MB) caps the
  cache, `sift.max_expansions` the terms of a wildcard, regex or fuzzy leaf. Both are per-session settings.
- **Caches kept for the next statement** (parsed dictionaries, bm25 segment bytes, rows of joined tables, the strings of shared value stores, the facts planning reads of partitions) hold at most `sift.backend_cache_kb` (default 128MB) together in each backend, besides the limit of each: with 200 pooled connections that is 25 GB at the most, not the sum of the separate limits (about 480 MB a backend). The least recently used entry that no statement holds goes first; `-1` leaves each cache to its own setting. Idle backends keep what they cached, so lower it for large pools.
- **A pooled backend that has run every kind of statement** (aggregates, lookup joins, `count(DISTINCT)`, search, partitions, writes, VACUUM, merges, verify, index builds: `test/idle-series.tsv`) holds about 100 to 125 MB of anonymous memory after a few thousand statements with 100,000-row tables, of which about 50 to 60 MB are live contexts (the caches above, each within `sift.backend_cache_kb`) and about 45 MB are memory that C library keeps free after the peaks of heavier statements: `malloc_trim` gave back 33 MB of it. It climbs in steps for the first several thousand statements and then moves inside a band; it does not follow the number of statements. A pool that cares about that figure can recycle its backends (the server lifetime of a pooler); fixing the C library's mmap and trim thresholds did not shrink it.
- A ranked scan keeps `LIMIT + OFFSET` hits in memory (16 bytes each); very deep pages (`OFFSET` in the millions) cost that.

## Memory budgets

Every main path declares the memory it may hold as a formula of the settings above plus a fixed constant, never a number of rows (`test/mem-budgets.tsv`). The test build asserts it wherever a test runs the path: a path over its budget fails with `sift memory budget exceeded: <scope>: <actual> > <budget> bytes (<formula>)`, and `sift._test_mem_highwater()` and the `SIFTMEM_SCOPE` lines of the server log give the peak of each scope. The release library carries none of it. An `open` row is a defect that is being fixed: its budget is the ceiling measured today, and it flips to the formula in its `target` when the fix lands.

## Dead documents and statistics

Rolled-back and deleted rows stay in the index's document count, document frequencies and average length until VACUUM marks them dead. From then on a segment of format 2 or later leaves them out of all three, so a dirty index scores exactly as the merged one does (`test/sql/live_stats.sql`). A format 1 segment (2.x) keeps counting them until it is rewritten (a merge, or a VACUUM that finds it more than `dead_rewrite_pct` (50) percent dead); no REINDEX is needed. Effect of counting them (`bench/sql/dead_docs.sql`, 50,000 live documents, four rolled-back loads of 50,000):

| dead documents | top-score change | top 10 of 5 queries |
|---|---|---|
| like the live ones | -1.3% to +0.4% | unchanged |
| all about one term | -24% to +1.7% | 3 of 10 kept for `w40 OR w41 OR w7`, the others unchanged |
| after `VACUUM` | exactly the original (2.x: -5.7% to +0.3%) | unchanged |
| after `VACUUM`, `sift.promote` and `sift.merge(index, true)` | exactly the original | unchanged |

`sift.segments(index)` shows `dead_docs` of immutable segments (marked by VACUUM); rolled-back rows not yet vacuumed appear only as the difference between `sum(ndocs)` and the table's live rows. Autovacuum counts aborted inserts as dead tuples, so a table whose loads often fail should have a low `autovacuum_vacuum_scale_factor` (or a manual `VACUUM` after the failed load).

Vacuumed documents also cost query time until their segment is rewritten, because a query that walks postings drops the dead ones through the liveness rows of every page it reads. Cost of the dirty segment relative to a clean one (the same live rows rebuilt by `REINDEX`), in user instructions per query (`bench/dirty-query.sh` data, 200,000 documents, 10 to 45% deleted and vacuumed; not 1.3.1 code: the 2.0.0 and 2.0.1 builds and 3.0, format 2 segments):

| query | 2.0.0 | 2.0.1 | 3.0 |
|---|---|---|---|
| `count(*)` of a term | 18.5 to 18.6x | 6.6 to 6.7x | 1.16 to 1.28x |
| `count(*)` of two terms | 3.5 to 4.4x | 1.7 to 2.3x | 1.0 to 1.25x |
| `count(*)` of three with OR | 4.5 to 6.2x | 1.5 to 2.1x | 1.0 to 1.2x |
| ranked AND, top 10 |  |  | 1.0 to 1.3x |
| ranked OR of three terms, top 10 |  |  | 1.3 to 1.8x |
| a rare term, top 10 |  |  | 1.3 to 2.0x |

A term count is the sum of its live document frequencies (each segment stores the vacuumed postings of every term) corrected for the pages the heap decides, so it does not depend on how much of the segment is dead. Queries that read postings still read the dead ones before dropping them: up to twice the clean cost at 45% dead. Not-yet-vacuumed rolled-back rows are not in the liveness rows and cost one heap check each, as many as the dead rows among the candidates (`bench/dirty-query.sh -m rollback`).

## Updates

A `HOT` update does not touch the index; any other update inserts the row's text into the index again, even when the indexed
column did not change: rows are found by TID and the new row version has a new one, so PostgreSQL's `indexUnchanged` hint
cannot let the insert be skipped. A table with large indexed texts (100 kB) and frequently changing other columns should leave room
for HOT updates: `ALTER TABLE t SET (fillfactor = 80)` (applies to new pages) and keep other indexes off the updated columns.

## A `sift_col` index at 30 million rows

One run each on 2026-10-23, PostgreSQL 18.6, `shared_buffers = 8GB`, autovacuum off,
a table of 29,526,504 rows in arrival order (28 GB of heap, 13 columns, 22 leaves with five JSON paths). Sizes and WAL are exact; times are indicative. Nothing here is measured above 30 million rows.

| build | workers | `maintenance_work_mem` | seconds | WAL | segments | private memory, all processes |
|---|---|---|---|---|---|---|
| `CREATE INDEX` | 0 | 1GB | 65.6 | 746 MB | 1 | 150 MB |
| `CREATE INDEX` | 2 | 1GB | 31.1 | 750 MB | 3 | 160 MB |
| `CREATE INDEX` | 8 | 2GB | 17.0 | 750 MB | 9 | 186 MB |
| `CREATE INDEX` | 16 | 4GB | 16.9 | 750 MB | 9 | 188 MB |
| `CREATE INDEX CONCURRENTLY` | 8 | 2GB | 26.1 | 750 MB | 9 | 766 MB |
| `REINDEX` | 8 | 2GB | 17.2 | 750 MB | 9 | 188 MB |
| `REINDEX CONCURRENTLY` | 8 | 2GB | 25.5 | 750 MB | 9 | 766 MB |

- **Size and WAL:** 743 MB of segments (25 bytes a row, 2.6% of the heap); the build writes that much WAL plus 0.5% (pages are logged once). The build is linear in the rows (2.2 us a row serial); no worker count above 8 helped on this host. PostgreSQL grants one participant per 32 MB of `maintenance_work_mem`, so 16 workers asked with less than 544 MB run with fewer, without a message. `pg_stat_progress_create_index` shows `blocks_done` rising to `blocks_total` (3,728,640 here) during a parallel scan.
- **Concurrent build:** 1.5x the time and about 600 MB more memory (the validation pass sorts the row identifiers of the whole table); it also waits for every older transaction, as any `CREATE INDEX CONCURRENTLY` does.
- **Parallel build:** one segment per participant (3 with 2 workers, 9 with 8, also 9 when 16 were asked for). The first `VACUUM` after it rewrites them into one: 31.5 s and 747 MB of WAL, and the file doubles (1.42 GB for 0.71 GB of live segments; the next `VACUUM` changed nothing) because the free space is in front of the live segment; `REINDEX` compacts it, and a parallel `CREATE INDEX` or `REINDEX` does that rewrite itself: it reserves a gap in front of the participants' segments, merges them into it and cuts the file behind it (VACUUM cannot while a standby streams; the file of a build belongs to the transaction): 3,000,000 rows, 13 columns, 8 workers, a streaming standby, the file 206 MB with 99 MB live after the first VACUUM, 115 MB with 115 MB live now; the build takes 39.3 against 18.9 CPU seconds and writes 255 against 104 MB of WAL (27.8 s and 205 MB with the first VACUUM it replaces) (the gap it reserves is the statistics' estimate of the index, which overstates the json columns of this table: 202 MB for 115 MB live, so the file peaks near 2.8x the index during the build and ends at 1.0x; the estimate is 1.7x the live bytes of 9 plain columns, 47 MB for 28 MB at 500,000 rows, and 2.0x of 19, 183 MB for 90.5 MB, and a gap of 1.1x the live bytes costs the same, 6.7 against 7.1 s and 185 against 185 MB of WAL at 19 columns, 1.8 against 1.8 s at 9, while no gap at all costs 276 MB of WAL there: the estimate stays generous, a gap that is too small is what costs; a build that launches no worker reserves none: with `max_parallel_workers = 0` the 28 MB index takes 28 MB of file and 28 MB of WAL) (and the first VACUUM no longer costs 8.9 s and 101 MB), `REINDEX CONCURRENTLY` keeps the old behavior. `sift.col_merge(index, true)` on the same index took 31.0 s and 747 MB of WAL. A build with `key_cut` is made in parallel only when the merge that follows the scan is made in 3 slices or more (an index of about 30 MB or more at the default `maintenance_work_mem`; the statistics estimate it, 1.7 times what is written): the merge rewrites every row and takes 0.7 to 0.9 of the time of the scan of one process, so under it one process builds the index (1,000,000 rows of 13 columns: 2.9 s alone, 3.4 to 4.0 s with 2 to 8 workers before this rule; 2.3, 2.1 and 1.8 s with the slices). A build without `key_cut` is always shared (1,000,000 rows: 1.7 s alone, 0.77 s with 2 workers, 0.34 s with 8).
- **Temporary files of a `key_cut` build:** a serial `CREATE INDEX` or `REINDEX` of a `key_cut` (or `key_order`) index on a table of more than one run writes the rows to one temporary file for each range of the key while it scans the table, and the NOTICE at the start says how many ranges, how many MB it expects and how the rows are written. The rows of a range go to its file as columnar chunks, encoded with the codecs of the index (frame of reference, delta, dictionary, run lengths, decimal scaling), with a layer of zstd (else lz4) on top when a sample of the first run shrinks by a fifth with it, and the strings of a range in one dictionary of the range: the NOTICE gives the rows of a chunk and the layer (`cascade` when no layer pays). The chunk is as many rows as the memory of the build holds for all the ranges, up to 16,384 (`maintenance_work_mem / 2`, at least 64 MB: the budget of the build, shared by the chunks of the ranges, which a range writes as soon as its rows or its share of the memory are over); when that holds fewer than 512 rows for each range (many ranges for a small budget) the rows are packed in blocks of 32 kB for each range, as before, and the NOTICE says `packed in blocks`. Measured on 200,000 rows of 12 columns and four path sets, the key not correlated to the heap, values that repeat: 66.5 bytes a row of files with the packed blocks, 8.3 with the chunks (the index is 41 bytes a row); the same table with hash-like values and 20,000 distinct strings: 195.4 and 91.1 (the index 165). With 154 ranges at 64 MB (chunks of 512 rows) 48.5 and 14.1. The build takes 4 to 5% more instructions than with blocks (4.4% and 4.9% at 64 MB and 1 MB of `maintenance_work_mem`), 8.7% with the chunks of 512 rows. They count against `temp_file_limit` and go to the first `temp_tablespaces`; the build is refused before it writes them, with the bytes it needs in the message and `temp_file_limit` and `temp_tablespaces` in the hint, when they exceed `temp_file_limit` or half the free space of a temporary tablespace (the index goes to the disk of the data, which may be the same one); the bytes are those of the chunks of a sample of the first run, times the rows of the table. The chunks of all the ranges hold at most the budget of the build while the table is scanned (scope `col_build_spool` of the table above), and the blocks of the packed form are 32 kB for each range at most and the budget between all the ranges (a build of 512 ranges at the shipped budget of 64 MB or more holds 16 MB for them besides `maintenance_work_mem`). The rows of a run read back from the chunks come a chunk at a time, so a run holds up to a chunk more than its budget.
- **Temporary files of a scoped build:** the sidecar of a scoped index writes none (the 5.0 scope segments wrote 14.8 MB for 626,630 entries on the lab fixture of [COL-SCOPE.md](COL-SCOPE.md#what-it-costs)); the entities are built as those of any index. `CREATE INDEX CONCURRENTLY` also has the sort of row identifiers that PostgreSQL does (about 30 bytes a row at that memory). A `key_cut` index (also scoped) is built by one process, so its key is in one unit when the build ends.
- **A `key_cut` build and the rewrite after it:** runs that overlap in the key (a key that is not a number, a key of two values, the participants of a parallel build) are cut by key by the rewrite of `sift.col_maintain` (a parallel build merges its participants' runs at its end), whose output goes into new blocks while the blocks of the runs wait for the snapshots that can read them. 300,000 rows, 13 columns, a first run three times the cap of a run of the ranges: the file 54.1 MB after the build of overlapping runs, 95.3 MB after the rewrite pass (1.76x) and 153.6 MB (2.84x) with a snapshot held through three passes, 55.5 MB after the `VACUUM` that follows once the snapshot is gone; the build by ranges ends at 67.0 MB live in a file of 67.9 MB (1.01x) with runs a third of the size (the point directory and the order arrays cost about 1 MB a run at this size). A `maintenance_work_mem` of 1.5 GB or more used to turn the ranges off (the cap of a run is 768 MB of rows in memory); it now cuts the runs at the cap. `sift.col_sections` shows the shares (`point_dir`, `order_arrays`, `free`). A snapshot that holds a pass back (a standby with `hot_standby_feedback`, a long query, the transactions of `REINDEX CONCURRENTLY`) keeps the blocks that pass freed from being reused, so the rewrite of `sift.col_maintain` waits for the horizon once the blocks held reach one pass (`sift.col_auto_merge_pass_mb`) or half the index, whichever is less, and the file stands at the live bytes plus one pass meanwhile (`sift.col_maintenance_status` names the snapshot). Overlapping runs of 300,000 rows, 13 columns, `sift.col_auto_merge_pass_mb = 6`, a snapshot held through the passes: the file was 1.26, 1.41 and 1.55 times the live bytes after the first three passes, where the gate stopped only at half the index, and is 1.11 times after the first pass now, which is where the rewrite waits. When no rewrite is running (it is not due, or it waits for a horizon that has passed) `VACUUM` moves the segments that end the file down into the holes and cuts the file, with a standby streaming too: the first `VACUUM` moves them, the cut follows once the horizon has passed what moved (a file of 15.2 MB for 5.1 MB live was 5.2 MB after three `VACUUM`s; before, twelve left it at 11.4 MB).
- **A rewrite costs the whole index, not the change.** Six daily cycles of 29,526 inserts, 14,763 scattered updates and 29,526 updates of one burst each: `VACUUM` took 0.5 to 3 s and `sift.col_maintain` 5 ms until the write buffers and dirty units crossed the threshold, then rewrote everything (31 and 33 s, 1.0 and 1.2 GB of WAL with the table's own), once every 2 to 3 days of such changes. The file stayed at 2.1x the live segments (1.52 GB for 0.72 GB). Plan the free space of a rewrite (about 2x the index) and its WAL. `sift.col_index_status` shows `index_bytes`, `free_bytes`, `dirty_segments`, `dead_pct` and why a rewrite is `due` in 13 ms (`sift.col_leaves` takes 0.4 s, the other views 4 to 36 ms at 14,565 units).
- **Hot standby:** same answers, same plan, a faster scan than the primary (the aggregate over 29.8M rows: 134 to 138 ms against 163 to 166 ms). It replays a 100,000-row insert 0.2 s after the commit, a rewrite of 765 MB of WAL in 0.8 s and a `REINDEX` of 769 MB in 1.0 s (700 to 900 MB/s); a base backup of the 33 GB database took 47 s. Long queries need `hot_standby_feedback`, as above.
- **Crash recovery** is the redo of generic WAL and nothing else: after a rewrite and a `REINDEX` (1,463 MB of WAL since the checkpoint) the server accepted connections 3.3 s after `pg_ctl stop -m immediate` (a b-tree `REINDEX` and insert, 463 MB: 1.3 s), with the same answers.
- **`sift.col_verify(index, true)`** sorts a hash for every live row (about 130 bytes each) within `maintenance_work_mem` and spills the rest to temporary files: 6 bytes of memory a row at 1 MB of it, where it held the whole array (29.7M rows took 70 s and 2.3 GB of private memory in 5.0.0, and failed with `invalid memory alloc request size` above 16.7 million rows before that). The answer is exact: every heap tuple is compared with its row of the index, as before.
- **`sift.tomb_log_limit`** (64 MB by default) is the memory a backend keeps of the tombstone log of a `sift_table`: 64 bytes for each row deleted or updated since the last `VACUUM`. The entries past it are kept in sorted runs on temp files (a block read for each run when a lookup misses the memory), so a read of a log of any length, and a `DELETE` or `UPDATE` of any number of rows, completes within the setting: a `DELETE` of 400,000 rows held 1.8 MB at a limit of 1 MB and 14.3 MB with the log in memory. Only `temp_file_limit` or a full disk stops it: the fold of the marks of an index (keys waiting past the limit are a temp file too) then ends with an error, holds nothing, and the next fold clears the rows. A `CREATE TABLE AS` or `COPY` into a `sift_table` writes no log: its rows wait in the writer of a segment, which ends at half of `maintenance_work_mem` and at least 64 MB.
- **`count(DISTINCT text)`** interns each distinct string (about 88 bytes a value) while the scan runs; past `work_mem` times `hash_mem_multiplier` the scan ends and the statement runs again as PostgreSQL plans it (the sort of its values spills), so the memory of the statement follows the setting, not the number of distinct values: 3 bytes a row at 1 MB, where it was 75 to 79. The planner does not price this rerun; a statement that cannot run again keeps its values in memory.
- **`pg_dump` writes only `CREATE INDEX`**: a restore builds the index again, at the times above.

## Settings that matter

| Setting | Effect |
|---|---|
| `maintenance_work_mem`, `max_parallel_maintenance_workers` | `CREATE INDEX` speed and segment count (above) |
| `temp_file_limit`, `temp_tablespaces` | `CREATE INDEX` runs and merge staging (above) |
| `autovacuum` and its scale factors | marks dead documents, promotes and merges; the index does not shrink without it |
| `hot_standby_feedback = on` on replicas | merges free blocks a replica query may still read; without feedback the replay waits for such a query up to `max_standby_streaming_delay` and then cancels it (`sift.standby_conflicts`, on), as for a heap query; with that setting off it fails at once with a retryable "segment recycled during scan" (40001) |
| `max_worker_processes` | the maintenance worker needs a slot; when none is free the log says so and the inserting session promotes and merges itself |
| `sift.log_min_duration` | logs promotions, merges and worker runs that take at least that long (default 1s, -1 off) |
| `sift.async_maintenance` | off: only VACUUM and the inserting sessions promote and merge |

## Features and their costs

- **Materialized views** can carry a sift index and get ranked scans and `count(*)` pushdown like tables.
- **`SERIALIZABLE`**: a SiftScan takes a predicate lock on the whole heap relation, and a bitmap scan on the whole index (PostgreSQL does this for every index access method without predicate locks), so a concurrent write to the table can make a serializable transaction fail with `40001` where a btree-indexed query would not. Retry on `40001`. Finer locks would need one per term searched (a new document conflicts only if it has that term) and one for the vocabulary range of every wildcard, prefix or regex; a lock per page does not work because a document is appended to the write buffer, not to the page where its terms are read.
- **Row-level security and security barrier views.** A role under a policy (or reading a security barrier view) gets no ranked scan, no `count(*)` pushdown and no index estimate: the match is not leakproof and the index statistics (document count, document frequencies, expansion limits) include rows the role cannot see, so a score or `EXPLAIN` estimate would depend on hidden rows (before 2.0.1 a score of 4.99 for a term of 20 visible documents was `ln(1 + (3020 - 20 + 0.5) / (20 + 0.5))`, computed with the 3,000 rows a policy hid). Its matches come from a sequential scan, slower on a large table, and `sift.score()` raises an error. The table owner, who bypasses the policy, keeps the scan. With `sift.rls_scores = on` (superuser) the role gets the ranked scan, and a score then does depend on the hidden rows ([USAGE.md](USAGE.md#row-level-security)).
- **`ALTER INDEX ... SET/RESET`** of `k1`, `b` or an analyzer option (`stemmer`, `fields`, `analyzer`, `prefix_index`, folding) needs a `REINDEX`. Until then queries and inserts on the table fail ("built with other analyzer options") and the statement warns. To change them without downtime, build the new index with `CREATE INDEX CONCURRENTLY` and drop the old one.
- **`ANY (array)`**: ``col @@> ANY (ARRAY['a', 'b'])`` is the OR of the elements, scanned and scored like ``col @@> 'a OR b'`` (`sift.score()`, `ORDER BY`, `LIMIT` and `count(*)` work). A NULL element is skipped; a NULL or empty array matches no rows. A list with no score or order that is estimated above 100,000 rows (after a `LIMIT`) is left to the bitmap scan, as fast or faster there on a 1,000,000-row table.
- **`FOR UPDATE`, `UPDATE`, `DELETE`, `MERGE`**: matching works through a bitmap scan; `sift.score()` read straight from a table those statements join is an error; a subquery or `WITH` query that reads it is planned apart (rank there and change the rows by key).
- **Indexes beyond 2^31 blocks (16 TB).** The orphan sweep and `sift.verify` collect block numbers in PostgreSQL `Bitmapset`s, which stop at 2^31 members: a larger index is untested and unsupported (the format itself allows 32 TB).

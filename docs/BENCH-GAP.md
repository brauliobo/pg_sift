# Gap report: pg_sift against ClickHouse and Elasticsearch on the store questions

Internal tooling. The goal for 3.0 is for pg_sift to be faster than ClickHouse and Elasticsearch on the quick aggregation questions of the
online-store benchmark ([BENCHMARKS.md](BENCHMARKS.md#analytics-an-online-store)). This file says where it is not, where its time goes, and the
single change that would move each question the most. The tables below are generated; the text under "Findings" was written from the first
profile (below) and has to be re-read after every regeneration.

Status: **a snapshot of 2026-10-18 (historical baseline), taken on a 3.0 development build.** The per-unit pre-aggregates (`6681929`), the BM25 match
sets as the row selection of the aggregate pushdown (`74f771e`), the scan priced by stored bytes (`25e5075`) and the `count(DISTINCT)` bitmaps (`92cf75a`)
were merged after it, and the 3.0 final pass (2026-10-19, `sift_col`, 3 CPUs, [BENCHMARKS.md](BENCHMARKS.md#analytics-an-online-store)) measured questions 02 to 04 at
1,000,000 orders in 0.793, 0.816 and 0.841 ms against the 5.64, 4.69 and 4.45 ms of the first gap table below. The pg_sift profile is measured; the ClickHouse and
Elasticsearch columns of the gap tables are those of the preliminary run of 2026-10-18 (7 warm runs, 4 CPUs per container, 1,000,000 and 10,000,000 orders: `docs/results/store.json` of
commit `2699fb1`), which `docs/results/store.json` no longer holds: it now has the final pass of 3.0 at 1,000,000 orders (1 and 3 CPUs), so `bench/bench store gap` on it prints other tables than
the generated ones below. The engines' own accounting (rows and bytes read, memory, threads) is still to be measured: the owner asked for
ClickHouse and Elasticsearch to run only once v3 is final (`bench/bench final --docs`, which fills this file in).

## Re-measuring

| what | command |
|---|---|
| the quick run (200,000 orders, the same equality checks, a few minutes) | `bench/bench store all --size quick` (results in `bench/out/latest/store.json`) |
| two runs side by side, ratio of every warm median | `bench/bench store compare A.json B.json` |
| the gap tables of a results file | `bench/bench store gap [docs/results/store.json]` |
| the pg_sift profile (private cluster under a memory cap) | `S_SIZES=1000000,10000000 bench/steps/gap.sh` |
| everything, once the code is final | `bench/bench final --docs` (`--dry-run` prints the plan, time and preconditions) |

The results JSON has one format (`meta` and `rows` with `dataset, tier, engine, class, variant, metric, unit, value, min, max, stderr, n, values`); runs are diffed with `compare`.

## Planning

Planning time is measured in two ways, both on the pg_sift cluster: `EXPLAIN (ANALYZE)` inside one backend (the first statement of a backend, with empty
caches, and the median of the later ones), and `pgbench` running `EXPLAIN (COSTS OFF)` 400 times on one connection (parse, rewrite and plan, without
execution), best of three, for four setups: no sift library loaded in the session (a plain table), the library loaded (`session_preload_libraries`) on the same plain table,
a sift table with `sift.enable_agg = off` (the planner hook returns at once) and with it on (SiftAgg planned). The share is the warm planning time against the
`sift_col` median of the store benchmark.

## Findings (from the profile above; re-read after a new run)

Sources: the gap tables (store.json of 2026-10-18, commit `2699fb1`, 7 warm runs, 4 CPUs per container), the profile tables (private cluster, pg_sift 3.0 built from this checkout, `-O3`, AVX-512 host, the
store.json settings), `EXPLAIN` plans in `docs/results/store-gap-*.json`. "Estimate" marks a number projected from a measurement, not measured.

### Planning is not the lever

- Planning in a warm backend takes 0.01 to 0.17 ms, at most 3.1% of the `sift_col` median of the same question (0.4% to 3.1% at 1M). The planning time of the first statement of a new backend (empty caches) is 0.5 to 1.3 ms, which is the 1 to 2.5 ms a client that opens a connection per query sees; the store benchmark keeps one connection.
- The planner hook costs nothing measurable: parse and plan of the same plain-table statement takes the same time with and without the library loaded (differences of at most 0.03 ms, largest for question 09), and planning a `SiftAgg` against `sift.enable_agg = off` differs by less than 0.02 ms.

### Worker start-up decides the 1M numbers

A `SiftAgg` that reads nothing (every unit pruned by its zone map) takes 3.1 ms with 3 workers launched at 1M (6.5 ms with 4 workers at 10M) and 0.01 ms (0.15 ms) without workers: starting
the workers costs as much as the whole query at 1M. Questions 02 and 07 run in 4.9 and 5.9 ms with workers and in 2.5 and 2.9 ms without; the other aggregate questions are planned without workers at 1M and take 3.7 to 4.4 ms.
Most of the 4 to 6 ms medians of `sift_col` at 1M in the benchmark are this floor plus the client round trip.

|---|---|---|---|

| 03 revenue per month | none with the request cache off; 12x slower than a cached Elasticsearch answer at 10M (1.5x at 1M) | 72 instructions per row; `join_stage` (the aggregation of a chunk, group ids and updates inlined) 23 to 27%, `eval_nx` 9%, `gid_i32_avx512` 8% | none needed to lead (faster than both with the cache off); the numeric `sum` is decoded per row (`eval_nx`) |
| 04 top categories | 10M: 16.7x ClickHouse, 3.0x Elasticsearch (812 ms; 4.4 ms at 1M, a win) | the plan flips at 10M: `Gather Merge` over a `Parallel Seq Scan` with `Partial HashAggregate` (cost 169,291, 441 to 615 ms in two profiles) instead of `SiftAgg` (cost 167,846 in the plan without workers, 45 ms): the two are costed 0.9% apart and run 10x apart | cost `SiftAgg` by the units and column bytes it reads, not as a heap scan, so that it wins whenever it applies, and cost its parallel path the same way; expected about 45 ms (estimate: the measured no-workers run), ClickHouse 48.7 ms |

### Reading order for the fixes

By the size of the gap at 10M: question 04 (planner cost, the largest and the smallest change), 09 and 10 (BM25 match set into the column scan), 06 (distinct set), 07 and 05 (predicate order), 02 (count kernel); and, at 1M, the number of workers chosen from the estimated units.
After each change `bench/bench store all --size quick` re-measures in a few minutes and `bench/bench store compare` diffs it against a saved run; `bench/steps/gap.sh` re-profiles.

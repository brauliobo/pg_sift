# Aggregate pushdown on column indexes (SiftAgg)

Plain SQL over a table with a `sift_col` index (or a `sift_table` table) runs on the column data when the planner can prove the result is the one of the normal plan; everything else keeps the normal plan. `sift.enable_agg` (default on) switches the matcher. The result of a pushed query is the one of the plain plan, row for row: `scripts/coldiff.sh` runs every query both ways and compares (docs/AGG.md).

Files: `src/agg/plan.c` and `src/agg/plan_*.c` (shape matcher, cost), `src/agg/spec.[ch]` (what the planner proved, serialized into `custom_private`), `src/agg/agg.c` and the executor files beside it (`agg_int.h`, `unit.c`, `update.c`, `init.c`, `par.c`, ...; executor, EXPLAIN), `src/agg/kern*.c`, `src/agg/colsrc.h` and `src/agg/colsrc.c` (the seam to the column data and its provider registry), `src/agg/col.c` (provider over the `sift_col` index), `src/agg/pre.[ch]` (the pre-aggregates of a unit as the seam's records, shared by both providers), `src/table/src.c` (provider over a `sift_table` table, docs/COL-TAM.md section 6), `src/agg/stub*.c` (test provider, the `sift_colstub` index AM, `SIFT_TESTING` builds).

## What matches

`create_upper_paths_hook`, stages `UPPERREL_GROUP_AGG` and `UPPERREL_DISTINCT` (a `SELECT DISTINCT` of a plain scan is a group-by with no aggregate: same keys, same scan, the distinct target as output; not over a grouped or windowed query; `DISTINCT ON` is a group-by whose columns are first-row aggregates, see docs/AGG.md). Query shape: one relation (no inheritance, tablesample or row security) with an index of a provider, at most one lateral unnest of an indexed jsonb array or object (`jsonb_to_recordset`, `jsonb_array_elements`, `jsonb_array_elements_text` of an array of strings, `jsonb_each`, `jsonb_each_text`), inner joins in the FROM list flattened, no DISTINCT ON in the aggregating query. A window function of the same query level (`sum(sum(x)) OVER (ORDER BY month)`, `rank() OVER (ORDER BY count(*))`) is planned by PostgreSQL above the grouping stage, so the stage is the same with or without it.

| Part | Supported |
|---|---|

Unproven means no path. Not matched today: volatile expressions and transition functions, an expression of more than eight leaves, columns that are not in the index, joins that are not lookups of the kind below, a `UNION` of aggregates in one pass (see Shared CTE), nested aggregation of the unnested rows, and an `@@>` that is not a top-level `AND` conjunct (an `OR` with another predicate, conjuncts on two BM25 indexes: `docs/COL-SEARCH.md`, Limits). Each is a documented gap, not a silent difference: the query keeps its plan. The numeric ones are listed once, with the reason, in "What keeps the normal plan" under "Expressions PostgreSQL evaluates"; the aggregates that stay generic are in Generic aggregates. What stays on the normal plan is listed once per family, each shape with its reason: expressions ("What keeps the normal plan"), generic aggregates ("Generic aggregates"), joins and the per-order form ("Stays on the normal plan").

### Lookup joins, several leaves, per-order aggregates

- **Lookup join**: `[LEFT] JOIN small ON small.k = <leaf>` (one to three equalities of dictionary/integer/date leaves and columns of the table, up to 32 tables and 128 combos), `EXISTS` / `IN (SELECT ..)` (semi join: the row stays once however many rows match) and `NOT EXISTS` (anti join: the row stays when none matches), a key that is an expression of leaves (`small.k = lower(o.source)`), the rest of an `ON` that is no key (`ON small.k = o.x AND small.flag`, `AND o.y > small.min`: a filter of the combo; for a `LEFT` join it decides the match, for an inner join it is a `WHERE`), and a `WHERE` on the joined columns of an outer join (evaluated after the join, so an unmatched row meets NULLs). At least one equality of leaves and columns is the key; a join with none stays. The table is read at executor start with the query's snapshot; its rows are matched per distinct tuple of leaf values, cached across units. Exact: every matching row replicates the input row (a non-unique table needs no proof), a NULL key matches nothing, text compares as `=` does (deterministic collations), the unmatched rows are one row with NULLs (`LEFT`) or gone (`INNER`). The mapped columns are keys, filters and `CASE`/`coalesce` operands like leaves. `count`, `count(DISTINCT)` (hashable types), `min`, `max` (types with a btree order) and `sum`, `avg` (`numeric`, `float8`) of an expression of the joined columns are taken per matching row: the value is `NULL` for an unmatched `LEFT` row (an `INNER` join drops the row), the distinct values of the expression are kept once, and the aggregate compares them (the type's own comparison function) or adds them (`numeric` through its own functions, so the scale of the result is the normal plan's) when the scan ends. `sum` and `avg` of `int2`/`int4`/`int8`, `interval` and `avg(float4)` run PostgreSQL's own transition and final functions of `pg_aggregate` on the distinct values and their counts (`SAA_M_PG`: the state is copied and added `count` times as `nodeAgg` would, strict inputs skipped), so the type and scale of the result are the normal plan's.
- **Several leaves**: a key or filter over up to eight leaves (of the order and of its items: `CASE WHEN o.lang = 'en' THEN i.category ELSE ... END`) is evaluated by PostgreSQL per distinct tuple of the values, cached across units. `x->>'k' IS [NOT] NULL` on a leaf of another type is the null test of that leaf (a value it cannot hold raises the overflow error above).
- **Arrays of strings and lengths (3.1)**: `tags[] text` has one unnamed child, the element: `jsonb_array_elements_text(col->'tags') t` groups, counts and filters on `t` like on a field of an array of objects, and `col->'tags' ? 'a'`, `?|`, `?&` and `@>` are tests over the elements. `jsonb_array_length(col->'tags')` is a leaf after the source's, an int4 read from the element counts of the array (NULL where the array is absent; a JSON null in its place counts as absent where the normal plan raises an error, and a scalar or an object there raises the overflow error above). A number or a boolean among the strings is a value the text leaf cannot hold: the same overflow error, whose hint turns the pushdown off. Test `agg_jsonb_array`.
- **The text of any scalar (3.1)**: a path declared `astext` (`scores.* astext`, `items[]{score astext}`) holds what `->>` gives for a string, a number (as `numeric_out` prints it) or a boolean. `col->>'k'`, the `value` of `jsonb_each_text`, `jsonb_array_elements(...)->>'k'` and the `text` columns of `jsonb_to_recordset` read it: regular expressions, `LIKE`, `length`, casts and any other text expression run once per distinct text, as on a `text` leaf. The flag is in the index definition (`SIFT_COLD_ASTEXT`), the leaf is an ordinary text leaf in the segment, and the planner never uses it for `@>`, `?`, jsonpath or `jsonb_each`, where `"12"` and `12` differ. An object or array at the path raises the overflow error above. Test `agg_jsonb_astext`.
- **Key of a free key object**: `(o.metrics->>'m_total')::float8` next to the unnest, when the index has `metrics.* float8`, is a row level leaf built per unit from the elements whose key is `m_total` (NULL for the rows without it).
- **Per-order aggregates**: `SELECT .. avg(x) .. FROM (SELECT o.id, keys, agg(..) AS x .. GROUP BY o.id, keys) GROUP BY keys` and the same over a `UNION ALL` of up to four such arms (rollup levels over a shared CTE), where each arm groups by the unique id and by outer keys (or a NULL constant). The inner groups are one row's share of an outer group, so the scan keeps the inner aggregates (`count`, `sum`, `avg`, with `FILTER`) of the current row per outer group and adds them to the outer `count(*)`, `count(DISTINCT id)`, `avg`, `sum` (each with `FILTER` over the inner columns) when the row is done. A WHERE on the outer query is taken when PostgreSQL pushed all of it into the arms: quals on the keys filter the rows of an arm, quals on the inner aggregates are the arm's HAVING (a cell that fails it is no group of the arm and adds nothing to the outer aggregates). A HAVING or WHERE conjunct that is not `inner aggregate <op> constant` (`sum(x) > 2 * count(y)`, an `OR` of aggregates, a function of several) is a boolean expression of the arm's inner aggregates that PostgreSQL's evaluator runs per cell, with the aggregates as parameters. A `pseudoconstant` qual PostgreSQL leaves above the arms (`WHERE (SELECT ...) > 3`, `now() > ..`, a stable function of constants) is a gate: it is evaluated when the scan starts and turns the arm off or on. **Grouping sets** (`ROLLUP`, `CUBE`, `GROUPING SETS`, `GROUPING()`) in the aggregating query run in the same scan: a cell is added to the group of each set, keyed by the set number as for flat sets. **Cell keys**: an arm may group by more than its id and the outer keys (`GROUP BY o.id, category, kind` under `GROUP BY category`, or under no `GROUP BY`: `SELECT count(DISTINCT id), sum(n), count(*) FROM (..)`). A row then has several inner groups, cells, in one outer group, so the arm's other group expressions are keys of the cells, one key each shared by the arms with an equal expression, after the outer keys and before the set number (`Cell Keys` in EXPLAIN). A group never has them (the scan emits NULL), the outer aggregates take every cell (`count(*)` counts cells, `count(DISTINCT id)` the rows, `sum` and `avg` of an inner aggregate its cells' values) and the HAVING of an arm decides each cell by itself. Before this a global `count(DISTINCT id)` over the arms, and any outer key set smaller than the arms' group expressions, kept the plan: the cell was indexed by the outer group, which cannot hold two inner groups of one row.

## Ordered-set aggregates

`percentile_cont` and `percentile_disc` keep the values of each group exactly and pick the ranks with the final functions' arithmetic: `ceil(c * n)` for `disc`, `floor` and `ceil` of `c * (n - 1)` and `lo + frac * (hi - lo)` in double for `cont`, `DESC` counting from the end, NULL inputs left out, NaN last, `-0` equal to `0`. Aggregates on the same argument share one set of values. The values are an exact histogram of the distinct (group, value) pairs as long as it fits `work_mem` (4 slots of 16 bytes per pair at most); beyond that every value goes through a `tuplesort` in `work_mem` that spills to disk like the normal plan's sort (EXPLAIN ANALYZE: `Ordered Sets Spilled`), so memory is bounded and nothing fails or falls back. A constant fraction outside [0, 1] and a fraction that is a column of the group keep the normal plan (which raises its own error; a `Param` or stable expression is evaluated once); the array forms and the other argument types are generic aggregates (below). The overflow errors inside a float8 expression argument are not reproduced (as for `sum`).

## Generic aggregates

An aggregate without a native kernel runs on PostgreSQL's own functions (`SAA_GEN`): the scan decodes the argument leaves of the rows that pass the filters, builds the Datums of the argument expression (an expression of up to 4 leaves is evaluated by `ExecEvalExpr` per row, or per element below an unnest, like the lookup tables above) and calls the aggregate's transition function per row and its final function per group, the way `ExecAgg` does: initial value, strict transition functions with a first-value copy, expanded states, `FILTER`, the extra arguments and NULL direct arguments of the final function, the function's `fn_expr` (so `AggCheckCallContext`/`AggGetAggref` work), and the privileges (`EXECUTE` of the aggregate for the user, of the component functions for the aggregate's owner). Nothing is rewritten: the result is the one of the normal plan, row for row, including its errors (a float4 overflow, a bad cast), which are raised by the same function; the order of the groups' rows is the order the scan reads them, which is the heap order the sequential scan of the normal plan gives, so the order sensitive ones (`array_agg`, `string_agg`, `jsonb_agg` without `ORDER BY`) agree as long as the index is in heap order (the planner promises no more than PostgreSQL does for a plain scan: the SQL result of those is unordered).

| Family | Examples | How |
|---|---|---|
| Statistics | `stddev*`, `var*`, `corr`, `covar_*`, `regr_*`, over numeric, float8, int | `float8_accum`/`numeric_accum`/`int8_accum` and their finals; parallel through their combine functions |
| Booleans, bits | `bool_and`, `bool_or`, `every`, `bit_and`, `bit_or`, `bit_xor` | the transition functions |
| Sums without a kernel | `sum(float4)` | `float4pl` in heap order (the kernel adds in float8) |
| Min and max of text | `min(text)`, `max(varchar)`, any collation | `text_smaller`/`text_larger` over the decoded text |
| `DISTINCT` | `min`/`max`/`sum`/`avg`/`count(DISTINCT)` of other types, `string_agg(DISTINCT t, ',')`, `array_agg(DISTINCT x)`, `jsonb_agg(DISTINCT x)` | one varying argument without `ORDER BY`: the distinct values are kept per group in a hash set and fed in the type's btree order (NULL last, the first of equal values kept); when the sets pass `work_mem` the values move to the `tuplesort` above (`DEBUG1`: `DISTINCT of ... moved to a tuplesort`) |
| Collecting | `string_agg`, `array_agg`, `json_agg`, `jsonb_agg`, `json_object_agg` without `ORDER BY` | the transition function in scan order |
| `ORDER BY` in the call | `string_agg(x, ',' ORDER BY y DESC NULLS LAST)`, `array_agg(x ORDER BY y, z)`, `jsonb_agg(... ORDER BY ...)`, also with `DISTINCT` | one `tuplesort` of `(group, arguments)` in `work_mem` (spills to disk), then the transition function over each group's sorted rows; the sort operators, collations and NULL placement are the ones of the call |
| Several varying `DISTINCT` arguments | `regr_count(DISTINCT y, x)`, `array_agg(DISTINCT x ORDER BY x DESC)` | the same sort, with the rows equal on the `DISTINCT` keys (NULLs equal) dropped as they are read back |
| Hypothetical sets | `rank(c) WITHIN GROUP (ORDER BY x)`, `dense_rank`, `percent_rank`, `cume_dist` | the group's sort, then the aggregate's own transition function (it adds the hypothetical row) |
| Variadic, many arguments | `VARIADIC` aggregates, aggregates of more than 4 arguments | the argument slots are as many as the call has |
| Joined and mapped columns | `string_agg(c.derived_category ...)`, `max(upper(c.name))` over a lookup join | the value of the lookup table's row for the row, one joined argument per aggregate |
| Ordered sets | `percentile_cont`/`percentile_disc` with an array of fractions, over an interval, a date, text or any other type with a btree order, `mode()`, `DESC`, with `FILTER` | the values of a group go through one `tuplesort` of `(group, value)` (bounded by `work_mem`, spills like the normal plan's sort), then the group's transition function over the sorted values and the final function with the direct arguments |
| User aggregates | any `CREATE AGGREGATE` whose transition and final functions are not volatile | as above |

Stays on the normal plan, all checked at plan time:

- A volatile transition, final or combine function, or a volatile argument expression: calling it per row and per group is not a function of the data.
- A column that is not a scalar leaf of the index (`jsonb` members of a type the index does not hold, arrays, `bytea`, `char(n)`, and the types the index does not store yet), an argument expression of more than 4 leaves, more than one joined column in an aggregate, `DISTINCT` of a joined column over a hash set (it is taken through the sort), a lookup, and any sub-query or parameter that is not a constant or stable.
- `DISTINCT` or `ORDER BY` over a type without a btree ordering.
- A fraction or hypothetical value that is a column of the group (the normal plan evaluates it per group and raises its own error when it is outside [0, 1]); a constant, `Param` or stable-function fraction is taken.
- A parallel plan (no workers are planned, the leader scans alone) when the aggregate is ordered (`ORDER BY` in the call, ordered sets, hypothetical sets), `DISTINCT`, over a joined column, has no combine function (a user aggregate declared without `combinefunc`), has an internal state without serial and deserial functions, uses a function that is not `PARALLEL SAFE`, or when a native float `sum`/`avg` is in the same query (its lanes fix the additions' order; the generic states merge by worker). The plan is then the serial scan, not the normal plan.
- Hypothetical-set aggregates (`rank(c) WITHIN GROUP`) are priced by `AGG_GEN_HYP` so that the default plan stays the normal one: the scan sorts the group's rows and the transition function sorts them again, which measured 0.9 times the normal plan; the fixtures force the scan with page costs.

Generic aggregates in a parallel scan: each participant keeps the states of its rows per group; at the end the leader merges the workers' by key value with the aggregate's combine function (an `internal` state travels through its serial and deserial functions, any other state as a serialized datum of its type). The merged result is the aggregate's in the same sense as PostgreSQL's own parallel aggregates: exact where the function is (integers, numeric, text, booleans, bits, `array_agg` of a set with a following sort) and, for float accumulation (`stddev`, `corr`, `regr_*`, `sum(float4)`), different in the last digits since the additions are regrouped by worker (the comparator's tolerance, relative 1e-9). Collecting aggregates (`array_agg`, `jsonb_agg`) concatenate the workers' arrays in worker order, which is no order the normal plan promises either.

Cost: a generic aggregate is priced per row by `AGG_GEN_ROW` (12 operator costs for the call through `fmgr` and the Datum of a leaf) plus the transition function's own cost (`procost`: 1 for the built-in ones, 100 for a SQL function), the argument's expression cost and 2 per leaf, `AGG_GEN_DISTINCT` (10: the hash probe of the pair), `AGG_GEN_ORDERED` (24: the tuplesort put of an ordered set) and `AGG_GEN_SORTED` (30: the put and read back of `ORDER BY` or a multi-argument `DISTINCT`), and per group by `AGG_GEN_GROUP` (150: state, final function and the sort of an ordered group). They are the measured prices (a boolean or bit aggregate takes about 40 ns a row, a numeric accumulation 100 ns, a SQL function 1 us). The calls count the elements the data has, outside the factor that the unnest of the normal plan puts on the rest of the scan (see Cost): the whole table takes the scan, a selective store set keeps the btree plan (the S shapes at K10 and K400 of the analytics corpus did not change, and the fixture `g_cost_selective` asserts it).

The scan is the cost of decoding the leaves and building a Datum per value; what the aggregate itself costs (the numeric accumulation, a SQL function, the tuplesort of an ordered set) is PostgreSQL's and is the same in both plans, which is why the user aggregate and the sorting ones gain least.

## Shared CTE

PostgreSQL computes a CTE that the query names more than once once and hands the rows to every reference, so aggregates over it (S4: a time series at four granularities, each arm a `GROUP BY` of the same CTE) never reach the index. When a CTE with no recursion over a table that has a column index is read twice or more, `agg/cte.c` (a `planner_hook`) plans the query again with the CTE `NOT MATERIALIZED` (PostgreSQL itself refuses that for a CTE with a volatile function or data-modifying statement) and keeps that plan only if it has a `Custom Scan (SiftAgg)` and costs 2 times less than the materialized one, on top of the factor of about 6 that `agg_cost` charges every scan of an unnest (see Cost): the planner assumes 100 rows per `jsonb_to_recordset` call against the handful the data has. S4 keeps the materialized plan for the 400 store set and takes the inline one for the 4000 store set, where it is 5 times cheaper. Both plans are plans of the same query. The arms are planned apart, each with its own PlannerInfo, and the executor fuses those that qualify into one pass over the index (below, `fuse_register`); the others are each their own pass (four for S4).

## Numeric

A `numeric(p, s)` column with `p <= 18` is an INT leaf holding the number times 10^s, and the plan treats it as an int64 leaf with a scale: the same comparison kernels, group ids and accumulators as every integer leaf, PostgreSQL's own numeric functions for everything that is not integer arithmetic. An `int8` column is the same leaf with scale 0 (so it is also a group key now). Unconstrained, wider or negative-scale numeric is refused at `CREATE INDEX`, so those columns are never on the index.

**Predicates** (`numeric` column against a constant or a parameter): `= <> < <= > >=`, `BETWEEN`, `IS [NOT] NULL`, `IN`/`NOT IN` of constants (up to 64: an OR of equalities, an AND of inequalities, as PostgreSQL evaluates them; more: one test of a hash set of the scaled integers, NaN equal to NaN only; `NOT IN` with a NULL member is never true). The operand is evaluated when the scan starts and scaled with `numeric_mul`, `numeric_floor` and `numeric_ceil`; the operator is rewritten for the stored integers: `x = c` holds for `c * 10^s` when it is an integer and for no value otherwise (`x <> c` for every one), `x < c` is `x < ceil(c * 10^s)`, `x <= c` is `x <= floor(c * 10^s)`, `x > c` is `x > floor(c * 10^s)`, `x >= c` is `x >= ceil(c * 10^s)`. A constant beyond the integer range, NaN (greater than every number in PostgreSQL's numeric order) and the infinities give the same answer for every value of the column; none of them reaches the kernels.

**Expressions** (aggregate arguments, group keys, predicates, `count(DISTINCT)`): `+ - *`, unary minus, `abs`, `round`/`trunc` with a constant number of digits (also negative), `floor`, `ceil`, numeric constants, `int2`/`int4`/`int8` columns cast to numeric, and numeric cast to `int2`/`int4`/`int8`. They run as a program of int128 values scaled by the result's `dscale`, which is what PostgreSQL gives: the larger scale of the operands for `+` and `-`, their sum for `*`, the digits asked for by `round` and `trunc` (0 for a negative count), 0 for `floor` and `ceil`. Two expressions in a comparison are compared as their difference against 0. The planner tracks the digits each step can have from the columns' declared precision and refuses the expression when a step could need more than 38 (int128), a sum or average when its argument could need more than 26 (room for 10^12 rows), a cast to an integer when the digits it keeps could overflow it (PostgreSQL raises the error then). Equality is by value: a distinct count, a group key and a `min` over one expression compare scaled integers of one scale, so `1.0` and `1.00` are the same number. The text of a result is the one of PostgreSQL: a sum, key or extreme is written with the scale above, so trailing zeros are kept.

**Aggregates**: `sum`/`avg`/`min`/`max`/`count`/`count(DISTINCT)` of a column or an expression (`sum(DISTINCT)` and `avg(DISTINCT)` too). `sum` adds in 128 bits, so it is exact however many values there are, and is written as the numeric of the argument's scale (the `dscale` PostgreSQL gives the sum); `avg` is `numeric_div` of that sum and the count (as `numeric_avg` does); `min`/`max` are the value; a group without values is NULL. `sum`, `avg` and `percentile_cont` of `numeric(p <= 15, s)` cast to float8 divide the integer by 10^s in double: below 2^53 that is the correctly rounded value `numeric_float8` computes.

**Evaluated by PostgreSQL**: division, `%`, `sqrt`, `power`, the other functions, casts (`numeric(p, s)`, `numeric` against float8), NaN and infinite constants inside the arithmetic (a NaN in the column is not one of these: the programs above handle it) and `IN` with a parameter array or more than 64 constants have no kernel here (the result scale or the error is PostgreSQL's to decide); they run in PostgreSQL's own executor over the decoded leaves, in aggregate arguments, group keys and filters ("Expressions PostgreSQL evaluates" below). `min`/`max(DISTINCT)` and `percentile_*` over numerics are the generic aggregates' (the percentile functions pick from the sorted values; the scan keeps float8 ones only).

## Expressions PostgreSQL evaluates

An expression of up to eight scalar leaves (`int`, `date`, `timestamp`, `float` and `numeric(p <= 18, s)` columns, dictionary columns) that has no kernel is a combo: `ExecEvalExpr` runs the planner's own expression tree over the decoded values, once per distinct tuple of leaf values, and the rows look the result up by the id of the tuple. `numeric` leaves are rebuilt as the numeric the heap holds (scale, NaN included), so rounding, scales, operator semantics and errors are PostgreSQL's, not a copy of them. It serves as an aggregate argument (`sum`/`avg`/`min`/`max`/`count` of numeric and float8 expressions, `min`/`max`/`count` of the others; a numeric `sum`/`avg` adds with `numeric_add`, so it has no digit limit), as a group key and in a filter, next to the kernels in the same scan. What now runs this way: numeric `/`, `%`, `sqrt`, `power` and every other volatile-free function, the `numeric(p, s)` cast, `numeric` against float8, NaN and infinite constants inside the arithmetic, `IN` with a parameter array or more than 64 constants, expressions over 38 digits and `sum`/`avg` arguments over 26 digits, `CASE` and `COALESCE` over the leaves, and the same for `int`, `float` and `timestamp` leaves (`i4 % 7` as a key, `date_trunc('month', ts)`, `sqrt(abs(f8))`).

- Cost: each distinct tuple of leaf values pays `AGG_EVAL_SLOT` (60 operators) per expression, each row pays 3 per 64-bit leaf (the probe of its id), and a numeric `sum`/`avg` or an extreme 2 or 1 (the transition is the same work in both plans). The tuples are `estimate_num_groups` of the leaves' index expressions over the rows that reach the expression, so an expression over a column of many values pays the evaluation for every row. PostgreSQL prices the normal plan's evaluation at `procost` per function (1 operator) and a numeric transition at one operator as well, though a numeric function allocates and does digit arithmetic (40 operators and more) and a call through the interpreter costs about 5: the scan is credited half of that difference for every row that reaches an expression, a numeric transition or a numeric operation of a kernel program (`plain_credit`, floor 10 percent of the scan's price). That is what makes the 5 to 15 times faster shapes below pick the scan at the default costs, while `sum(rate / 3)` over 300000 distinct values (priced 27000 against 7000, the scan evaluates every row as the normal plan does and adds its machinery) and a selective query (the credit is per row that passes, the scan reads every unit) keep the normal plan. A scan with workers pays `AGG_SETUP_FACTOR` (110) times `parallel_setup_cost` once, whatever the worker count (starting the workers and opening the source takes about 8 ms), so a scan of a few milliseconds stays serial. Combos of dictionary and 32-bit leaves keep the price they had.
- Calendar keys (3.1): a group key on a `timestamp` column that is built of `date_trunc` (second to millennium), `::date` and `extract` (minute to millennium, `dow`, `doy`, `week`, `isoyear`; not `second`, `epoch` or `julian`) changes value only on a second, minute, hour or day boundary of the data, so it is not a combo. The scan numbers the rows' steps (`floor(ts / step)`, an unsigned multiply per row), covers the numbers of the unit in a range table as an integer key does, and evaluates the expression with PostgreSQL once per step of the range (about 1,100 days for three years of `date_trunc('month', ts)::date`, not once per timestamp). EXPLAIN shows it as `(per day)`, `(per hour)`, `(per minute)` or `(per second)` after the key. An infinity, or a range of more than 2^22 steps in a scan, falls back to a hash table of step numbers with the same ids, so the groups are the normal plan's. The estimate of the groups comes from the column statistics (36 months, not one per row), which is what lets the planner choose this path for the month-over-month questions on a `sift_table`, which has no stored month leaf. `timestamptz` keys depend on the session time zone and stay combos.
- Cache: the tuples are kept up to `sift.agg_combo_cache` entries (default 1048576) and dropped when it passes that, so memory stays bounded and a value that comes back is evaluated again; a combo with a lookup join or a dictionary leaf is never dropped (its ids are held outside the cache).
- Errors: an expression that can raise (a divisor that is not a nonzero constant, `sqrt`, `power`, `ln`, a cast of text, any function that is not leakproof) is evaluated only for the rows that passed the other conjuncts of its `WHERE` or `FILTER` (it is a late conjunct, applied last), and as a key or argument only for the rows that are aggregated, so `WHERE d <> 0 AND x / d > 1`, `FILTER (WHERE d <> 0)` and `CASE WHEN d = 0 THEN 0 ELSE x / d END` raise nothing, as in the normal plan. A row on which the normal plan fails fails here with the same error. PostgreSQL orders the conjuncts of a `WHERE` by cost, so a divisor of zero in a row that only a costly conjunct excludes can fail one plan and not the other; this is the one reordering. A lookup-table predicate or key (a boolean expression of ONE dictionary/integer column, evaluated by PostgreSQL once per value of the dictionary or of the range of the unit, also for values no selected row has) never takes an expression that can raise: it goes to a combo.
- NaN stored in a numeric column: the index keeps NULL and the overflow flag; the source presents the row as a value, `PG_INT64_MAX` and not NULL, with its bit in `SiftSrcVec.ovf`. Numeric orders NaN above every number and equal to itself, which is what that integer is to the kernels, so `min`/`max`, `count`, `count(DISTINCT)`, group keys, `ORDER BY ... LIMIT` and `IS [NOT] NULL` need nothing more; the code that adds or compares reads the bit. The programs (`+ - * abs round trunc floor ceil`, the aggregates and keys over them) carry a NaN flag per value, which any operand's NaN sets, and give `SIFT_NX_NAN` (greater than every value of a program, equal to itself) for a flagged one, as `numeric_add` and its kin give NaN. `sum` and `avg` keep a flag per group and give NaN. `SNX_CMP3`, the comparison of two expressions (`n > m`; not their difference, which cannot tell which side is the NaN), gives -1, 0 or 1 with NaN equal to NaN and greater than the rest. A comparison with a constant takes the answer for a NaN row from the operator and the constant (`NaN op c`: `<>`, `>` and `>=` for a number; `=`, `<=` and `>=` for NaN; `NaN < c` never), also when the constant is NaN or an infinity, whose answer for the numbers is the same for all of them. A constant comparison that holds for every number is a source filter only when it holds for NaN too. The cast to an integer raises `cannot convert NaN to integer` (`SNX_INTCAST`) for a NaN of a row the aggregate takes, or the conjunct reaches (a conjunct with the cast is a late one: it does not see rows another condition, or the snapshot, leaves out). `n::float8` is NaN, and a generic aggregate gets the NaN datum. The combos read the flag and rebuild the NaN as before (`sum(n / 3)`, `n % 3` as a key, `n > 1.5::float8`). `sift_table` tables still raise `0A000` for it (the provider does not pass the flag; see the requests).

### What keeps the normal plan

Listed once, with the reason:

- An expression of more than eight leaves, or reading a column that is not in the index: the expression cache supports at most eight inputs.
- Volatile functions, sub-plans, aggregates and window functions inside the expression: not constant per tuple of leaf values.
- A `numeric` column that the index cannot hold (precision over 18, unconstrained, negative scale) is not on the index, so no query reads it from the index (request below). The digit limits above do not apply to it.
- A filter on an expression (`lower(col) IN (...)`) is pushed, but PostgreSQL estimates 1% of the rows for an expression, so the normal plan can look cheaper than the scan: `CREATE STATISTICS s (mcv) ON lower(col) FROM t; ANALYZE t` gives the planner the real share.

## Executor

One unit at a time (the rows of a segment inside one superblock), through the seam of `src/agg/colsrc.h`:

1. row predicates to a bitmap with the kernel tables (integer comparisons are `range` and dictionary lookups `lut` of the column table, `cmp_f64` / `lut_i32` of the aggregation table; bitmap operations are the column table's `bits_*`); dictionary predicates are evaluated once per distinct value of the unit's dictionary;
2. with an unnest, element predicates in vectors of 4096 elements, the row bitmap lifted to the elements through their parent ordinals;
3. `sift_colsrc_live` and `sift_colsrc_vet`: dead rows out, then, after the value filters, the rows that the snapshot does not see (all-visible pages pass, the others are read in the heap; a `sift_table` table has nothing to check);
4. group ids: dictionary codes and integer values map to dense key ids through tables built once per dictionary / value range; ids combine into a direct array (up to 2^20 groups) or a hash table beyond;
5. aggregates accumulate by group in tuple order.

The groups leave as the rows of `custom_scan_tlist` (keys, then aggregates); the plan above projects and filters. `Rows Vetted By Heap`, `Heap Pages`, `Units`, `Units Pruned`, `Rows Scanned`, `Tuples Aggregated`, `Dense Chunks` (the chunks aggregated from their bitmap, below) and `Groups` are in EXPLAIN ANALYZE, the filters, group keys and pushed aggregates in plain EXPLAIN.

**Dense chunks.** A chunk of up to 4096 rows or array elements whose aggregates are `count`, `sum` and `avg` of one integer or float leaf (or `count(*)`), with or without a `FILTER`, grouped by dictionary (text) leaves or not at all, is aggregated from the bitmap of its rows: an aggregate takes the bits that pass its `FILTER` and have a value, a count is a popcount (a per group count with keys), a sum runs over the bits in row order (so a float sum has the same bits as before), and the group of every row comes from its dictionary code. There is no list of tuples and no gather by position, which was most of the instructions of `count(*) FILTER (WHERE ..)` over array elements. Anything else in the query (a join, an expression key, `min`, `max`, `count(DISTINCT)`, a late `FILTER`) and a unit that reads few rows (`SPARSE_RATIO`) run the tuple path; `sift.agg_dense = off` turns the dense path off for a comparison.

### One pass for the arms

The inlined arms of S4 scan the same rows for the same aggregates and differ in their keys. The nodes of one executor state register when they begin (`fuse_register`); the first to run takes every registered node whose spec equals its own once the keys are left out and the leaves, the columns of a joined table and the combo slots only some read are united (`agg/spec_fuse.c`, `sift_aggspec_fusable`: no sets or arms; the same aggregates, or when the arms join a lookup the union of theirs, each set updating its own (`SiftAggSpec.setaggs`; not with a percentile or `GROUPING`, which are numbered by the arm's list); the conjuncts of the `WHERE` every arm has are the pass's, and those an arm has beyond them are tested on its own set (`SiftAggSpec.setpred`), the pass keeping the rows of any arm (an `OR` of them, which also prunes units) and the arms the pre-aggregates answer one by one, and arms that join no lookup (a filter of the chunk per set costs more than the shared decode saves), staying apart; `sift.agg_fuse` turns the pass off; the same lookup joins of tables or correlated sub-selects, which repeat or drop the tuples of every set: an inner join and a left join of the same table are one left join, and the arm with the inner join drops the tuples without a row (and those that fail the rest of its `ON` clause) in conjuncts over the joined rows of its own set (`SiftAggSpec.postsets`); the distinct keys of the arms fit the 32 of a grouping set) and scans once with the distinct keys of the arms and the arm as the set key, the machinery of the grouping sets above (`sift_aggspec_fuse`). A common table expression or VALUES list joined as a plan is the same when it is the same CTE (its plan in the statement) or the same list and the conditions on it are the same (`SiftAggJoin.sig`); its plan outputs all its columns, so the arms number them alike, and the pass runs the plan of the node that starts it. A correlated sub-select is the same in two arms when its query as written, its conditions and the expressions of the scan it is called with are (`SiftAggJoin.sig`); PostgreSQL plans only the columns an arm reads, so the pass runs the sub-select of an arm that reads all the columns of the pass. Each node then returns the groups of its set. The tuples of a set are those of the node alone, in the same order, so the rows and the float sums are the ones of separate passes; `EXPLAIN ANALYZE` shows `Arms In One Pass` and the counters of the shared scan on each node.

### count(DISTINCT) of a 32 bit value

A dictionary code, a dense id of a numeric expression or an integer column up to 32 bits is counted per group in one of three forms (`struct Dist`); NULLs never enter, and the count is exact.

- **Bitmaps**: the values are dense (the range seen is covered by few enough 4096 bit chunks): each group has a directory over the shared range, its chunks are allocated when a value falls in one, and the count is a popcount. A set that fits the cache sets its bits one by one; a bigger one (2 MB and more) finds and prefetches the words of 32 values before it sets them, as each is a miss of its own.
- **Bounded set**: sparse values go to an open addressing set of (group, value) pairs, inserted in batches with the slots prefetched.
- **Sort**: past `get_hash_memory_limit()` (`work_mem` times `hash_mem_multiplier`, per aggregate) the pairs move to a tuplesort that spills to temp files, and the count of a group is read from the sorted runs. A bitmap or a set that outgrows the budget converts, so the memory never grows with the distinct values; EXPLAIN ANALYZE shows `Distinct Sets Spilled`.

Workers send a set that is still a bitmap of raw 32 bit values as its chunks of 32 bits or more (group, chunk number, the 512 bytes) and the bits of the sparser chunks as pairs; the leader ORs a chunk into its own and counts the new bits by popcount (`Distinct Chunks Merged` in EXPLAIN ANALYZE). The blob of a worker is at most the memory of its bitmap, which `hash_mem` bounds. A narrow set (`dist_narrow_words`) goes as the words of its window, a row for each group that has a bit, which the leader ORs into its own and counts by popcount; a dictionary's narrow set sends the values of the ids that have a bit, and the leader ORs the words as they are when its ids are the same. The values of a dictionary or of a numeric expression are ids local to a worker, so they go as pairs by value (the numbers themselves for a numeric expression, which the leader gives its own ids); `sum(DISTINCT)` and `avg(DISTINCT)` of numeric values are the same pairs from the set that adds each number once per group, and the leader adds the numbers it has not added yet (`agg_distinct_parallel`). `EXPLAIN (VERBOSE)` says `Serial Because` for a scan that cannot have workers whatever the cost (the aggregate whose state the leader cannot merge). Merging pairs one by one was 40% of the leader's cycles in Q06 at 3 workers.

A bitmap local to a unit (sized to the unit's range of values, merged per group at the end) was not built: a unit of 74 496 rows holds values from all over the domain whenever the heap order does not follow the value (Q06's customers and months are independent of the order of the rows), so its range is the whole domain and it shrinks nothing; when the order does follow the value, the shared bitmap is already local, as the active chunks are the same few. What the profile showed was a miss on the word of each bit, which the prefetch hides (15% to 40% fewer cycles of a backend at 10M, below).

## Parallel scan

The planner offers a second path with the workers PostgreSQL would give a parallel sequential scan of the table (`compute_parallel_worker`: table size, the `parallel_workers` reloption, `max_parallel_workers_per_gather`), only when the whole query is parallel safe (`glob->parallelModeOK`, no unsafe function in the spec) and the spec is one of the parallel kinds below; the cheaper of the two paths wins. The cost divides the scan by PostgreSQL's divisor (the workers plus the share of a leader that scans too, `parallel_leader_participation`), adds `parallel_setup_cost`, and charges every partial table for its groups (merge cost per group). `sift.enable_agg = off` removes both paths.

The node is not under a Gather: its workers return tables, not tuples, so it keeps a parallel context of its own (`sift_agg_worker_main`, one `shm_mq` per worker). The leader opens the source, creates the context, fills the shared state and launches, and waits for the workers with the source still open: the sources keep their page pinned, never locked, between calls, so no interrupt is held off (a held-off interrupt makes `InitializeParallelDSM` plan no workers and the wait never end). A worker opens the relations and the source with the leader's snapshot and parameters and registers the same predicates and keys from the spec. The work is a counter in shared memory that the leader and the workers take items from:

- Exact aggregates (counts, integer sums, min/max, count(DISTINCT)): an item is 2 superblocks. A participant aggregates all its items into one table and sends it when the counter runs out; the leader merges the tables by key value (dictionary codes and key ids are per process), unions the count(DISTINCT) sets and adds the rest. Integer arithmetic is exact, so the order does not matter.
- Float sums (`sum`, `avg` of float8): additions are not associative. The scan has 16 lanes (`SIFT_AGG_LANES`): lane l is the superblocks l, l + 16, l + 32, ..., summed in superblock order into a table of its own, and the leader adds the lane tables in lane order, as soon as the lanes before them arrived. Whether the leader or a worker scans a lane, the additions are the same, so the result is bit-identical for 0, 1, 2, ... workers and every SIMD level. `avg` counts and the "no float seen" flag merge with it; the overflow guard of `avg(float8)` takes the largest input of all lanes.
- Without workers the leader runs the same items, so a serial run is the same computation; a query whose workers cannot be launched (none free, nested in a worker, no DSM) runs on the leader alone.

All the memory that grows with the groups (key ids and values, the group arrays, count(DISTINCT) sets) is in one table context that is reset between lanes; the buffers of a unit and the registered expressions live as long as the scan.

Which specs run in parallel is `sift_aggspec_parallel_ok`, shared by the planner and the executor:

|  | Parallel (a table is dumped, merged by value, reset) | Serial only (the leader scans alone: no workers planned, no lanes) |
|---|---|---|
| Keys | a column (dictionary, integer, date, bool), an expression of one column (`SAK_LEAF`, `SAK_LUT`), float keys (bits), numeric keys (`SAK_NUM`: the value, 128 bits), keys of a combo (`SAK_COMBO`), the grouping set number (`SAK_SET`) |  |
| Aggregates | `count(*)`, `count(x)`, `count(DISTINCT row id)` of an unnest, the outer aggregates of two-level arms (`SAA_O_*`: counts, `sum` / `avg` of the cells, `count(DISTINCT)` of a key the arms group by), `sum` / `avg` of integers, float8 and numeric (leaf or expression), `min` / `max` of a leaf or a numeric expression, `count(DISTINCT)` of a dictionary or integer leaf, ordered-set aggregates (`percentile_*`: the histogram of values with their counts, or the sorted pairs of a spilled one), generic aggregates with a combine function (`stddev`, `var`, `corr`, `bool_*`, `bit_*`, `array_agg`, `string_agg`, user aggregates with `combinefunc`; not with a native float `sum`/`avg` in the query), any `FILTER` | `count(DISTINCT)` and `sum` / `avg` with `DISTINCT` of a numeric expression (a set of 128 bit values per group), mapped aggregates (`SAA_M_*`: values of a lookup table), generic aggregates that are ordered, `DISTINCT`, over a joined column, hypothetical or whose functions are not parallel safe or have no combine function |
| Shape | row filters of every kind, element filters, unnest, `sum(x * y)` programs, lookup joins and combos, grouping sets, virtual leaves (`jsonb` member by key), two-level arms (per-order aggregates) | a child plan run per combination of leaves (a correlated sub-select the scan cannot read as the table of a unique key), a hashed sub-plan in a lookup expression (`NOT IN (SELECT ..)`) |

A worker loads the lookup tables of the joins itself, with the leader's snapshot (a few rows each), and evaluates the slots of its combos; the output rows of a combo hold ids of the key tables, so a lane forgets them with the table. The partial table of a numeric sum carries the 128 bit state, the grouping sets are groups of the set number (an integer key), an ordered set sends its histogram as (group, value, count) runs and the leader adds the counts into one histogram (or a tuple sort once it does not fit `work_mem`), and `percentile_*` then walks the sorted values once as in a serial scan.

Generic aggregates (`SAA_GEN`, PostgreSQL's own transition and final functions) with a combine function are dumped as the aggregate's partial states and merged by key value with it; their workers are morsel based like the exact kinds. The others run on the leader alone, and a query with any generic aggregate is never fused with other arms.

The kinds that stay serial keep their state in structures that are not dumped and have no merge defined: their scan is one item over all the superblocks into one table, with float sums in tuple order. A mapped aggregate keeps the values of a lookup table that its sets refer to by id, per process, and adds the sums of float8 and numeric values in the order of its hash table; two workers cannot reproduce that order, nor the scale of a numeric when equal values differ in it, and the scan it would split takes about 30 ns a tuple (6 ms for 200,000 rows, the price of starting the workers). A hashed sub-plan (`x NOT IN (SELECT ..)`) and a child plan run per combination of leaves live in the leader's executor: a worker has no plan state to start them in. The per-order arms hold a cell per (arm, group) while a row is read and flush it into the outer accumulators at the end of the row; a row is in one item of work, so the arms run in workers like any other table: an item flushes its last row's cells before its table is dumped (`arms_flush`), the outer counts and sums add, the `count(DISTINCT)` of a key the arms group by travels as (group, value of the key) pairs that the leader gives its own key ids, and the float sums of the cells use the lanes. The guard of an inner `avg(float8)` travels with the tables (the largest input of each arm). A lateral `LIMIT 1` child of a unique key is read as a table (`First Row Lookup Tables`) and shared like one; PostgreSQL marks a lateral sub-select at the aggregate's own query level parallel restricted, so that case has workers only inside arms (a query level of their own). The test `aggstub_scan` checks that every parallel kind gets workers and gives the rows of the one-process scan and of the normal plan.

A scan with float sums and no workers launched adds the lanes in turn into one table: a lane's float sums are collected in the accumulator and added to the sums of the lanes before it when the lane is done, which are the additions the leader makes when it merges the tables of the lanes (`lane_fold`), so the bits are those of a scan with workers, without dumping and merging a table per lane.

`Workers Planned` and `Workers Launched` are in EXPLAIN; `Units`, `Rows Scanned`, `Tuples Aggregated`, `Units Pruned` and the heap counters add the workers'.

## Filters in the source

The row conjuncts that compare one scalar leaf of the rows with a constant are offered to the source before the scan (`filter_init`, `sift_colsrc_set_filters`, `SiftSrcFilter`), and the `sift_col` provider applies the ones it takes on the stored chunks: the engine tests the encoded values (`sift_col_filter`: the bit-packed and FOR chunks are compared as packed integers by the range kernels, the dictionary chunks through a bitmap of the matching codes) and nothing is decoded for the predicate. The forms:

- `=`, `<>`, `<`, `<=`, `>`, `>=` of an `int2`, `int4`, `int8`, `date`, `timestamp`, `timestamptz` or `bool` leaf with a constant or parameter, and of a `numeric(p <= 18, s)` leaf as its scaled integer (`amount > 100` is `value > 10000` at scale 2; a constant between two values of the scale rounds the comparison the way `numeric_operand` does, one that every or no value satisfies becomes "not null" or no row);
- `IN` of up to 8 integers (a longer list stays a table lookup in the executor: the engine would decode it).

Text leaves take their own path (`prune_str`, `filter_str`, "Text of any length"). A filter is exact: a NULL value never passes, the executor does not test the rows again, and a unit whose leaf has overflowed values is filtered on the NULL the index keeps for them, after the check above has seen that no row of the snapshot holds one (the one overflow value of a numeric leaf, NaN, is stored as NULL with the flag and passes `>`, `>=`, `<>` and not-null only, as in the executor). Float leaves, `OR`, `NOT IN`, element conjuncts, late (per-order) conjuncts and expressions stay in the executor. The provider passes every accepted filter to `sift_col_begin` too, so the units whose zone (min, max) refuses any of them are skipped before they are read.

For each unit `col_filter` orders the filters by the share of the unit's rows each keeps (an estimate from the zone of its leaf: the values spread evenly between min and max, a text leaf by its codes), the most selective first, and stops at the first that leaves no row: the unit costs the chunks read so far, no other leaf is decoded, the heap is not vetted. Each pass over a chunk costs about the same whatever is left in the selection, so the order matters for that early stop only.

What is left is read for its rows only: when the rows that still count are fewer than an eighth of the unit, the executor reads a scalar leaf of rows with `sift_colsrc_read_sel` (`sift_col_read` with a selection: the packed values at those positions are gathered, not the whole chunk decoded) into the zeroed vector of the unit; the aggregate inputs, the keys and the conjuncts that stayed in the executor take it as they would the whole leaf, since only the rows of the mask are looked at. `EXPLAIN ANALYZE` shows `Filters In Source` (the number of conjuncts the source took). The test provider and `sift_table` take none (their `set_filters` is empty) and keep the executor's comparison kernels (`cmp_int`: the `range` kernels at int32 and int64 width, scalar, AVX2 and AVX-512 chosen at run time like every kernel).

## The JSON type of a path (`jsonb_typeof`)

`jsonb_typeof(x->'k') = 'number'`, also `'string'`, `'boolean'`, `'object'`, `'array'`, `'null'`, `jsonb_typeof(..) IN ('string', 'number')`, their
complements `<>` and `NOT IN` and `jsonb_typeof(..) IS [NOT] NULL` are a conjunct of the query that the source answers (`SAP_TYPE`,
`typeof_test`, `compile_typeof`, `sift_colsrc_filter_types`; tests `agg_jsonb_typeof`, `agg_jsonb_typeof_parallel`, the `k_typeof_*` fixtures). The argument is
a path of the jsonb value (`->`, `#>`, nested), not its text, and it names a scalar leaf of the index (`bool`, `int2`, `int4`, `int8`, `float4`,
`float8`, `numeric`, `text`, `astext`; not lossy, not a key of a map or a list element).

- **An `astext` leaf** holds the text of a string, a number or a boolean, so its stored values have no type of their own: the chunk keeps the
  kind of each number and boolean, a string is the leaf's own, an object or an array is an overflow value with its tag, and a
  JSON null is a NULL slot of its own kind. A `'12'` that is a string stays a string. A segment of minor 3 has no kinds, so a test that tells
  the types of an astext leaf apart raises there with the `REINDEX` hint, as a NULL slot does for `'null'`.
- **What it keeps.** The rows whose type of the leaf's path is in the set, a set of seven types: `string`, `number`, `boolean`, `object`,
  `array`, `null` (a JSON null) and none (a missing key, a NULL document, a path that leads to no value: `jsonb_typeof` is NULL). A stored value
  has the type of its leaf (a `float8` leaf holds numbers), a value the leaf could not hold the type its chunk kept,
  a NULL slot the kind of the chunk (`null` or none). `= 'a'` and `IN` are the listed types; `<>` and `NOT IN` the others **but none**, as
  PostgreSQL gives NULL for a path with no value, which no comparison keeps; `IS NULL` is none, `IS NOT NULL` every type but none. A name that
  is no JSON type is no type (`= 'bogus'` is not pushed, `<> 'bogus'` is every type but none).
- **What it does not raise on.** The rows of any other type are dropped without reading their value: a string among the numbers of a `float8`
  leaf does not raise the overflow error that every other read of that leaf raises, because the reads of a leaf with a type filter give such
  a value as NULL (`tolerate_ovf`) and the filter has already dropped or refused every row that has one.
- **What it raises on.** When the query reads the values of the leaf besides (an aggregate, a key, another conjunct of it: `SIFT_SRC_JT_READ`),
  a kept row whose value the leaf cannot hold (a number out of the float range, a non-integer in an `int4` leaf, and any string, boolean, object
  or array asked for on a leaf of another type) raises the error of the pushdown, as the read of that value does, unless no snapshot sees the row
  (the unit's page is not all-visible: `sift_col_vet` runs on those rows only). When it does not (`count(*) WHERE jsonb_typeof(m) <> 'number'`,
  a `count(*)` of the strings of a number leaf), the rows are counted by their types and no value is read: nothing raises. A row whose type the
  chunk does not know (an overflow value with no tag, a NULL slot or an astext value of a unit that has no kinds, written by minor 3 or merged
  from one) raises with the hint to `REINDEX`, whatever the query reads. The filter runs first, on the live rows of the unit, before the other
  integer filters of the source: an error is possible for a row that another conjunct would drop, never the contrary. A sum or any other read of
  the same leaf that no type filter guards keeps raising for the strings, as today.
- **As an expression.** Anywhere else `jsonb_typeof(x->'k')` is a text leaf after the source's (`SiftAggVLeaf.types`, `types_leaf`, the
  leaf `#typeof`, `read_types_leaf`): per row the name of the type (a dictionary of six, a NULL where the path has no value) that the source
  reads from the chunk (`SiftSrcProvider.read_types`, `sift_col_row_types`), no value of the leaf read. So it is a group key (the five types,
  `null` and a NULL group; at most seven groups), a branch of an `OR` or a `NOT`, in an aggregate `FILTER`, a `CASE`, a function of the type
  (`upper`, `coalesce`, `LIKE`, a comparison), with the existing machinery of the leaves of text (lookup tables over the dictionary). The PostgreSQL
  semantics are the leaf's: a path with no value is NULL, a JSON null is `'null'`. These shapes are not the fast path of the conjunct: the
  vector of types is decoded and the expression evaluated per distinct name.
- **Not taken.** A name that no row has as a conjunct (`= 'bogus'`: it goes through the expression above), a query that tests the type of a path in
  an expression (`FILTER`, `CASE`, `OR`, a key) **and reads the values of the same path** (`sum(x) FILTER (WHERE jsonb_typeof(x) = 'number')`): the
  leaf cannot give the strings among its numbers and only a conjunct (the form above) guards the read, so the scan would raise where PostgreSQL's
  guard skips them; the plan is the normal one, which `k_typeof_not_pushed` checks. Also a path of an element of a list or map, and a
  `sift_table`: it keeps a jsonb column as one opaque leaf, so there is no leaf of the path to give the types (the table needs declared paths,
  `docs/COL-TAM.md` section 11; the provider then only forwards `filter_types`, `read_types` and `tolerate_ovf`), and the stub source.
- **Where it runs.** `process_unit` calls the source before the integer filters (`type_filters`), the rows left are read as for those filters
  (a sparse selection decodes the leaf at those rows only), a worker does the same on its units, and a match set from a BM25 conjunct is
  expanded to the stored rows like the other filters. A unit's pre-aggregates do not answer a query with it. `EXPLAIN` shows the conjunct in
  `Filters` and, with `ANALYZE`, `Type Filters In Source`.

## Zone pruning

The row conjuncts of the query that compare an integer leaf of the rows (`int2`, `int4`, `int8`, `date`, `timestamp`, `timestamptz`, `bool`, and a `numeric(p <= 18, s)` leaf as its scaled integer; not a jsonb element, not a lossy leaf) with a constant or parameter by `=`, `<`, `<=`, `>`, `>=`, or by `IN` of a list that fits a table, become, per leaf, an interval `[lo, hi]` (`sift_aggspec_zone_cmps`, `prune_init`: the operand is evaluated once per scan, comparisons of one leaf are intersected; `<>`, `NOT IN`, element conjuncts and float leaves are not used; an `OR` is tested disjunct by disjunct, below). A source that takes the conjunct as a filter (above) also gets it whole in `sift_col_begin`: an integer `IN` is tested against its members, so a unit that lacks the value is skipped too. The executor passes the intervals to `sift_colsrc_begin` as `SiftSrcPrune`; the `sift_col` provider turns each into two comparisons (`>= lo`, `<= hi`) for `sift_col_begin`, which skips the units whose min/max zone map excludes either, before any leaf is decoded, and counts them (`Units Pruned`). The test provider skips by the minimum and maximum of the unit's values. The executor still applies every conjunct to the rows of the units it reads, so pruning only removes work: a unit is skipped only when no row of it can pass. It applies to every spec, parallel or not.

An `OR` of such tests (two ranges, a list of equalities, `BETWEEN`s, an AND of ORs, an OR of ANDs of several leaves) is a `SiftSrcPrune` that holds its disjuncts: the provider (`sift_col_begin_zones`) prunes a copy of the kept units with each disjunct and keeps the union, so a unit is read when any disjunct may match. A disjunct no zone can refuse (a text test, an expression of the leaf, `<>`) leaves the `OR` without a test. `agg_cost` prices the units an `OR` leaves as the sum of its disjuncts' shares (at most 1). The `OR` is not used by the rollup path: it answers a unit whole only from the plain comparisons (`SiftSrcPrune` entries without kids).

`agg_cost` prices the scan of the units that are left. The share kept for one comparison is `f + (1 - f) * (1 - corr^2)`, f being the selectivity PostgreSQL estimates for it (`clause_selectivity`: the column's MCVs and histogram, taken when the conjunct is compiled) and corr the correlation of the heap column with the heap order from `pg_statistic` (0 when unknown, and for jsonb paths and index expressions); the most selective comparison counts, and at least one unit is read. A column that grows with the heap (ids, insertion time) has |corr| near 1 and a range query is priced by its range, an unclustered column is priced by the whole table. The leaf read, predicate and unit terms scale with the share; tuples and aggregate updates already follow the selectivity. The numeric comparisons and the `IN` lists count in that share like the integer ones (their selectivity is taken when the conjunct is compiled). The share of the units is counted, for the comparisons and short `IN` lists with a constant at plan time, on a sample of the real zones of the index (at most 2048 units, the same units in every integer leaf, `SiftColZones`): a unit stays when the zone of every conjunct meets its values, so two windows that no unit meets leave about none; a conjunct with no constant (a parameter) or a source without zones keeps the estimate above. A unit that keeps one row in eight or fewer is read at those rows only (docs/COL-SEARCH.md), so the leaves no filter tests are priced for the share of rows that pass (`AGG_SPARSE_LEAF`).

### Statistics request

The correlation is a stand-in for what the planner needs, and `SiftSrcStats` of the `sift_col` provider carries only the row and unit counts and the visibility share today (`ndistinct`, `min`, `max` and `elems_per_row` are zero). For each integer leaf of the rows, from the engine (computed at build or ANALYZE from the zone maps it already keeps, nothing read per query):

- `zone_width[leaf]`: the mean over units of `(zone.max - zone.min) / (leaf max - leaf min)`: how wide a unit's zone is relative to the range (0 for a perfectly clustered column, 1 for a random one). With it the share of units a window of fraction f of the range overlaps is `min(1, f + zone_width)`, which replaces `f + (1 - f) * (1 - corr^2)`.
- `zone_hist[leaf]`: 32 equal-width buckets of the range, each with the number of units whose zone overlaps it, to price skewed ranges and `=` on a clustered column exactly.
- `ndistinct`, `min`, `max` of every scalar leaf and `elems_per_row` of every group leaf, for the key-table sizes and the unnest cost.
- `inline_frac[leaf]`: the share of the rows of a text leaf whose unit stores the strings inline (the writer knows it per unit; `sift.col_leaves` counts `inline_chunks`), which `inline_text_cost` uses instead of the average width of the heap column.

## Text of any length

A unit stores the strings of a text leaf inline when one is over 255 bytes; the scan hands such a unit to the executor as a dictionary of its own, with a fresh id, so group keys, `count(DISTINCT)`, `min`/`max` and lookup-table filters work on text of any length (fixtures `t_text_long*`, `t_text_inline_*` with strings of 250 to 600 bytes: filters, groups, `min`/`max` in the C collation, `count(DISTINCT)`). There is no error path for long strings. The caches keyed by dictionary id (`DictSlot`: lookup tables, key maps) are a ring of `NDICT_SLOTS` entries whose memory is freed when an entry is reused, so a new id per unit costs a rebuild per unit and no growth.

A row conjunct that is a text test on a plain `text`/`varchar` column goes to the provider (`prune_str`, `filter_str` of `agg/colsrc.h`) instead of being evaluated on the unit's dictionary: `col = const`, `col <> const`, `col = ANY (consts)`, `col <> ALL (consts)` for every deterministic collation, `col < <= > >= const` in the C collation and `col LIKE 'prefix%'` (no other wildcard). `sift_aggspec_str_test` recognizes the shape in the lookup-table predicate, `str_init` hands the tests to `prune_str` once per source (each worker), and `process_unit` narrows the unit's rows with `filter_str` before anything is read; when the provider answers true the leaf is not read for that conjunct. The `sift_col` provider runs it as `sift_col_filter` on the encoded chunk: the zone of an inline unit prunes by the prefix keys, and a selective equality decodes the prefix blob and the lengths only. A `NOT IN` list with a NULL, a Param list and any other expression keep the lookup-table form. The `sift_table` provider has no callbacks yet (`prune_str`/`filter_str` NULL: the executor tests the values itself, correct and slower for inline units).

300 000 rows of 310 bytes, W=0, median of 7 (plain / SiftAgg): `count(*) WHERE s = const` 28.8 / 6.1 ms (4.7x, before `filter_str` 80 ms for the lookup table over the unit's interned strings); `GROUP BY s` over all rows 339 / 150 ms. Reading a leaf of long strings builds the unit's dictionary (about 0.5 us a row), which the heap scan beats when few rows pass or when the aggregate is cheap: `count(DISTINCT s) WHERE grp = 3` 13.5 ms plain against 183 ms, `GROUP BY d` with `max(s)` over a range 61 against 80 ms. `agg_cost` therefore charges a leaf of a text column of average width 200 bytes or more (`pg_statistic`; jsonb paths and expressions are not priced) 56 units a row when anything but a pushed text test reads it, and 3 units when only a pushed test does (`inline_text_cost`): the first two queries above keep the normal plan, the equality and the group-by-text take SiftAgg. The mix of dictionary and inline units of a column is not known to the planner; the request below replaces the width with the share of inline units.

## Exactness

Integer, date, timestamp, dictionary, boolean and numeric results are exact. `sum(int)` is int8, `avg(int)` is the `numeric` division of the exact sum and count. Float `sum` and `avg` add in the order of the lanes above per group (a scan that is serial only adds in tuple order), so the result does not depend on the SIMD level or the number of workers; it can differ from the normal plan, which adds in heap order, by the rounding of reordered float addition (the comparator's tolerance: relative 1e-9, absolute 1e-12).

A generic aggregate is PostgreSQL's own arithmetic over the values in scan order, so it is exact where the function is (numeric, integers, text, dates) and, for float accumulation (`stddev`, `corr`, `sum(float4)`), differs from a normal plan that sorts before aggregating by the rounding of the reordered additions (the comparator's tolerance); the normal plan's own order is not fixed either. Its errors are the function's, raised at the same value.

Float sums are not the normal plan's, and they are not the same between a serial scan and one with workers: a serial scan adds in tuple order into the 16 lanes, workers each fill their own lanes over the units they took and the leader adds the lanes in order, so the last digits can differ between the two and from the normal plan. It is the class of difference PostgreSQL's own parallel float sums have (a parallel plan adds partial sums in the order the workers finish); every other aggregate is exact. Within one mode the result does not change with the SIMD level.

The order of the groups is not stable between a serial and a parallel run (the workers merge their tables in launch order and a hash table lists its groups by slot): a query that needs an order has an `ORDER BY`, as with the normal plan, whose group order is the hash table's too.

PostgreSQL's float8 aggregates raise errors that a plain double sum would hide. `sum(float8)` raises the overflow error when a group's sum is infinite and none of its inputs was. `avg(float8)` keeps a sum of squares (`float8_accum`) that overflows first; the scan does not keep it and raises the same error when the inputs are so large that it could have (`8 * n * max(x)^2 >= DBL_MAX`). The one input where the normal plan does not fail although the bound is met (all values equal and above 1e150) fails here too; set `sift.enable_agg` off for it. Overflow errors inside a float8 expression argument are not reproduced (the result is infinite).

A value the index cannot hold (a jsonb member that does not fit the declared type, a JSON string in a number path, text over its declared `text(N)`: the shredder's overflow) is not read from the leaf by the scan: where the rows are not read again from the heap (below) it raises `0A000` with a hint when it meets one, instead of the cast error the normal plan raises on a value that is not valid (`22P02`). The planner refuses leaves the engine marks lossy, and a leaf a unit flags with an overflow value (`SiftColLeafStats.has_ovf`, from the zones the planner reads for its statistics, memoized per backend) or a write buffer holds one of; the NaNs of a numeric leaf apart, which PostgreSQL evaluates: a query that reads one keeps the normal plan, which reads the value from the heap, and gives the rows it gives, or the error it gives (`col_agg_overflow`; a number out of the range of its `int2`, `int4`, `int8`, `float4` or `float8` path is such a value: `col_agg_overflow_range`). The scan reads those rows again from the heap only for the columns of a `jsonb_to_recordset`: the value a row has depends on the expression that reads it (a record column or a `->>` cast reads the string `"2"` as 2, `@>` and jsonpath compare it as a string), which the leaf does not record, so every other read of a flagged leaf keeps the normal plan (and `check_overflow` below stays the guard of a plan older than the value). For a recordset the flagged rows leave the unit's live mask and come back after it as an in-memory unit made from the heap tuple (the snapshot's version, a HOT chain followed, the index expression evaluated again), shredded with the SQL of the function: the text of a scalar through the input function of the declared type, a key of an array or a scalar is NULL, and the error the function raises (a string that is no number, a list that is no array, an element that is no object, a column the query does not read) is kept and raised when the row reaches the expression, after the row's own conjuncts, so the rows that do not reach it raise nothing. The planner charges `AGG_RECHECK_FRAC` of the rows at `AGG_RECHECK_ROW` operator costs when the leaf is flagged; `EXPLAIN ANALYZE` shows `Rows Read Again From The Heap`. The flag stays with the unit, dead rows included, until the segment is rewritten: a `VACUUM` rewrites a lone segment that flags the overflow of a leaf only in dead rows, whatever its share of dead rows (`sift_cseg_stale_ovf`), and the pushdown is back without a `REINDEX`. A `VACUUM` that finds dead rows on under 2% of the heap pages skips the vacuuming of the indexes, so the index never hears which rows died: its `amvacuumcleanup` then looks up the heap row of every row that holds an overflow value (dead to every snapshot, following a HOT chain: `sift_cseg_reap_overflow`) and clears the liveness of the gone ones before the merge picks (`col_agg_overflow_vacuum`). A plan made before such a value was written (a prepared statement's generic plan) is invalidated by the writer: the first row of a write buffer that overflows a leaf sets the leaf in the buffer's directory entry and invalidates the table's relcache entry in every session at once, whether or not its transaction commits (`col_agg_overflow_buffer`), so the next use plans again and keeps the normal plan. A scan that is already running when another session writes such a value, or that was planned before, returns the rows of the normal plan: before a unit is filtered the rows that hold such a value in a leaf the scan reads are checked against the snapshot (`check_overflow`: the live ones, then the heap check of `sift_colsrc_vet` for those rows only), and a writer that is in flight, rolled back or committed after the snapshot leaves none to see (`agg_overflow`, an isolation spec). A row of the snapshot that holds one still raises the error (a plan older than a value committed before the snapshot: the invalidation above leaves that window narrow).

## SIMD

Kernels are chosen at run time through the `sift_cpu` rebind registry and `sift.simd`; the scalar table is the specification and the AVX2 and AVX-512 tables are bit-identical to it, so every result is the same at every level. `sift_aggkern_for(level)` returns a level's table for the differential test. `scripts/coldiff.sh` runs the corpus at `sift.simd = scalar` and `auto`.

### Grouping sets and float keys

- **Sets**: the scan keeps one group table per set over the same key ids; the set is a key of the groups, so a group of the empty set is one group and a data `NULL` is not the `NULL` of a rolled up key. `GROUPING(a, b)` is the bit mask of the sets (the first argument is the highest bit); the empty set returns its one row over no input too. A query of N sets is priced as N group updates per tuple; the filters, leaf reads and unnest are paid once.
- **Float keys**: a float4/float8 column or expression is a key through its bits, with `-0` as `0` and every NaN as one NaN (`float8_eq` and `hashfloat8`); the index stores `-0` with its sign (the scan treats it as `0`) and a value it cannot hold raises `0A000` as above, and the group is emitted as the type's value (`float4` stays `float4`).

## Cost

`agg_cost` prices the scan from the source's statistics: a leaf read, a predicate, a tuple that passes the filters, a key id and an aggregate update, each in `cpu_operator_cost` (about 3 ns here: the constants were fitted on whole table runs of one to three keys and aggregates, 17 ns per unnested element all in). The operators the scan itself runs (reads, filters, tuples, keys, aggregate updates, the merge of workers) are charged `AGG_SCAN_SPEED` (0.2) of their count: the shapes it runs alone take 0.4 to 0.9 ns for an operator counted at 3 ns, and at the full count a scan 5 to 40 times faster than the normal plan was priced above it; the reads of lookup tables, the children's plans and the expressions PostgreSQL evaluates keep their price. The arms of a `UNION ALL` that run as one pass (`agg/fuse.c`) are priced as one under `SiftAggRows`: the others pay `AGG_FUSED_ARM` (0.1) of their price. The scan reads every unit that the zone tests leave (above, "Zone pruning"; none on a column the heap order does not follow), so a selective query is priced by its table scan against the btree plan's selected rows: the measured crossover keeps the normal plan for the 10 and 400 store sets and takes the scan for the 4000 store set and the whole table. The grouping sets, the mapped aggregates and the outer WHERE add the update cost of their sets and accumulators only: no constant changed. Heap vetting of the rows on pages that are not all-visible is added per page, of the pages of the units the zone tests leave (a table just rewritten by `CLUSTER`, `VACUUM FULL` or `pg_repack` has an empty visibility map: a scan that keeps a tenth of the units is charged a tenth of the table's pages, not all of them). Elements per row of an array default to 3 when the source has no statistic.

The scan is also charged the stored bytes it reads (`scan_bytes`): the compressed bytes of the index shared among its leaves by value width (4 or 8 bytes), 0.1 operator per byte (about 3 GB/s), times the share of the units the zone tests leave; a source that does not know its bytes (a table) is taken to compress by half. This is added after the credit above, so a scan of wide columns of a big table is priced by what it reads, and the heap plan keeps PostgreSQL's own page and tuple prices.

Two terms keep the selective queries on the normal plan, where the scan reads every unit and the btree plan reads the selected rows. The scan pays a start-up of 210000 operator costs (about 0.6 ms: opening the source, the lookup tables, the first units; 1 to 1.5 ms measured on a scan pruned to a few units), which a plan on a few dozen rows does not. A scan of an unnest is charged the square root of the excess of the unnested rows the normal plan expects (100 per call of `jsonb_to_recordset`, `jsonb_array_elements`, `jsonb_each`, less what its filters cut) over the elements the selected orders hold (about 6 for an unfiltered unnest of 3 elements per row, 1 when an element filter cuts the expectation: G2), because its sort, join and aggregate costs grow with that excess though the data has a handful per row. The estimates of the two plans then cross where the times do. A metric of a free key object looked up by key (`metrics->>'m_total'`) is charged 9 operator costs per element of the object and key (`AGG_VLEAF_ELEM`): a float key of it at K400 was 0.3 times before. S3 at K400 (0.6 to 0.85 times before) and the summed-`numeric` shape without a path flag at K400 keep the btree plan; S1 and S2 at K400 and every shape at K4000 keep the scan. The fixtures `p_cost_selective_unnest`, `p_cost_selective_numeric` and `p_cost_selective_metric_key` assert it (`expect: plain`).

A path with workers pays `AGG_SETUP_FACTOR` (22) times `parallel_setup_cost`: starting four workers and opening the source in each takes about 8 ms, and in the estimates of this path (the unnest excess included) a cost unit is worth about 0.5 us, so the default 1000 would charge 0.5 ms. At 22 the scans of under 15 ms (G1 to G6, S1, S2, S4, S6 and S7 at K4000) keep the leader alone, which is what the measurements ask for (W=4 not above W=0 beyond noise), and S3 (241000 units) and the percentile scan (G7, 185000 units) take the workers and gain. The ordered-set aggregates add the merge of their histograms, 1.5 operators per value (`AGG_ORDERED_MERGE`).

The rows the node returns are bounded by the groups its tuples can make (`rows_out` in `agg_cost`: the sets times the unnested rows it expects to aggregate). PostgreSQL's group estimate of an unnest is its default 200 distinct values times the 100 rows it assumes per call, 768500 groups for S5 (20334 exist), and the sort and window above the node were priced for them: the node's plan was estimated above the plain parallel plan (261889 against 252983) though it runs five times faster, and the plain plan is cheaper by its pathkeys. With the bound the plan above the node is priced for the groups that can exist (S5: 117883 against 350917 plain at every worker count).

A plan with a SiftAgg node is not JIT compiled (`sift_planner`, `src/agg/cte.c`): its cost, which stands for 15 to 40 ms of scanning, is above `jit_above_cost`, and compiling the projections of the nodes above (a window, a union) took 3.5 to 5 ms of those queries (S3 -17 percent, S5 -14, S4 -13).

The shapes with a fixture:

| Shape | Reason |
|---|---|
| `FULL JOIN` to a table | the unmatched rows of the table would be output rows with no source row; the scan only emits tuples of source rows |
| `RIGHT JOIN` | PostgreSQL turns it into a `LEFT` join of the other side, so the table is the preserved side: the same reason as `FULL` |
| a correlated or row-valued `NOT IN (SELECT ..)` | the hashed `SubPlan` reads the row, or tests two columns at once: it is no lookup table over one leaf. `NOT EXISTS` is a join (pushed) |
| a correlated `LEFT JOIN LATERAL (SELECT .. LIMIT 1)` lookup | the row PostgreSQL takes among duplicate keys depends on its plan, so the scan cannot be exact unless the key is unique: write it as a join on the key |
| join to a sub-select with `GROUP BY`/`LIMIT`/`DISTINCT`, a CTE that is read more than once, `VALUES`, a function in `FROM` | PostgreSQL does not pull them up to a base table, so the right side is a plan, not a table the scan can read at start; running a child plan under the node is not done |
| the scanned table on the nullable side of an outer join (`spine s LEFT JOIN items t ON t.d <@ s.range`) | the scan would have to return a group for every row of the other table (a `RIGHT JOIN`): write the aggregate first and join the spine above it, which is pushed |
| a lookup keyed from a column of another joined lookup | a second join level (one combo holds one table); a literal, a `CASE`, or a join of the lookup to the scan's own column is pushed |
| join with no equality between leaves and columns of the table (a range or inequality join, `ON true`) | nothing to hash the table by; each distinct tuple would scan the table |
| more than 3 keys in one join, more than 32 joined tables, more than 128 combos | the limits of the spec (`SIFT_AGG_MAX_JOINS`, `SIFT_AGG_MAX_COMBOS`) |
| key or filter that is volatile (`random()`, `clock_timestamp()`) | PostgreSQL evaluates it per row; the combo cache evaluates it once per distinct tuple |
| the same leaf with two types in one combo (`varchar` leaf compared with a `text` column and `IS NULL` of the leaf as `varchar`) | the combo types each leaf once; the relabelled use is another type |
| join key of text with a nondeterministic collation | the equality of the collation is not byte equality of the dictionary entries |
| `sum`/`avg`/`min`/`max` of a joined `money` column | no hash opclass for the distinct-values table of mapped aggregates |
| `sum(float4)` of a joined column | float4 addition is order dependent: the distinct-values form adds `value * count` |
| `sum`/`avg` of other types of a joined column (`numeric` and `float8` are matched; `int2`/`int4`/`int8`, `interval` and `avg(float4)` through the PostgreSQL functions) | the aggregate is not in the allowlist of `mapped_pg_agg`; a function whose transition state is not a copyable datum cannot run per distinct value |
| volatile outer qual above the arms (`WHERE random() < 0.5`) | PostgreSQL evaluates it once per inner group; the scan would evaluate it per cell, in another order; fixture `t_two_level_where_volatile` |
| outer qual above the arms that mixes a group column of an arm with an inner aggregate (`avg_price > 100 OR kind = ..`) | the column belongs to the cell's outer group, which is known only when the cell is attributed; fixture `t_two_level_where_mixed` (the inner aggregate may still run in the scan) |
| outer qual that reads the columns of several arms of the `UNION ALL` (it stays as a filter of the append) | a cell belongs to one arm; the qual would need the other arms' cells of the same row, which the scan has not seen yet |
| a non-null constant as the key of an arm (`SELECT id, 'z', avg(x) .. GROUP BY id`; `NULL` is pushed) | the arms are the cells of one outer key, and no arm's group expression holds the constant: the key's value table would take it from the arm |

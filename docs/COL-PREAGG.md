# Pre-aggregates of a unit (metadata-only and low-cardinality aggregation)

Status: the writer, the format, the provider callbacks, the SQL hooks and the `SiftAgg` consumption (section 6) are implemented and shipped in 3.0 (column format 1, minor 2 introduced the pre-aggregates; 3.0 writes minor 3); the element rollups, the per-unit rollup of the elements of a list or of the values of a map, are column format minor 4 (sections 2, 6 and 7), and the rollups of the units are refreshed on demand by a background worker (section 7); the rollup of the rows of a unit by a few scalar columns, `rollup_dims`, is column format minor 9 (sections 2 and 6).
Files: `src/col/preagg.[ch]`, `src/col/preagg_opt.c`, `src/col/preagg_read.c` (formats, option, compute, verify; portable), `src/col/seg_write.c` (written with the unit), `src/col/seg.c` (read per segment), `src/col/pagg.[ch]` (through the column source), `src/col/rollup.c` (the on-demand refresh), `src/agg/colsrc.h` (`unit_exact`, `unit_agg`, `unit_hist`, `unit_rollup`, `preagg`), `src/agg/spec.c` (`sift_aggspec_preagg`), `src/agg/unit.c` (`preagg_*`), tests `col_preagg`, `col_preagg_elem`, `agg_preagg`, `agg_preagg_elem`, `agg_preagg_elem_parallel`, `agg_preagg_rollup`, `col_rollup_refresh`, the isolation spec `col_rollup_refresh`, the TAP `col_rollup_ondemand`.

## 1. What other engines precompute, and what is taken

| System | What it keeps | Taken here |
|---|---|---|
| Parquet / ORC | per row group and column: `null_count`, `min`, `max`, (ORC: `sum`, `count`) in the footer ([Parquet statistics](https://github.com/apache/parquet-format/blob/master/README.md), [ORC ColumnStatistics](https://orc.apache.org/specification/ORCv1/)); `count/min/max` answered from the footer | the zone maps already hold this (`SiftCZone`); exact 128-bit `sum`/`sum of squares` added (the zone's int64 sum overflows) |
| ClickHouse | row counts and min/max of a part answer `count()` and `min/max` with no scan (`optimize_trivial_count_query`, implicit `_minmax_count_projection`); aggregating projections, `AggregatingMergeTree` ([projections](https://clickhouse.com/docs/en/sql-reference/statements/alter/projection)) | the top-level cube is a projection `GROUP BY dim` with `count`, `sum` per measure; the element rollup is a projection over all the dims of a list with the aggregates stored as plain columns (`count`, `sum`, `min`, `max`: the finalized states of `AggregatingMergeTree`, which merges only the same sort key); no merge-time state, the unit is immutable |
| Apache Pinot | star-tree: `dimensionsSplitOrder`, `functionColumnPairs` (`SUM__col`), `maxLeafRecords`; every group-by/filter column must be in the tree ([star-tree index](https://docs.pinot.apache.org/basics/indexing/star-tree-index); Xin et al., *Star-Cubing*, VLDB 2003; Gray et al., *Data Cube*, ICDE 1996) | the top-level `cube(dim: m1, m2)` is `dimensionsSplitOrder` of depth 1 with `SUM`/`COUNT` pairs, the same rule (a query may use it only if all its aggregates and its one group column are stored); the element rollup keeps every dimension of the list in one level and no pre-aggregated star nodes (section 1, below); `rollup_dims` is the same for the rows of the table: the distinct tuples of two to six scalar columns per unit, any subset of them answered by adding up the tuples (no split order), bounded by a cap of tuples per unit |
| Druid | rollup at ingestion, segment metadata ([rollup](https://druid.apache.org/docs/latest/ingestion/rollup/)) | the element rollup is the ingestion rollup of Druid (distinct tuples of the dimensions with the aggregates), per unit and kept beside the rows (the rows stay: results are exact, and a query that does not fit scans them) |
| DuckDB | zonemaps per row group; row-group counts answer `count(*)`; statistics propagation | `sift_col_unit_exact` + zone cover test |
| Snowflake | micro-partition metadata answers `count/min/max` ([micro-partitions](https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions)) | same |
| PostgreSQL | index-only scans trust the visibility map; aggregates split into transition and combine functions ([xaggr](https://www.postgresql.org/docs/current/xaggr.html), [index-only scans](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)) | visibility rule of section 4; section 5 builds PostgreSQL's own transition states |

Differences that matter: a unit is immutable, so there are no mutations to maintain (ClickHouse) and no segment updates (Elasticsearch); correctness under DML is the visibility rule alone. Results are PostgreSQL-exact: nothing is approximate (no sketches).

**Why a rollup of all the dimensions of a list per unit, and not a star-tree, a chosen cube or a projection.** The question is which GROUP BY of the elements of a list or the values of a map (`items[].kind, items[].sub, items[].flag`) can be answered without reading the unit, when the query is not known when the index is built.

- *Apache Pinot* builds a star-tree over `dimensionsSplitOrder`: a tree whose nodes carry the aggregates of the records below them, with a "star" child per level that stands for any value of the dimension, so a query that groups or filters by a prefix-compatible subset of the dimensions reads a few nodes. The tree answers every subset of its dimensions only if the split order puts the query's dimensions first and the leaf threshold (`maxLeafRecords`) is not hit; a dimension left out of the tree makes the query ineligible, and the size grows with the number of distinct prefixes. It is built per segment, like here.
- *Druid* rolls rows up at ingestion to the distinct tuples of the dimensions with the aggregators stored (count, sum, min, max); every query is answered from the tuples, and the original rows are gone. The tuple table is exactly what is stored here, per unit; the difference is that the rows stay, so a query that does not fit (a `count(DISTINCT)`, a high-cardinality key) scans them and is exact.
- *ClickHouse* gives two tools: a projection `GROUP BY` that the optimizer picks when it covers the query (a different projection per dimension subset is a different copy of the data), and `AggregatingMergeTree`, whose rows hold partial aggregate states merged in the background (it merges rows of the same sort key, so it needs the grouping to be the sort key; it is made for incremental updates, which an immutable unit does not have).
- *Here* one rollup per unit and list keeps the distinct tuples of up to 6 low-cardinality dimensions with `count(*)` and, per measure, the non-NULL count, the sum, the minimum and the maximum. Any GROUP BY over a subset of the dimensions, and any filter on them, is the same pass over the tuples (add up the tuples that agree on the group key), so there is no split order to guess, no star node, and nothing is stored twice. The price is that all the dimensions are in every tuple: the number of tuples is the number of distinct combinations in the unit (bounded by a cap and the byte budget; the greedy drop of the highest-cardinality dimension keeps the rollup small when the product explodes), where a star-tree stores prefixes. For the dimensions this is meant for (a few dozen values each, correlated in real data) the unit's tuple count is small: the 28 units of 100,000 documents (13,800 elements each) hold 36 tuples for `kind, flag` and 1,440 for `kind, sub, flag`, where every combination of 12, 40 and 3 values is present (section 2, measurements). A query by a dimension that was dropped, by a measure that is not stored, or by a high-cardinality key is not answered; it scans that unit as before.

**Not covered by design**: `count(DISTINCT x)` (except of a column the cube holds a histogram of: its groups are its distinct values, so the units that answer add their groups to the set the scan fills, `sift.agg_preagg_distinct`; one column, no `FILTER`, plain 32-bit or text) and other aggregates that are not additive over tuples (`percentile_*`, `mode`, `string_agg`, `array_agg`, statistics such as `stddev` of floats), `min`/`max`/`sum` of a measure that is not stored, a measure that is an expression, group keys of high cardinality (a key with more distinct values than the tuple cap in a unit: that unit scans), and numeric (decimal) measures of jsonb (section 9). Sketches (HLL, t-digest) would answer some of them approximately; the answers here are exact or the unit scans.

## 2. What is precomputed (written when a unit is built, merged, promoted, rewritten by VACUUM's merge, and by every worker of a parallel build)

- **Placement**: after the zone arrays, inside the `ZONES` section of the segment (the segment header has no free section: BM25 shares it). Header `COLP` (version, ncols, nsb, offsets); no unit record is touched, so a metadata query never reads a chunk. Format minor 2 (a segment of the minors 0 and 1 is refused with the REINDEX hint, as is one of minor 2 now that the current minor is 3).
- **Leaf sums** (every INT-class leaf, children of lists included): exact `sum` and `sum of squares` as int128 (`u64 lo`, `i64 hi` arrays over the units, 40 bytes per leaf and unit). `sumsq` can leave int128 only for int8 values of about 10^18: flag `SIFT_CAGG_SUMSQ_OVF`, the consumer then scans. Zone data are reused for `count`, `nnull`, `min`, `max`, float `sum` (row order of the unit).
- **Cube** (`sift_cpagg_cube`): per unit and dimension `GROUP BY dim -> count(*)`, and per measure the non-NULL count and the sum (INT measure: exact int128; float: double in row order, seeded with the first value as `float8pl` does, so a group of `-0` sums to `-0`). Group keys are in key domain, ascending, the NULL group last: a text dictionary leaf by **segment code** (translate by value through the segment dictionary), an integer, `date`, `bool` or `numeric(p,s)` leaf by its stored value (a leaf holding `date_trunc('month', ts)` is the time dimension). Stored as varints (counts, deltas of keys, zigzag int128), framed by a directory so one dimension decodes alone.
- **Dimensions** are scalar INT/STR leaves (no floats: `-0` and `NaN` group by value in PostgreSQL), top level, not inline text, no overflow value. A dimension with more than 256 groups in a unit has no histogram in that unit (cap; `cube(...)`: 4096). **Measures**: `numeric`, `real`, `double`, `int2/4/8` leaves, at most 8 per dimension in the default (decimals and floats first, then integers; the dims a unit keeps are chosen by their size with the first 3 measures, under the budget below, and a dim that is kept carries all its measures: +1.6% index bytes on a 10-column table with 4 dims, +0.0% to +1.6% from 25k to 200k rows).
- **Min and max per group** (column format minor 7): the reloption `cube_minmax` (boolean, default on since 3.3, `ALTER INDEX ... SET`; `cube_minmax = false` writes what 3.2 wrote) makes every group of the cube of the units written from then on also hold, for each integer measure (`int2/4/8`, `numeric(p,s)` as its scaled integer), the smallest and the largest value of its non-NULL rows (flag bit 1 of the dim body; after the sums of the measure, the minima of the groups that have a value, then the maxima, as zigzag keys; the decoder refuses a group whose minimum is above its maximum and any other flag bit; `sift.col_verify` recomputes them and refuses them in a segment older than minor 7). Float measures keep none. The segment is written as minor 7 only when the option is on and `sift.col_format_minor` is 7 or more (12 is the default) and, for a schema with jsonb paths, when every kind of its rows is known (promotion and merge lower the setting otherwise): an index without the option writes the bytes it wrote before, and under a setting of 6 or less the option is ignored, so a 3.2 library keeps reading both; a 3.2 library refuses a minor 7 segment with the REINDEX hint. Units written before the option have none and scan; `REINDEX`, a merge and a promotion write them. `sift.col_refresh` rewrites the older segments without a rebuild (section 7). The default is measured (200,000 rows of 13 columns, 53 units, minimum of 15 runs, 2026-10-22, PostgreSQL 18.6, a host at a load of 30): `GROUP BY kind` with `min`/`max` of an int4 and an int8 5.5 ms scanned, 0.34 ms from the groups, the other queries unchanged; the sidecar grows 5.5 kB of 152 kB (+0.17% of the index) and the CPU of insert, promotion, merge and VACUUM stays inside the noise (a unit that cannot hold the larger cube in its budget of 2% of its bytes drops the least useful dim, which then scans). Cost: 1.0% to 3.0% of the index bytes (store-like table of 8 columns, default cube with 4 dims, 25,000 to 200,000 rows: +6.1, +10.1, +16.0 and +13.3 kB of pre-aggregates over 205, 451, 729 and 1,368 kB of index). 200,000 rows, `GROUP BY kind` with `min`/`max` of an int8 and a numeric(10,2): 30.5 ms normal plan, 2.6 ms every unit scanned, 0.23 ms from the groups.
- **Calendar cells of a date or timestamp** (column format minor 8, `sift_table`): a `sift_table` has no index option and no expression leaf, so the cube of each unit also holds, for every top-level `date`, `timestamp` and `timestamptz` column, the groups of its calendar cells, at the **finest grain that fits**: days, else months, else years (the *ladder*). The key of a group is the first day of the cell, as days since 2000-01-01 (a `date`); a `timestamptz` is cut in UTC days, whatever the zone of the session. The directory leaf is `grain * SIFT_PAGG_CAL` (128) plus the column (grain 1 day, 2 month, 3 year), so the grain is recorded per unit, a table of mixed units reads them all, and the reader asks for the dim of a column at whichever grain the unit has. A grain fits when the unit has at most 1,024 cells of it (`SIFT_PAGG_CAL_GROUPS`: 2.8 years of days, 85 of months, 1,024 of years), each standing for 8 rows or more on average (`SIFT_PAGG_CAL_ROWS`: answering from cells has to read far fewer than the rows), and the dims of all the calendar columns together fit 5% of the unit's bytes (at least 4 kB; the other dims take 2%). A cell takes about 20 bytes with one measure and about 33 with four, so 1,024 cells are 20 to 35 kB, the 5% of a unit of 400 to 700 kB; a narrow table keeps days for the 60 or so days a unit spans. The measures are those of a default dim. A unit with an infinity or a day before 4713 BC in the column, one that fits no grain, and one written before minor 8 has no dim for the column and scans.

  The planner answers from the cells every key that is a function of the cell. For a key of the leaf `x` it finds the grains whose cells hold one value: `date_trunc(unit, x)` and `extract` or `date_part(field, x)` of a `date`, `timestamp` or `timestamptz` (see below), the casts `::date`, `::timestamp`, nested and combined (`date_trunc('month', date_trunc('hour', x))::date`, `extract(year FROM date_trunc('month', x))::int`), a comparison, `IN` or `IS NULL` of them as a test. A key that depends only on the day (`day`, `week`, `dow`, `isodow`, `doy`, `isoyear`, `date_trunc('week' | 'day')`, `::date`, and every function of a week start, whose year or month can differ from the day's) needs cells of days; one that depends only on the month (`month`, `quarter`) cells of months or days; one of the year (`year`, `decade`, `century`, `millennium`) any cell. A unit whose cells are coarser than the key needs scans (a week key over cells of months), as does a key that changes within a day (`hour`, `minute`, `second`, the timestamp itself): the plan says why (`sift.col_rollup_misses`: `rows_key_finer_than_day`). The planner evaluates the key's expression once for each cell, at its first day, so a `GROUP BY extract(isoyear FROM ts)` costs a group per cell instead of a row.

  A `timestamptz` key reads the session zone (`date_trunc('month', tz)`), which the UTC day cells cannot answer and a bucket per day does not give either: it is a lookup the planner does not build, and `sift.col_rollup_misses` says `combination`; the same key over the clock of UTC, `tz AT TIME ZONE 'UTC'` or `date_trunc('month', tz, 'UTC')`, is a function of the UTC day and is answered. A key of an hour or less on a timestamp says `rows_key_not_a_column`; on a `date` a key that cuts finer than a day says `rows_key_time_zone` or `rows_key_finer_than_day`. A `date` column whose values (an infinity included) are too far apart for a lookup table of its days is not keyed by cells either (`combination`). On a `date` column the keys that cast to `timestamptz` (`date_trunc('month', d)` is that) are answered from cells of days only: a month cell would give a skipped day of a zone (a date that does not exist there) the value of its first day. A range on the column (`ts >= a AND ts < b`, any zone for a `timestamptz`: the bounds are instants) is decided by the span of each cell: a cell inside passes, one outside does not, the NULL cell never does, and a unit with a cell that a bound cuts is scanned. With no key a range of the column answers the units whose zone it does not contain from the cells too; an `extract(...) = k` or `IN` test of a `date` runs on the cells (`SAP_LUT`, its grains narrowed to those the test is constant over). Other tests, a `FILTER` of the aggregates, two keys and `min`/`max` of the column scan the unit as before. The decoder refuses a key that is not the first day of a cell of the unit's grain, a column that is not a date or timestamp, and keys out of order, and `sift.col_verify` and the check of the cube recompute the cells, at the grain they have, from the chunks. Written only when `sift.col_format_minor` is 8 (the default) and the schema has no JSON path leaves; under 7 or less a `sift_table` writes the bytes it wrote before and a 3.2 library reads it. A `sift_col` index keeps them for every date, timestamp and timestamptz column too since 3.3 (the reloption `calendar_columns`, default `'all'` or empty; `'ts, d'` names the columns, `'off'` none; `ALTER INDEX ... SET` applies to the units written afterwards), with the same ladder, budget and planner rules; an index with JSON paths, `preagg = 'off'` or a `cube(...)` given dim by dim has none by default and refuses the option when it names columns. Measured on 200,000 rows of 13 columns with a `date` and a `timestamptz` (53 units, minimum of 15 runs): `GROUP BY date_trunc('month', d)` 2.4 -> 0.54 ms, the UTC month of the `timestamptz` 2.6 -> 0.70 ms, the other queries unchanged; the sidecar +1.8% of the index for the two columns (+1.0% for one). A superunit does not merge the calendar cells (merged, they cost another +1.2% and answered no query faster).
- **Rollup of the rows** (column format minor 9, opt-in): the reloption `rollup_dims = 'a, b'` or `'a, b, c: m1, m2'` (default off, `ALTER INDEX ... SET`; the names are columns of the index) makes every unit written from then on also hold the **rollup of its rows**: the element rollup below with the rows of the unit in the place of the elements of a list. A cell for each distinct combination of the values of the dims (two to six boolean, integer, date, `numeric(p,s)` or text columns of the top level; NULL is a value of its own) with the rows of the cell and, per measure, the non-NULL count, the exact sum, the minimum and the maximum. The measures are the ones named after the colon, else the integer and `numeric(p,s)` columns that are not dims (decimals first, 8 at most); a float column is none, because a float sum depends on the order of the additions. Same blob and encoding as the rollup of a list, listed in the element blob of the unit under the leaf number `ncols`, which no list has; the decoder also refuses a rollup of the rows whose cells do not add up to the rows of the unit, a cell with no rows, a measure with more values than its cell has rows, and a minimum above a maximum. **Bounded**: a unit keeps its cells only when it has at most a tenth of its rows of them (at least 64, at most 4,096; the cells of the exact dims named, none dropped); a unit with more has no rollup and is scanned, so a high-cardinality column costs no bytes in that unit and the answer is the scan's (`Units Without The Rollup` of `EXPLAIN ANALYZE`). The segment is written as minor 9 only for an index with the option when `sift.col_format_minor` is 9 (the default) and, for a schema with jsonb paths, when every kind of its rows is known (promotion and merge lower the setting otherwise); an index without the option, and any setting of 8 or less, write the bytes they wrote before, so a 3.2 library keeps reading them; a 3.2 library refuses a minor 9 segment with the REINDEX hint. Units written before the option scan; `REINDEX`, a merge, a promotion and `sift.col_refresh` (section 7: it counts a segment without them as stale only under a setting of 8 and where the kinds of the rows are known) write the cells; the on-demand refresh of section 7 does not ask for them, because it would turn a segment a 3.2 library reads into one it cannot. `sift.col_verify` recomputes them from the chunks and refuses them in a segment older than minor 9. Cost: see "Rollup of the rows, size, time and answers" below.
- **Element rollups** (format minor 4; `COLP` directory version 2, written only by a minor 4 writer, `sift.col_format_minor`; they replace the depth-1 element cubes of the first minor 4 builds, which no release carried): for a list group (an array of objects `items[]{k, n, x}`, an array of scalars `tags[]`, a map `m.*`) per unit one **rollup** of the list whose rows are the elements: the distinct tuples of the values of up to 6 low-cardinality leaves of the list (the **dims**), each with its element count and, per **measure** (a numeric leaf of the same list, at most 8), the non-NULL count, the sum, the minimum and the maximum. A tuple is a group of the `GROUP BY` of all its dims, so any `GROUP BY` over a subset of the dims, any filter on the dims, and `count`, `sum`, `avg`, `min`, `max` of a measure are answered by adding up the tuples that agree on the subset (an element that is not an object is a tuple with NULL members, as the unnest produces it). Encoding of the blob of a list: `u8 ndims, u8 nmeas, varint ntuples`, the leaf of every dim and measure, then column-wise: per dim a NULL bitmap and the keys as zigzag deltas (tuples sorted by dims, a NULL sorts after the values; text by segment code, integers, dates and numerics by stored value, as in the cube above), the counts, and per measure the non-NULL counts, the sums (an integer measure: exact int128 as two varints; a float8 measure: the sum in row order of the unit, seeded as `float8pl` does), the minimums and the maximums. The element blob of a unit follows the cubes of the columns: `u8 nlists`, then per list its leaf and byte count, then the blobs; the directory header gains `ecubedir_off` and `ecube_bytes` after the leaf-sum offsets. **The dims of a unit are in its blob**: units of one index may have been written with different dims (an `ALTER INDEX` between two builds, a dim dropped for one unit), and the reader answers a unit only if the blob holds the dims and measures the query reads; otherwise that unit scans. Depth 1: a dim is a boolean, integer, date, numeric or text scalar leaf of a list that is itself a top-level column of the index (a list inside a list is refused by the index). **Default**: every list of the index with at least one dim candidate, its dims (at most 6) and the numeric leaves as measures (8 at most, decimals and floats first); the number of tuples is at most `min(4096, max(64, elements / 32))` and, so that a product of dims that grows with the data cannot make the rollup large, the dims are dropped from the one with most distinct values in the unit until the tuples fit (`kind, sub, flag` of 12, 40 and 3 values with 13,800 elements per unit keep `kind, flag`); each list gets its own budget of 2% of the unit's encoded bytes, at least 2 kB, apart from the cube's. **Explicit**: the option `rollup` of the index (section 2, `Option`) or the clause `rollup(items[].kind, items[].sub: items[].score)` of `preagg` names the dims (and the measures) of a list; the unit holds exactly these or, when the tuples exceed the cap of 4096, no rollup for that list (the unit scans, and `EXPLAIN` shows it as `Units Without The Rollup`; no dim is dropped behind a name the option gave). A unit has no rollup for a list whose count overflowed (a value that is not an array, a list cut by the shredder); a dim that overflowed is left out of the dims of its unit; a measure that overflowed is left out of the measures. Minor 3 segments have none of it and are read as before, in the same index, and stay as written (the on-demand refresh of section 7 leaves them alone: a rollup would need minor 4 and 3.0 would refuse the segment; their rollups come with the merge that rewrites them). `sift.col_verify` recomputes every rollup from the chunks. Size and time: "Element rollups, size, time and answers" below.
- **Options.** `preagg`: `'default'` (every dimension candidate, 3 measures to choose the dims, the first 3 measures of the dims kept take at most 2% of the unit's encoded bytes, at least 2 kB: the smallest histograms are kept first); `'off'` (leaf sums only, no rollups); `'cube(country: amount, quantity; status)'` (exactly these, no budget; names are attribute names or shredder paths); a `rollup(dims: measures)` clause beside a `cube(...)` clause (each clause replaces the default of its kind). `rollup` (a reloption of `sift_col`, **declarative**, new in 3.1): `WITH (paths = 'items[]{kind text, sub text, flag text, score float8}', rollup = 'items[].kind, items[].sub, items[].flag')` names only the dims, with the names of `paths`; the lists they belong to are inferred from the names, the measures are the numeric leaves of the list (8 at most), and the segments written from now on hold exactly these dims (up to 4096 tuples a unit, no byte budget). `rollup = 'off'` disables the rollups and keeps the cube, `rollup = 'default'` or no option is the automatic rule above. The names are checked when the index is created and when `ALTER INDEX ... SET (rollup = ...)` runs, and an error names the leaf: `invalid rollup option: "x" is not a leaf declared in paths`, `... is not a leaf of an array element or a map value`, `... is not a low-cardinality leaf: it must be a boolean, integer, date, numeric or text leaf` (a float, a JSON or an `astext` leaf cannot be a dim), `... is named twice`, `a leaf name is missing`, `the list of "x" has more than 6 rollup leaves`. A leaf with too many distinct values is not an error of the DDL, because the values are the data's: a unit whose tuples exceed the cap of 4096 holds no rollup for that list and scans (the first query that meets such a unit asks for a refresh once per segment, section 7, and the refreshed segment is remembered so that it is not asked for again). A change applies to the segments written afterwards; the units already written are asked for on demand (section 7) or rewritten by a merge. The option `rollup_on_demand` (boolean reloption, default true) and the setting `sift.col_rollup_on_demand` turn the asking off per index and per session.

## 3. Interface (phase 1)

- Engine (`col/pagg.h`): `sift_col_unit_preagg_ok(unit)` (stored unit, `sift_col_unit_exact`), `sift_col_unit_agg(unit, leaf, &SiftCAgg)`, `sift_col_unit_hist(unit, dim, mcxt, &SiftCHistDim, &SiftColDict)` (false: the unit scans). A unit of the write buffer or a delta batch has no sidecar.
- Provider seam (`agg/colsrc.h`, additive, NULL = none): `preagg(rel, &SiftSrcPreagg)` (planner: dimensions and measures the index writes), `unit_exact`, `unit_agg` (`SiftSrcUnitAgg`: counts, min/max, exact sums, sumsq, float sum, flags), `unit_hist` (`SiftSrcHist`: groups, `SiftSrcDict` of the segment, count, per measure `nn`, `sum`/`sumf`). Memory valid until the next `unit_hist`. Implemented for `sift_col` (`agg/col.c`) and `sift_table` (`table/src.c`); both read the sidecar through the shared `agg/pre.c`. A table unit is exact when `sift_col_unit_preagg_ok` holds: its superblock has no write buffer row and no tombstone (`tbl_sb_mask`). A segment of an older layout answers by the schema it was written with: a column the layout lacks, or a measure the table dropped, scans the unit.
- SQL: `sift.col_unit_agg(index, leaf)` and `sift.col_unit_hist(index, dim, measure)` (one row per stored unit / group; `exact` is the visibility rule), `sift.col_index_info` columns `preagg_bytes`, `preagg_units`; `sift.col_verify` recomputes sums and cubes from the chunks (C4). Test `col_preagg`: every leaf and every histogram against direct SQL after build, insert, update, delete, VACUUM, promote, merge and a parallel REINDEX; random data with NULLs, `NaN`, `-0`, infinities, int8 near 10^19, negative integers; invalid options. `sift._test_col_pagg_fold` is the benchmark of the metadata path.
- **sift_table owner** (done, `tbl_preagg`): sealed segments carry the sidecar (same writer). The table provider has the four callbacks over the table's `SiftColUnit` (the same `sift_col_unit_*` calls); `SiftColVisibility.sb_mask` is all-ones only for a superblock with no tombstone and no write buffer row (UPDATE/DELETE invalidate only the superblocks they touch); delta pages are in-memory units and scan. `SiftSrcStats.exact_frac` estimates the share of superblocks that qualify, from the write buffers and the dead tuples the statistics count.

## 4. When a unit's pre-aggregate may answer

1. **Visible and clean** (`unit_exact`): stored unit, no dead row (SB not dirty in the segment's liveness bitmap: VACUUM marks it, a merge rewrites it and recomputes), and every heap page it has rows on is all-visible to the snapshot (VM, as index-only scans; never for a non-MVCC snapshot). Rows inserted later are other units (write buffer, newer segment), scanned by the normal path and added to the result: the aggregate describes exactly its own rows. Inserts, updates and deletes cost only the units they touch.
2. **Predicate covers the unit** (consumer): no predicate; or the predicate on the dimension itself (`=`, `IN`, range: select groups by key value, text by the dictionary); or a zone-covered predicate (`min..max` of the leaf inside the range and `nnull` accounted: the unit answers whole, a disjoint unit is pruned as today). A unit the predicate cuts through is scanned. A predicate on another leaf than the dimension is never answered from a histogram.
3. **Leaf not lossy**: no `SIFT_COLZ_OVERFLOW` in the leaf and unit (`unit_agg` false), no inline-text zone for text min/max.

## 5. PostgreSQL-exact semantics (what the consumer builds)

| aggregate | from | notes |
|---|---|---|
| `count(*)`, `count(x)` | `nvals`, `nvals - nnull`; group `count`, `nn` | `int8` |
| `sum(int2/int4)` | int128 sum | `int8` when it fits (else the unit scans, PostgreSQL would raise); `sum(int8)` is `numeric` (its state is an int128 sum) |
| `sum/avg(numeric(p,s))` | scaled sum / 10^s | every value has dscale s, so the `NumericAggState` (N, sumX, maxScale s) is built from (count, sum); final function is PostgreSQL's |
| `avg(int)` | (count, sum) | build `int8[2]` / `Int128AggState`, call `int4_avg`, `int8_avg` |
| `stddev/variance(int, numeric)` | (count, sum, sumsq) | exact `Int128AggState`/`NumericAggState` with `sumX2`; sumsq overflow: scan |
| `sum/avg(float8)`, `avg(float4)` | unit sums in row order | same order caveat as PostgreSQL's parallel sum (float addition is not associative); refused: `sum(float4)` (float4 accumulator), float `stddev` (Youngs-Cramer `Sxx` is not stored) |
| `min/max` | zone key; per group of a cube with `cube_minmax`, the stored minimum or maximum of the integer or numeric measure | integer, date, time, numeric, float (`NaN` last, as PostgreSQL); `-0` vs `0` ties may print either; not text (codes and prefix keys are not order); per group not float |

NULL: an all-NULL measure group (`nn = 0`) yields NULL, the group still counts its rows; a NULL key is its own group. Group keys of text are compared bytewise: deterministic collations only (as `SiftAgg` today).

## 6. Consumption in SiftAgg (built)

- **Shapes** (`sift_aggspec_preagg`, `agg/spec_preagg.c`: the planner costs with it, the executor starts with it). A row level scan of one `sift_col` index (no join, combo, set, arm or unnest) with no key, or one key that is a dictionary text, `int2/int4`, `int8`, `numeric(p,s)`, date or bool column the index writes a histogram of (`SiftSrcPreagg`; an `int8` or numeric key is the column itself, not an expression of it, and its group is the stored integer: the key of the result is built from it as the scan builds it); aggregates `count(*)`, `count(m)`, `sum/avg(int2, int4, int8)`, `sum/avg(numeric)` of a measure `m` of that histogram, `count(key)`, `min/max` of an integer or numeric measure `m` per group when the cube holds them (`cube_minmax`), and, without a key, `min/max` of an integer, date or numeric column. Conjuncts: on the key's column (without a key: on one column) any test the executor evaluates (`=`, `IN`, `IS NULL`, `LIKE`, comparisons, expressions of the column) runs on the groups; on any other column only an integer or date comparison that the unit's zone lies inside (and without NULLs) keeps the unit answerable. Everything else is scanned as before: float sums (the order of the additions), `count(DISTINCT)`, `min/max` per group of an index or a unit without them, a float `min/max` per group, two keys, an expression of a key, tests on other columns, text `min/max`.
- **Executor** (`agg/unit.c`, `preagg_unit`, called by `process_unit` first): `sift_colsrc_unit_exact`, the zone test of the other columns, then the unit's sums (no key) or its histogram. A text group is translated to the key id once per dictionary (`dict_kmap`, as reads do), an integer group through the range table (`key_cover`, the part of `key_prepare` it shares); the conjuncts on the key column are evaluated by `eval_pred` on a vector whose rows are the groups; each kept group adds its rows to `seen` and its `PaVal` (rows, non-null rows, exact int128 sum) to the aggregate states of the group table (`preagg_add`: `count`, `sum`/`avg` of int, `sum`/`avg` of numeric in 128 bits, `min`/`max`). A unit that cannot answer (dirty page, write buffer, no histogram for the column in that unit, a measure the histogram lacks, an overflow value) is scanned into the same table, so a mixed table is exact and workers need no change (each folds its share; the blobs merge as before).
- **Cost** (`agg_cost`, `preagg_share`): the share of the units that are exact is the share of all-visible pages (`allvisible_frac`); those units cost `AGG_UNIT_COST + groups * AGG_PREAGG_GROUP` (25 operators per group, about 80 ns), the others the scan as before. From 98% exact no parallel path is offered: starting workers costs 3.1 ms (1 M) to 6.5 ms (10 M), more than the answer. Question 04's plan flip (`SiftAgg` against a parallel heap aggregate, 0.9% apart in cost, 10x in time) is gone because the exact units are no longer costed as a scan.
- **Element level** (`sift_aggspec_preagg` with `group >= 0`, `preagg_rollup` in `agg/unit.c`): the unnest of an array leaf (`jsonb_to_recordset`, `jsonb_array_elements`, `jsonb_array_elements_text`) or of a map (`jsonb_each`, `jsonb_each_text`: the key is the dim of the map's rollup, the value its measure) over the rollup of that list. Group keys: none, one or several of the dims of the unit, in any order (a subset of its dims), or a function of one dim (`upper(kind)`, `left(day, 7)`, a `CASE` on an integer dim: evaluated once per distinct value of the tuples, like a lookup key of the scan); conjuncts on the dims: `=`, `<>`, `IN`, `IS [NOT] NULL`, `LIKE`, comparisons and an `OR` of them, evaluated on the tuples; aggregates `count(*)`, `count(x)` of a dim or a measure, `sum`/`avg`/`min`/`max` of an integer or float8 measure of the same list; each may carry a `FILTER (WHERE ...)` on dims (run on the tuples); on the rows only the zone comparisons above. Every kept tuple adds its count and its per-measure states to the group table (`preagg_fold`), through the key ids, the direct address table or `hash_group` of the scan, so a mixed table is exact. The dims and measures a unit holds are read from its blob: a unit that lacks a dim of the query, a measure it reads, or the rollup itself is scanned (the other units of the same query still answer), and asks for a refresh (section 7). Not answered: a conjunct on a leaf that is not a dim (`WHERE e.q > 3`), a key of the rows (`d.grp`), a key that is not a dim or a function of several, `count(DISTINCT)`, a `FILTER` on a measure, `percentile_*`, an aggregate of an expression, a float aggregate other than `sum/avg/min/max` of a float8 measure, `sum(float4)`. A float8 sum adds the tuples where the scan adds the rows, so its last digits can differ (as for a parallel sum); the unit scans instead when a value of the float leaf is not finite or above 1e100 for `sum`/`avg` (min and max only refuse NaN), so `avg(float8)` keeps its overflow check. `EXPLAIN` shows `Units From Pre-aggregates` (units answered from a rollup), `Pre-aggregate Dims` and `Measures` (what the query reads), `Units Without The Rollup` (exact units scanned for lack of it) and `Rollup Refresh Queued` (segments asked for, section 7).
- **Rows level** (`sift_aggspec_preagg_why` tries `preagg_rollup` with group -1 when the histograms cannot answer a scan of the rows, and in `agg/unit_preagg.c` the same `preagg_rollup` answers it): for an index with `rollup_dims`, a scan of the rows with two or more group keys, or a key and a conjunct on another column, or a conjunct on a column other than the histogram's whose zone a unit must lie inside (which only the units of a clustered column do). The group keys are dims, one or several, in any order; every conjunct tests dims only (`=`, `<>`, `IN`, `IS [NOT] NULL`, `LIKE`, comparisons, an `OR` of them) and runs on the cells, so a range of a column that is not clustered, or an `IN` list with gaps, is answered too; the aggregates are `count(*)`, `count(x)` of a dim or a measure, `sum`/`avg` of a `smallint`, `integer`, `bigint` or `numeric(p,s)` measure, `min`/`max` of one, each with an optional `FILTER` on dims. A query the histograms answer (one key, tests of that key's column, no test at all) keeps them: they have fewer groups than the cells. Not answered: a float aggregate, `count(DISTINCT)`, an expression of a key (`a % 3`) or of an aggregate's argument beyond `column * k + c`, a conjunct on a column that is not a dim, grouping sets, top-N, and a dim of `int8` or `numeric(p,s)` as key or test (the cells hold them, the executor tests 32-bit values and dictionary codes). `EXPLAIN ANALYZE` shows `Pre-aggregate Rollup: rows`, `Pre-aggregate Dims` and `Measures`, `Units From Pre-aggregates`, and `Units Without The Rollup` for the exact units that had none (written before the option, or over the cap); `EXPLAIN (ANALYZE, VERBOSE)` gives the reason of a refusal. The cost is the element level's (next bullet): the cells against the rows of the unit, per unit.
- **Rollup or scan, by cost** (`rollup_cheaper` in `agg/unit.c`, `sift_aggspec_unit_costs` in `agg/spec_preagg.c`, the planner's `preagg_unit_ops`): a rollup costs its tuples, not its elements, but a tuple costs more than an element: the varint decode of the columns the query reads and the fold into the groups take 300 to 800 user instructions, where a scan spends 6 to 150 on an element (counts of one key 17, three keys 50, three float aggregates with min and max 150; 100,000 documents, 400,530 elements, 41,760 tuples in 29 units, `perf stat`). So a rollup of 1,440 tuples over 13,800 elements (10%) answers `GROUP BY kind` with `count` in 14.6 million instructions where the scan needs 7.0, and `GROUP BY` three keys or float `min`/`max` in 19 and 32 where the scans need 20 and 54 to 78. The executor therefore takes, per exact unit, the cheaper: the tuples of the unit's rollup (read from its header) times the cost of a tuple of this query, against the unit's elements (the zone of one of its leaves) times the cost of an element of this query; the units it scans that way show as `Units Scanned By Cost` and ask for no refresh. The setting `sift.agg_rollup_cost` scales the tuple (0: always the rollup, the tests of the rollup path set it). The planner prices the exact units with the same two costs and the tuples it expects (the product of the distinct values of the rollup's dims, at most the elements of a unit and 4096). Looking at a unit (its exactness, its rollup) costs buffer reads too: after three units in a row whose rollup costs at least a quarter more than their elements, the next sixteen are scanned without looking, and one is looked at again.
- **Switches and EXPLAIN**: `sift.agg_preagg` (on) turns it off for the plan and the executor; `EXPLAIN ANALYZE` shows `Units From Pre-aggregates` next to `Units` and counts `Rows Scanned` for the scanned units only (the line appears only when the shape qualifies). `EXPLAIN (ANALYZE, VERBOSE)` of a node that cannot use them prints `Pre-aggregates: <reason>` instead (`sift_pawhy_name`, the first check that failed, in this order: switch off, none stored, arms, grouping sets of the rows (those over a list's elements are answered), joins, combos, post-aggregation, virtual leaves, no aggregate, search, top-N; then the rollup checks of the keys, conjuncts and aggregates, or the histogram checks of the rows).
- **Tests**: `agg_preagg_rows` (24 shapes three ways on indexes with named measures, default measures, a dim over the cap, no option and the setting 7, through DML, VACUUM, write buffer, promotion, merge, an option given after the build and switched off, parallel build and scan, a rolled-back delete), `col_preagg_rows` (the minor of every segment, the corrupt-rollup decoder, verify, the cap, the option's errors) and the minor 9 step of the TAP `extension_lifecycle`; `col_refresh` (staged refresh, answers and verify at every step, the planner's counts, a changed `cube(...)` and `rollup`, minor 3, the refusals), the isolation spec `col_refresh` (a reader in a transaction, a writer and an update in flight), the TAP `col_refresh_crash` (a PANIC before the replacement, a cancel and three `kill -9` inside a refresh) and `col_refresh_compat` (an index of the real 3.0.1 library, refreshed at minor 3 and read back by it); `agg_preagg_minmax` (19 shapes three ways on indexes with and without `cube_minmax`, built under minor 6, and given the option after the build, through DML, VACUUM, promotion, merge and a parallel build), `col_preagg_minmax` (the minor of every segment, the corrupt-cube decoder, verify) and the minor 7 step of the TAP `extension_lifecycle`; `agg_preagg_wide_key` (19 shapes three ways: int8 and numeric group keys, tests of them, through DML, VACUUM, promotion, merge and a parallel build); `agg_preagg` (regress: 21 shapes on a default, an explicit-cube and a `preagg = 'off'` index through build, update, delete, VACUUM, write buffer, promote, merge, parallel build, parallel scan, numeric NaN, a rolled-back delete: each shape three ways, pre-aggregates, scan of every unit and the heap, must agree; `pre` says all, some or none of the units answered), the `pa_*` fixtures of `scripts/coldiff.sh` (every variant and heap state), and the design notes rows AP01 to AP04. ## 7. On-demand refresh of the rollups (`src/col/rollup.c`)

A rollup is written when a unit is built, so `ALTER INDEX ... SET (rollup = ...)`, a new dim in the option, a measure the units were written without or an index built before 3.1 leaves units that the query could answer if they had the rollup the query reads. Waiting for the next merge is slow (a tier merge rewrites a segment when its tier fills) and `REINDEX` rewrites everything; the index learns from its readers instead.

- **Request.** A `SiftAgg` that scans an exact unit only because its rollup is missing, was written with other dims, or lacks a measure the query reads (`Units Without The Rollup` in `EXPLAIN ANALYZE`) records the segment of the unit, once per segment and generation, in a bounded queue in shared memory (64 segments; a named DSM segment, no `shared_preload_libraries` needed; a full queue drops the request and counts it). `Rollup Refresh Queued` shows how many units of the query asked. The SELECT writes no page and takes no lock the query did not take: it works in a read-only transaction; a parallel worker asks for the units it scans and the leader adds its counts to the EXPLAIN; a hot standby never queues (`RecoveryInProgress()`) and the queue of a standby stays empty. The result of the query does not change: the unit was scanned, as before.
- **Refresh.** A background worker (one per database, started at the first request, launched at most every 2 s, at most 8 databases at a time) takes a queued segment and rewrites it as a merge of that segment alone does (`sift_col_merge_segments` with `n = 1`, the pre-aggregate options the index has now), under the maintenance lock, and replaces the old segment by the new one with the atomic directory update of every merge. So: VACUUM, merges and promotion wait on the maintenance lock as they do for each other, readers and writers do not (a reader keeps reading the old segment through its snapshot of the directory; a writer's rows are in the write buffer or in other segments); a request for a generation that is no longer in the directory (a merge replaced it first) is skipped and counted; a crash before the replacement leaves the old segment and the orphaned new one for the sweep (test `col_rollup_ondemand`: a `PANIC` after the new segment is written, then `col_verify`, the same segments, the same answers, and the request served when asked again). The refresh granularity is the segment (its units are one file): a segment of a `CREATE INDEX` is the whole table of one build worker, and rewriting it also rewrites the units that already had their rollup.
- **What is not asked for.** Units that a refresh would not change: dirty units (a page not all-visible, a dead row: they are scanned for another reason, and the next merge rewrites them), units of a minor 3 segment (the refresh would write minor 4, which a 3.0 reader refuses), any server with `sift.col_format_minor = 3`, a unit whose explicit rollup exceeded the cap (the refreshed segments are remembered by index, generation and options, so the same segment is not rewritten again for it; the memory is lost at a restart, which costs one more rewrite per segment), an index with `rollup_on_demand = false`, a session with `sift.col_rollup_on_demand = off`.
- **Switches.** `sift.col_rollup_on_demand` (on, per session), the index option `rollup_on_demand` (true, `ALTER INDEX ... SET`), `sift.col_rollup_worker` (on; off leaves the requests in the queue for `sift.col_rollup_refresh(index)`, which serves them in the calling session and returns the segments rewritten: the way to refresh on a schedule, or in a test).
- **Refresh of every segment on request: `sift.col_refresh(index [, max_segments])`** (`src/col/rollup.c`; `refreshed`, `remaining`). `ALTER INDEX ... SET (preagg, rollup, cube_minmax)` changes what the units written afterwards hold; the call rewrites the segments written before, so that the index does not wait for queries to ask (the on-demand refresh covers rollups only) or for a `REINDEX`. A segment is stale when a header-only census of the cube and element blobs of its units (`sift_cpagg_census`, no chunk read) finds a dim, a measure set (exactly the named ones with `cube(...)`), a rollup list or rollup dims (exactly the named ones with `rollup(...)`), or min and max that the options and `sift.col_format_minor` do not ask, or when a section no unit holds is one every unit can: a dim of `cube(...)` whose values lie in a range, or whose dictionary has the entries, of its group cap, a default dim of at most 32 groups, the dims of `rollup(...)`, the default rollups in a segment of minor 3. A unit over a cap or a byte budget has none, as it did when it was written, and is not a reason to rewrite. Each stale segment is rewritten as the merge of it alone (the path of the on-demand refresh: the same rows, dead ones dropped, the same answers) and replaces the old one in one WAL-logged directory change under the maintenance lock, which readers and writers do not wait for (the call holds `RowExclusiveLock` on the index, the lock of an insert, and nothing heavier); the new segment is written before the old one is released, so a cancel or a crash (`kill -9` included) leaves the segments done and the one in hand as it was, and the call made again does the rest, a segment rewritten being current. `max_segments` bounds the rewrites of a call (NULL: all, 0: only count what is stale). A segment of a minor above `sift.col_format_minor` is left as written (a rewrite would drop what only that minor holds: at 3 the index stays what 3.0 reads, and a 3.0.1 library verifies and answers from the refreshed segments); a rewritten one is written at the setting. The space of the old segments is reused after `VACUUM`, as after any merge, so the file holds up to one more copy of the index until then. A server remembers the segments it refreshed (the queue's memory) and does not rewrite them again for a unit that cannot hold a section. Not on a hot standby (it replays the rewritten segments). Measured below.
- **What the planner counts.** The memoized statistics of the index's segments (read again when a segment, `preagg`, `rollup`, `cube_minmax` or `sift.col_format_minor` changes) also count the units that hold the histogram of each dim, with min and max, and the rollup of each list; `SiftAgg` is priced for the answers from pre-aggregates on that share of the units (`preagg_share`), so an index that is half refreshed costs between the two, and a dim that no unit holds (a column with too many values) no longer counts as answered from the cube. Cost of the min/max `GROUP BY` after 0, 1, 2, 3 steps of the refresh and when done, 25,000 / 50,000 / 100,000 / 200,000 rows: 546 / 543 / 537 / 534 / 527, 564 / 556 / 547 / 538 / 529, 602 / 585 / 568 / 551 / 534, 676 / 664 / 645 / 613 / 543.
- **Time and size of the refresh**: adding min and max to every segment of 25,000 / 50,000 / 100,000 / 200,000 rows takes 23 / 36 / 50 / 81 ms (one segment 8 / 12 / 17 / 15 ms, the rest 15 / 24 / 33 / 66 ms) and removing them 17 / 32 / 50 / 70 ms, a rebuild with the option 24 / 33 / 44 / 76 ms (offline). The index grows 7.5 / 16.4 / 15.2 / 17.3 kB of pre-aggregates over 270 / 426 / 754 / 1,401 kB (3.0%, 3.8%, 0.0% by page, 1.8%). The `GROUP BY kind` with `min`/`max` of an `int8` and a `numeric(10,2)` takes 0.6 / 1.2 / 1.5 / 3.3 ms scanned and 0.18 / 0.13 / 0.30 / 0.24 ms from the groups after it (the normal plan 4.3 / 7.7 / 14.1 / 29.7 ms). Time grows with the rows of the segments rewritten.
- **Observation.** `sift.col_rollup_state` (requested, refreshed, skipped, dropped, queued, refreshing: the counters of the server since it started) and `sift.col_rollup_requests` (index, segment generation, units that asked, time, state `queued` or `refreshing`); the objects are in `sql/pg_sift--3.1.sql` and `sql/pg_sift--3.0--3.1.sql`, one block at the end of each.
- **Not built.** A miss counter that advises which dims to name in `rollup` (the per-index count of the queries that scanned for a dim, the dims that would have answered most) is the next step; the requests today ask for what the option says.
- **Time to the first fast query** after `ALTER INDEX ... SET (rollup = 'items[].kind, items[].flag')` on the 1,000,000 documents (276 units, one segment, the worker on): the first query after the `ALTER` runs as before (0.05 to 0.08 s, 0 of 276 units from the rollups, 276 queued), the worker rewrites the three 8 MB segments (about 0.7 s each) and the query that follows answers all 276 units from the rollups **1.9 to 3.1 s after the `ALTER`** (three runs; the queries polled every 100 ms, each in its own transaction: a transaction that began before the replacement keeps scanning, because the new segment is newer than its snapshot). `sift.col_rollup_refresh` from a session takes 1.9 s for the same three segments.

## 8. Not done, risks

- Time buckets derived inside the writer (`date_trunc` of a timestamp leaf) were rejected: `timestamptz` buckets depend on the session `TimeZone`, month arithmetic is the host's. A leaf that holds the expression (as the benchmark index does) is the dimension; for time-clustered tables the zone cover test already answers units inside one month from the unit sum.
- The top-level cube has depth 1 (one dimension per histogram) and, unless the index has `cube_minmax`, no per-group `min/max`; the lists have the full rollup (section 2). No float variance, no sketches. A dimension over the cap in a unit silently has no histogram there: the consumer must scan that unit (it does, `unit_hist` false).
- Format minor 2 must merge with other tracks' bumps (take the highest) and `REINDEX`; the cube costs about +4% serial build CPU and 1.1% bytes (2.4 kB per unit; the budget caps it at 2% of the unit).
- Element rollups are not written by a minor 3 writer and are refused by a 3.0.x reader like every minor 4 segment. Tests: `col_preagg_elem` (every histogram and rollup against `jsonb_array_elements` / `jsonb_each` after build, DML, VACUUM, promote, merge, parallel REINDEX, minor 3, 4 and mixed indexes, options), `agg_preagg_elem` (25 shapes three ways, plus the unit counts), `agg_preagg_rollup` (34 shapes, dims in any subset, filters, min/max, maps), `agg_preagg_elem_parallel` (Gather over a partial `SiftAgg` on a mixed index), `col_rollup_refresh`, the `pa_elem_*` and `pa_roll_*` fixtures of `scripts/coldiff.sh`, the crash and replica TAPs.
- **Numeric measures of a jsonb path.** A rollup measure is a `smallint`, `integer`, `bigint`, `numeric(p,s)`, `real` or `double precision` leaf; a jsonb path has no numeric type (the types of `paths` are `bool, int2, int4, int8, float4, float8, text, astext`), so `sum(e.amount)` of `jsonb_to_recordset(...) e(amount numeric)` is scanned and a jsonb amount is a measure only as `int*` or `float8`. Why there is none, concretely: PostgreSQL's `numeric` sum has the display scale of the widest input (`1.5 + 2.5 = 4.0`, `1.50 + 2.50 = 4.00`), jsonb keeps the scale of every value as it was written (`1.5` and `1.50` are two values), and the shredder renders numbers with `numeric_normalize` (no exponent, no trailing fraction zeros): a column of scaled integers with one declared scale `s` (what a heap `numeric(p,s)` leaf is) would give `4.00` for a group whose values were all written with one decimal, and the pushdown must return exactly what the normal plan returns, text included. Two ways out. (a) *Declared scale, flag only*: a path type `numeric(p,s)` whose slot holds the value times `10^s` only when the jsonb value has exactly `s` fractional digits and fewer than `p` digits in all; any other value (`3`, `3.5`, `3.123`, an exponent) is an overflow slot, as an out-of-range number is today, and the unit or the query that reads it scans. This is the case of money written by one producer (`12.50`, `3.00`); it needs the grammar `numeric(p,s)` in `paths` (and in the canonical spec the segment stores), the scale check in the shredder's number path and the typed planner mapping, no change of the chunk or sidecar formats: the numeric leaf and its int128 sums exist for heap columns, so it fits column format minor 4. (b) *Scale tracked per value*: keep each value's own `dscale` (a nibble per slot, like the type tag) and the maximum per rollup tuple, so that any mix of scales is answered with PostgreSQL's display scale; this is a chunk flag, a rollup field and a verify rule, i.e. a minor 5. Recommendation: (a) in 3.1.x or 3.2, with a build-time count of the overflowing values in `sift.col_index_info` so that an index on data that does not keep one scale is visible. Not implemented here: it adds a path type to the shredder, the planner and `col_verify`, which is the size of the element rollups again and shares none of their code.
- Churn: a unit with a dead row (its liveness bit cleared by VACUUM) or a page that is not all-visible answers from its rows, never from the sums; the correctness never changes. The way back needs no `REINDEX`: `VACUUM` rewrites a lone segment more than `dead_rewrite_pct` percent dead (`sift_col` option, default 10, `ALTER INDEX ... SET`; 100 never; the BM25 index keeps 50), `sift.col_promote` and the worker give the rows written since stored units, and the tier merge rewrites the rest (`col_preagg_maint`). Below the threshold a segment keeps its dirty units on purpose: uniform deletes dirty every unit at 0.1% dead, and each rewrite costs the whole segment. PostgreSQL's `VACUUM` skips the index and leaves the pages not all-visible when few tuples are dead (`INDEX_CLEANUP auto`, under 2% of the pages): units come back at the first `VACUUM` that vacuums the index, as for index-only scans. A `sift_table` has no pre-aggregates yet, so nothing of this applies to it.
- Dictionaries are per segment, parallel builds have one per participant: translation by value is per segment, not per unit.

## 10. Superunits: one summary for a group of units (column format minor 12, reloption `superunit`, default 16)

Answering from the pre-aggregates costs a read, a decode and a fold for every exact unit: 5 to 16 microseconds a unit, so a whole-table aggregate over N rows is linear in the number of units (sections 6 and 9). A **superunit** is `superunit` (2 to 256) consecutive units of a segment with the merged sums and cube of the group stored once more, so that the group is one read, one decode and one fold. The reloption `superunit` (default 16 since 3.3; 0: none) makes the segments written from now on column format minor 12 (under `sift.col_format_minor = 12`, the default; 10 and below write what they wrote before), and an index with `superunit = 0` writes the bytes it wrote before. 16 is the default because it costs +1.0% of the index (200,000 rows, 53 units: whole-table `count`/`sum` 0.26 to 0.37 ms by the units, 0.05 to 0.08 ms by the groups; groups of 64 cost +0.8% and cut by a range predicate fall back to their units more often; groups of 4 to 8 cost +1.3% to +1.5%), the write path (insert, promotion, merge, UPDATE and VACUUM CPU) is inside the noise, and the queries a summary cannot answer (a float sum, a filter on a column the cube lacks, `count(DISTINCT)`) stay within 10% of the plan without it. The one cost seen is a range query on a table of fewer than 16 units (2 units: 0.10 to 0.13-0.15 ms), the exactness test of a group that never forms.

- **What is stored.** After the element cubes and the small-set summaries, in the `COLP` directory of version 4 (`SuperHeader`, `src/col/seg_int.h`): the page mask of every unit (32 bytes: the pages of its superblock that hold rows, so that the exactness of a unit is decided without reading its record), for every INT leaf and group the merged `count`, `nnull`, `min`, `max`, exact `sum` and `sum of squares` (64 bytes), and per group the merged cube: the dims every unit of the group holds with the same measures, the groups added up by key (text by segment code, as in a unit), counts, non-NULL counts, exact sums and, with `cube_minmax`, the smallest and largest values. A float measure is left out (its sum depends on the order of the additions, which the units fix) and so is a dim with more than 4,096 groups in the group; a leaf with an overflow value in a unit has no summary for that group. List rollups are not merged. Written by the writer's own `sift_cpagg_super_leaf` / `sift_cpagg_super_cube` from the stored units' bytes, and recomputed by `sift.col_verify` with the same functions, so the stored bytes are checked byte for byte; the reader refuses an unknown flag, a record that is not what a group of its size can hold, sizes that do not add up, and a directory out of order.
- **When a group answers.** The scan hands over a group of a segment as one unit (`Superunits` in `EXPLAIN ANALYZE`) when every unit of the group passed the zone tests and is exact on its own (docs/COL-PREAGG.md section 4, tested for each unit in the order of `unit_allvisible` then `unit_clean`: the all-visible bits, the directory, the liveness) and the whole group lies inside the range the scan was given. The consumer then applies the same rules as for a unit, to the merged zone (a predicate on another column must cover the merged `min..max`) and the merged cube. When it cannot answer (a predicate cuts through the group, a measure or dim the merge left out, a float sum), the group is split and its units are read one by one, as without the option; after four splits and no answer in a scan it stops asking. The answers of the three ways (summaries, units, plain plan) are the same rows: the integer and numeric sums are exact whatever the order, counts and sums of the groups are those of the units added up. `sift.agg_super` (on) turns the use off.
- **Cost, size.** The block is 0.5% to 1.5% of the index (200,000 rows, 1,024 rows a unit: +1.7% of the index with groups of 16 (sidecar 633,232 bytes without, 707,776 with), +1.0% with groups of 64 (678,912); 400,000 rows: sidecar 1,240,824 bytes without, 1,361,936 with groups of 16, 1,308,152 with groups of 64) and is built from the units' own bytes at the end of the segment (no second pass over the rows). Parallel scans take the superblocks in ranges of `superunit * 4 * segments`, so that a group fits in a range; a group cut by the end of a range is read as units.
- **Scaling.** A scan of the pre-aggregates over N rows is O(units); with groups of F units it is O(units / F) reads, decodes and folds plus, for each unit, the exactness test (the all-visible bits of its pages against the stored page mask, one liveness bit), which the rows below measure at under 0.1 microsecond a unit with groups of 64.

- **Not done.** A second level (groups of groups: a tree whose range query combines O(log units) nodes), merged element rollups, merged float measures in an order-independent form, and the groups for a `sift_table` (its provider has no sidecar callbacks).
- **Tests.** `agg_preagg_super` (20 shapes three ways on an index with groups of 4, of 2, of 256, with no option and built under minor 7, through DML, VACUUM, promotion, merge, an option set later and a parallel build), `col_preagg_super` (segment minors, byte for byte damage of the block, verify, merge, delete and VACUUM), the minor 8 step of `extension_lifecycle`.

pg_sift 5.0.2: a patch release of 5.0.1 that closes crashes and a runaway disk use that merges and planning could cause, makes the temporary files of key-range builds several times smaller (and refuses a build whose files cannot fit), makes the advice to `REINDEX` a connected index exact, and lowers the memory of the automatic `key_cut` decision, column merges, the tombstone log and idle backends. The library only: the extension version moves to 5.0.2 with an empty update script, no format changes, nothing is rebuilt.

## Highlights

- **Merges end.** A `sift_col` index whose scope key has more rows than one segment holds, or whose merge writer cuts at a lower memory than the writers of its inputs used (a lowered `maintenance_work_mem`), was merged again at every step of `sift.col_merge`, of the steps that follow `CREATE INDEX CONCURRENTLY` and `REINDEX INDEX CONCURRENTLY`, and of the maintenance worker: each pass wrote the segments again and the index grew until the disk was full. A merge now ends when its output is the end state of the tiers, and a step that makes no fewer segments than it read ends the steps.
- **Crashes closed.** Planning a top-N (`ORDER BY .. LIMIT` over one table) read paths that `add_path` had freed, and the planner crashed (signal 11) on some memory layouts. Planning an aggregate on a `sift_col` index read index metadata from cached state that a reload of the entry frees. The sub-plans of the joins that an aggregate scan reads (a parallel sub-select under a lateral join) are shut down with the scan, which PostgreSQL 19 asserts on, and a backend that spilled the tombstone log of a `sift_table` closes its temp files before its shared-memory exit, which PostgreSQL 19 also asserts on. `sift.table_ddl_check` opens the table of an `ALTER TABLE` or `RENAME COLUMN` only after the statement has locked it. Building a `sift_col` index over `jsonb` array paths no longer reads past the end of a bitmap, so the layout of a leaf no longer differs between runs.
- **Partitioned indexes are refused, not read.** `sift.promote`, `sift.index_format`, `sift.col_promote` and the other maintenance functions and inspectors raise an error for the parent index of a partitioned table, which has no storage, where they went on to read a metapage that does not exist.
- **Builds by key range write much smaller temporary files, and say when they cannot.** The files of a `CREATE INDEX` or `REINDEX` of a `key_cut` index hold columnar chunks (the codecs of the index, one dictionary for the strings of a range, zstd or lz4 when a sample shrinks by a fifth): on 200,000 rows of 12 columns and four path sets, 66.5 bytes a row become 8.3 for repeating values and 195.4 become 91.1 for hash-like values. A build whose rows do not fit `temp_file_limit` or half the free space of the temporary tablespace is refused before the first file is written (`54000`, with a hint) instead of writing overlapping runs without a word. `CREATE INDEX CONCURRENTLY` and `REINDEX CONCURRENTLY` of a `key_cut` or scoped index are built by one process, end with the key in one unit, and their second pass files the rows by key range (about 100 to 110 bytes a row of temporary files at 1 MB of `maintenance_work_mem`, from 150 to 216).
- **Segments follow the rows, not the estimate.** `CREATE INDEX` and `REINDEX` of a `sift_col` index without `key_cut` cut their segments by the rows the heap pages have given so far: a table that was never analyzed, or whose `reltuples` is far too high, is no longer cut into segments several times larger than its rows.
- **`REINDEX recommended (stale connection)` is exact for a connected index.** The stamps of the child segments and the metapage keep the insert horizon of the parent index in bits that were reserved (no format minor, no byte more; a 5.0.1 library reads the same files and ignores them). Parent rows inserted and then merged into the parent's base segment, and rows inserted into a `key_cut` parent, advise once they reach `sift.col_connect_refresh_pct` percent of the parent rows. A child stamped by an earlier release is told only by the keys the journal records until it is written again.
- **Memory.** The automatic `key_cut` decision holds `maintenance_work_mem` and a constant, not up to 400,000 sampled rows; a `key_cut` merge opens each input when its rows are reached, so its dictionaries follow the largest input and not the sum; reading a compressed dictionary of strings holds one copy at its peak, not two; the fold of the tombstone log keeps its keys within `sift.tomb_log_limit` and the batch of log entries it reads is a quarter of the limit, so a limit below 64 kB is kept; a scan with `track_changes` no longer counts the whole log at every read; a backend that only reads an index keeps no insert context for it; the cache of an aggregate over an expression of a numeric column and a lookup no longer restarts at every few values at the default `work_mem`.
- **Aggregates over a lookup cost less.** A `sum` or `avg` of numerics over the values of a lookup adds a value that occurred once as it is, instead of multiplying it by a numeric one and calling PostgreSQL's numeric functions twice for every distinct value and group.

## New and changed settings

- **`sift.col_build_key_ranges` (removed).** A serial `CREATE INDEX` or `REINDEX` of a `key_cut` or `key_order` index on a table of more than one run, with a numeric key of three values or more, always writes runs that do not overlap in the key; there is no off mode. A `SET` of it once the library is loaded fails with `invalid configuration parameter name`; a configuration file, `ALTER SYSTEM`, `ALTER DATABASE` or `ALTER ROLE` entry that names it logs `invalid configuration parameter name ..., removing it` and the server starts: delete the entry.
- **The refusal for temporary files.** A key-range build whose estimated files (the packed and compressed bytes of a sample of the first run times the rows of the table) exceed `temp_file_limit` or half the free space of the temporary tablespace stops with `the rows of the build need about N MB of temporary files` (SQLSTATE 54000, a hint naming `temp_file_limit` and `temp_tablespaces`). Raise the limit or point `temp_tablespaces` at a larger disk.

## Who is affected and what to do

- **Everyone on 5.0.1 or 5.0.0** gets the fixes by replacing the library. 5.0.2 contains everything of 5.0.1 (there is no change you give up by moving) and 5.0.0 goes straight to it.
- **Update (the steps):** install the files and restart the server (a standby too, in any order: the files of 5.0.0, 5.0.1 and 5.0.2 are read by all of them). `ALTER EXTENSION pg_sift UPDATE` in each database moves the extension version to 5.0.2 and changes nothing else (`pg_sift--5.0.1--5.0.2.sql` is empty); the new library runs without it. No `REINDEX`, nothing stored is wrong. Without a restart a session keeps the library it loaded first and says `Reconnect` when it meets the new file: reconnect pooled sessions.
- **An index that grew from a runaway merge** keeps its size until you `REINDEX INDEX CONCURRENTLY` it: the disk holds both files until the swap.
- **Going back:** if you ran `ALTER EXTENSION pg_sift UPDATE`, run `ALTER EXTENSION pg_sift UPDATE TO '5.0'` in each database first; then install the files of the older release and restart. Nothing else has to be undone. An older library reads the files of this release; the advice for parent rows that came in is the one thing it does not give.

## Known limits

What this release does not bound or fix, so that the memory claims above are read for what they are:

- **Scopes that are still open.** `agg_lookup`, `col_build`, `col_merge`, `col_merge_inputs`, `col_scope_refill`, `col_write_buffer`, `col_writer_dict` and `col_writer_points` are measured ceilings, not budgets of settings (`test/mem-budgets.tsv`), and the peak of the operations listed as open in `test/mem-slope.tsv` still grows with the rows.
- **A column merge is not proven flat.** The writer of a `key_cut` merge keeps a per-row term that the test `col_merge_exact_memory` only caps.
- **The automatic `key_cut` decision reads a sample of the table.** Its memory follows `maintenance_work_mem` plus a constant.
- **A rewrite is yours to start:** an index that stays in a state `sift.col_maintenance_status` flags costs more to read than a rewritten one until you run the `REINDEX`.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 5.0.1 with the install; extension SQL 5.0.2 (`pg_sift--5.0.1--5.0.2.sql`, empty); no column format minor and no BM25 metapage minor changes. The library opens the files of 5.0.0 and 5.0.1 as they are, on a primary and on a standby, and the files of this release are read by 5.0.1.

## SQLite extension

pg_sift for SQLite 5.0.2 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 5.0.2 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-5.0.2-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.2/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.2/sqlite/CHANGELOG.md).

## MariaDB extension

pg_sift for MariaDB 5.0.2 (`sift`, a UDF library and two SQL files; a separate component from the extensions above). Rebuilt with the PostgreSQL 5.0.2 release: no change to the SQL files.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- One library per MariaDB series, because it calls the server's own symbols and refuses to load into another series: 10.11, 11.4, 11.8, 12.1 and 13.0; Linux x86-64. Each was built in the stock `mariadb:<series>` image against that server's headers and loaded into a server of the same image before release. `BUILD-INFO` in the tarball lists the server version and the glibc each library needs.
- Index format 2: an index of 3.4.0 to 3.7.0 opens as it is, nothing to rebuild.

Download `sift-mariadb-5.0.2-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it, copy `lib/<series>/libsift_udf.so` of your server's series
(`SELECT VERSION()`) into its `plugin_dir`, then `SOURCE sql/functions.sql` once per server and `sql/sift.sql` once per database (`sha256sum --ignore-missing -c SHA256SUMS`).
Documentation: [mariadb/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.2/mariadb/README.md).

pg_sift 5.0.1: a patch release of 5.0.0 that stops index builds and maintenance from blocking writers, lowers the memory of builds, merges, checks, caches and the tombstone log (most of it now follows a setting, not the rows; what does not yet is listed under Known limits), no longer rewrites a `sift_col` index by itself, and closes a set of crashes and wrong states that a dropped object, a cancel or an unusual argument could cause. The library only: the extension version moves to 5.0.1 with an empty update script, no format changes, nothing is rebuilt.

## Highlights

- **Maintenance: nothing rewrites a `sift_col` index by itself any more.** A connected child index of tens of GB was rewritten in a single transaction that lasted many hours, and the next rewrite began the moment it ended: a rewrite costs the whole index (and, for a connected child, a read of the keys of its parent), so no rule could tell when it paid. `VACUUM`, the maintenance worker, the reads that owe a rewrite and the re-decision of a key start none; rewriting a whole index is your decision, `REINDEX INDEX CONCURRENTLY`. What stays automatic is the incremental work: the promotion of the write buffer, the merge of the small segments and of the overlays, the fold of the log, `VACUUM`, and the release and compaction of the value store. `sift.col_maintenance_status` says when a `REINDEX` is worth it (below).
- **Locks: `CREATE INDEX CONCURRENTLY` and `REINDEX CONCURRENTLY` of a `sift_col` index with a `scope` or `track_changes` no longer block the writers of the table.** They hold nothing stronger than `ShareUpdateExclusiveLock`, except for a few milliseconds at the end of the build, wait for the writers that hold the table without queuing the ones that come after, and fill the scope segments in the validation pass. A concurrent build of a scope index over a relation of pairs without a journal does the same.
- **Locks: other waits that blocked every session behind them are gone.** `sift.col_value_store_compact` asks for its locks as `VACUUM` does and fails at once with `55P03` when one is held, instead of queuing every later statement behind a long transaction. Sessions that give codes to new strings in a shared value store no longer wait for each other's merge of the store's runs. A `DELETE` or `UPDATE` of a `sift_table` no longer waits for the rewrite of the tombstone log that `VACUUM` makes, and an `INSERT` whose write buffer fills no longer waits for a `COPY`.
- **Memory: builds, merges and checks hold less, and the structures below follow a setting, not the rows.** `CREATE INDEX` and `REINDEX` of a `sift_col` index free the scratch of each sorted run and merge when it ends (a scope of three entries a row built with a 2 MB run budget peaked at 207 MB at 200,000 rows and now at 33 MB); a column merge no longer keeps a string dictionary for every input segment; `sift.col_verify` and `sift.check` with `heapallindexed` hold 6 bytes a row at 1 MB of `maintenance_work_mem` where they held 130; `count(DISTINCT x)` of a text column and the cache of an aggregate over an expression stay within hash memory; an aggregate scan of the write buffers of a `sift_table` reads them one superblock (2 MB) at a time. A column merge decodes the units of its inputs through a rolling window that gives their arrays back as the rows are written, and parses and drops the dictionary of each input at its last unit instead of keeping every one until the merge ends; the segment writer of a build, a merge or a `VACUUM` keeps the entries of the order arrays (`order_array_columns`) on temporary files in sorted runs, so its memory no longer follows the rows of its segment (the runs count against `temp_file_limit`); a build no longer loads the tombstone log, and the key journal a connected or scoped index reads is streamed in blocks; the reader of a write buffer holds the records of an open segment at their size; a concurrent scoped build remembers btree probe answers within `maintenance_work_mem`; the automatic `key_cut` decision is bounded by constants, and a table with empty superblocks is decided instead of skipped; partitioned aggregate scans open each partition twice at most and keep the sources hash memory holds.
- **Memory: named scopes with exact-byte tests.** The new memory scopes (`col_merge_window`, `col_writer_spool`, `col_writer_order`, `col_conn_changed`, `col_scope_probe`, `col_key_cut_decision`, with `col_tomb_log` and `col_write_buffer` tightened) assert the bytes a structure holds at small, known steps of rows, and the per-row term must be zero or fit a stated ceiling; `col_merge_exact_memory` fails when a merge keeps 64 more bytes of every index row. The scopes that are not closed are listed under Known limits.
- **Memory: caches and idle backends.** A backend no longer keeps the lookup keys of every write buffer it saw, the dictionaries of segments a merge retired, or the strings of the shared value store of an index that was dropped; a pooled backend that runs a mix of statements settles in a band of about 100 to 125 MB instead of growing with the number of statements (`mem_idle_series`).
- **Crashes and wrong states closed.** A cancel or an error right after the last directory switch of a `sift` (BM25) promotion or merge no longer frees blocks the directory still lists (`Block N is referenced twice`). A relation, function or namespace dropped while a statement reads it ends with the error of a missing object, not a segmentation fault; the inspectors and functions that take a relation or a NULL argument raise an error that names it (`42P01`, `42809`, `22004`) instead of crashing or saying the index is corrupted. A grouped query over a table with a `sift_col` index joined to a subquery whose join key is computed over an outer join crashed the backend while it was planned (5.0.0 only), and a grouped partitioned query with `GROUPING SETS` and a `NOT IN` subquery failed with `PlaceHolderVar found where not expected`. A reader that built a write buffer's references from the heap and ended in an error left the slot owned until the backend exited; the other readers waited for it and polled. The damaged-index registry no longer puts a damaged index back in service when it is full.
- **Maintenance workers are quieter.** A worker with nothing to do leaves after two looks, a request that arrives while one leaves is no longer dropped, the fold of the log is asked for only when a fold can clear marks, a failed or shut-down merge returns its blocks to the index, and the message that no background worker slot was free is logged once an hour for each job and names the jobs that hold them.

## New and changed settings

- **`sift.col_auto_merge_max_active` and `sift.col_auto_merge_max_workers` (removed).** They bounded the automatic rewrites, which are gone. A configuration file or `ALTER SYSTEM` entry that still names them logs `invalid configuration parameter name ..., removing it` and the server starts; delete the entry. `sift.col_auto_merge` (default on) still controls the incremental work, and `sift.col_auto_merge = off` stops it.
- **`sift.backend_cache_kb` (new, default 256 MB).** The total a backend keeps in its caches of parsed dictionaries, `sift` segment bytes, joined-table rows, the strings of shared value stores and the facts of partitions, dropping the least recently used entry of any of them. The separate limits added up to about 480 MB a backend, which a pool of connections multiplied. `-1` leaves each cache to its own setting; lower it on a server with many backends, raise it for a few backends that join large tables. No `REINDEX`: the setting is read when a cache admits an entry.
- **`sift.tomb_log_limit` (default 64 MB, was 8 GB).** The memory a backend keeps of the tombstone log of a `sift_table` (64 bytes for each row deleted or updated since the last `VACUUM`, the entries of its own statement included). The entries past the limit are kept in sorted runs on temp files, so a read of a log of any length and a `DELETE` or `UPDATE` of any number of rows complete (the error past the limit of 5.0.0 is gone); the cost is a block read for each run when an entry is not in memory, and temp files within `temp_file_limit`. A value you set yourself stays as you set it.

## When to `REINDEX`

`sift.col_maintenance_due(index)` names the reason a rewrite would pay (`stale connection`, `stale scope`, `dirty units`, `fragmented units`, `key ranges overlap`, a value store with garbage) and `SELECT * FROM sift.col_maintenance_status('idx')` shows it in `rewrite_due`, with `blocked_by` saying `REINDEX recommended (reason)`. The reasons `write buffer rows`, `overlay units` and `scope segments` are met by the incremental work and recommend nothing. `stale connection` is said for a connected index only when parent keys were deleted or changed, or parent rows were inserted, beyond `sift.col_connect_refresh_pct`: updates of the parent's other columns and the merges, rewrites and `VACUUM` of the parent index no longer make it appear (before, a few rounds of 3% to 8% of the parent rows updated and merged made it appear in nearly every round); parent rows that a merge already put into the parent's base segment are not advised. When the parent index is cut by key (`key_cut`) no inserted parent rows are counted (a key_cut merge rewrites only the partitions it touches, so the partitions carry different stamps and no stamp tells a rewritten row from an inserted one): only deleted or changed keys advise, and a child whose key_cut parent grew through inserts alone is not advised; reads still join for those keys and answer as the normal plan does. This is a limit of this release. Nothing is logged, and nothing is wrong meanwhile: reads answer correctly from the rows of the units and the keys of the parent; they only cost more than a rewritten index would.

- Run `REINDEX INDEX CONCURRENTLY idx` in a window of your choosing, for example after the nightly `VACUUM`: the disk holds both files until the swap, and a connected child index reads the keys of its parent once. `sift.col_maintain(index)` rewrites in place and holds the maintenance lock meanwhile.
- A reason that stays on a large index is not an emergency: plan the `REINDEX` for the quietest hours, one index at a time, and watch the disk for twice the index.
- The metapage is that of 5.0.0: a 5.0.0 index opens and verifies unchanged, and 5.0.0 opens the indexes of this release.

## Who is affected and what to do

- **Everyone on 5.0.0** gets the fixes by replacing the library. An index that 5.0.0 would have rewritten by itself is now left as it is, and the status recommends the `REINDEX`.
- **Update (the steps):** install the files and restart the server (a standby too, in any order: the files of 5.0.0 and of 5.0.1 are read by both). `ALTER EXTENSION pg_sift UPDATE` in each database moves the extension version to 5.0.1 and changes nothing else (`pg_sift--5.0--5.0.1.sql` is empty); the new library runs without it. No `REINDEX`, nothing stored is wrong. Without a restart a session keeps the library it loaded first and says `Reconnect` when it meets the new file: reconnect pooled sessions.
- **Going back:** if you ran `ALTER EXTENSION pg_sift UPDATE`, run `ALTER EXTENSION pg_sift UPDATE TO '5.0'` in each database first; then install the 5.0.0 files and restart. Nothing else has to be undone. 5.0.0 keeps the whole log in memory and fails with `54000` past `sift.tomb_log_limit`: raise the setting (its default there is 8 GB) if you lowered it for 5.0.1.

## Known limits

What this release does not bound or fix, so that the memory claims above are read for what they are:

- **A column merge is not proven flat.** The scope `col_merge` is still open in `test/mem-budgets.tsv`: 36 to 47 MB on 1,600,000 rows at 1 and 4 MB of `maintenance_work_mem`, and 177 MB in a parallel worker of a `key_cut` build of 1,600,000 rows at the default. The decoded units sit in the closed scope `col_merge_window` (`maintenance_work_mem` plus 24 MB), but the writer of a `key_cut` merge keeps a per-row term that the test `col_merge_exact_memory` only caps (444 bytes a row, against 1 for a plain merge, measured between 8,000 and 40,000 rows). No test shows a `key_cut` merge flat at any size.
- **The automatic `key_cut` decision reads a sample of the table** and its memory is bounded by constants, not by `maintenance_work_mem`: 534 MB at the most (`col_key_cut_decision`, test `col_key_cut_sample_small`).
- **Other open scopes:** `col_build` (the rows, runs and segment writer of `CREATE INDEX`: 77 MB at 4 MB of `maintenance_work_mem` on 400,000 rows and 136 MB at the default), `col_scope_refill`, `col_write_buffer` (up to 93 MB in its crash test) and `agg_lookup` (the table of a lookup join follows the rows of the lookup table). `test/mem-slope.tsv` lists the operations whose peak still grows with the rows of the table (merge, promotion, `VACUUM` of churned tables, `CREATE TABLE AS` of a `sift_table`, among others): their ceilings are the measured ones, not a bound.
- **An index with a `key_cut` parent that only grew by inserts is not advised for a `REINDEX`** (see above); reads stay correct.
- **Planner, default settings:** in the plan gate's stock lane, two shapes of an aggregate over an expression of a numeric table column and a looked-up column (`dimexpr_dim_c`, `dimexpr_two`) fall outside their instruction band, in 5.0.0 as well; their answers are the same.
- **A rewrite is yours to start:** an index that stays in a state `sift.col_maintenance_status` flags costs more to read than a rewritten one until you run the `REINDEX`.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 5.0.0 with the install; extension SQL 5.0.1 (`pg_sift--5.0--5.0.1.sql`, empty); no column format minor and no BM25 metapage minor changes. The library opens the files of 5.0.0 as they are, on a primary and on a standby, and the files of this release are read by 5.0.0.

## SQLite extension

pg_sift for SQLite 5.0.1 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 5.0.1 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-5.0.1-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.1/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.1/sqlite/CHANGELOG.md).

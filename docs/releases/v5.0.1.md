pg_sift 5.0.1: a patch release of 5.0.0 that ends a loop of full rewrites of connected indexes, stops index builds and maintenance from blocking writers, bounds the memory of builds, merges, checks, caches and the tombstone log by the settings that name them, and closes a set of crashes and wrong states that a dropped object, a cancel or an unusual argument could cause. The library only: the extension SQL stays at 5.0, no format changes, nothing is rebuilt.

## Highlights

- **Rewrites: a connected `sift_col` index no longer rewrites itself in full again and again.** In 5.0.0 an index connected to a parent index (`connect`) could report `stale connection` after almost every round of updates and maintenance of the parent, and its automatic rewrite started again the moment the last one ended; a rewrite of hours ended with its reason due, each pass held the blocks of the one before, and the file grew by a copy for each pass (an index of 11 GB reached 46 GB over more than ten hours). Two causes are closed: the rule that counts the parent rows inserted since a segment's stamp counted every row that a merge of the parent index wrote again (it now leaves out the largest parent segment), and the next automatic rewrite now waits as long again as the last took (`sift.col_auto_rewrite_backoff`) and never starts a step over a size (`sift.col_auto_rewrite_max_size`).
- **Locks: `CREATE INDEX CONCURRENTLY` and `REINDEX CONCURRENTLY` of a `sift_col` index with a `scope` or `track_changes` no longer block the writers of the table.** They hold nothing stronger than `ShareUpdateExclusiveLock`, except for a few milliseconds at the end of the build, wait for the writers that hold the table without queuing the ones that come after, and fill the scope segments in the validation pass. A concurrent build of a scope index over a relation of pairs without a journal does the same.
- **Locks: other waits that blocked every session behind them are gone.** `sift.col_value_store_compact` asks for its locks as `VACUUM` does and fails at once with `55P03` when one is held, instead of queuing every later statement behind a long transaction. Sessions that give codes to new strings in a shared value store no longer wait for each other's merge of the store's runs. A `DELETE` or `UPDATE` of a `sift_table` no longer waits for the rewrite of the tombstone log that `VACUUM` makes, and an `INSERT` whose write buffer fills no longer waits for a `COPY`.
- **Memory: the memory of builds, merges and checks follows the setting, not the rows.** `CREATE INDEX` and `REINDEX` of a `sift_col` index free the scratch of each sorted run and merge when it ends (a scope of three entries a row built with a 2 MB run budget peaked at 207 MB at 200,000 rows and now at 33 MB); a column merge no longer keeps a string dictionary for every input segment; `sift.col_verify` and `sift.check` with `heapallindexed` hold 6 bytes a row at 1 MB of `maintenance_work_mem` where they held 130; `count(DISTINCT x)` of a text column and the cache of an aggregate over an expression stay within hash memory; an aggregate scan of the write buffers of a `sift_table` reads them one superblock (2 MB) at a time.
- **Memory: caches and idle backends.** A backend no longer keeps the lookup keys of every write buffer it saw, the dictionaries of segments a merge retired, or the strings of the shared value store of an index that was dropped; a pooled backend that runs a mix of statements does not grow.
- **Crashes and wrong states closed.** A cancel or an error right after the last directory switch of a `sift` (BM25) promotion or merge no longer frees blocks the directory still lists (`Block N is referenced twice`). A relation, function or namespace dropped while a statement reads it ends with the error of a missing object, not a segmentation fault; the inspectors and functions that take a relation or a NULL argument raise an error that names it (`42P01`, `42809`, `22004`) instead of crashing or saying the index is corrupted. A grouped query over a table with a `sift_col` index joined to a subquery whose join key is computed over an outer join crashed the backend while it was planned (5.0.0 only), and a grouped partitioned query with `GROUPING SETS` and a `NOT IN` subquery failed with `PlaceHolderVar found where not expected`. A reader that built a write buffer's references from the heap and ended in an error left the slot owned until the backend exited; the other readers waited for it and polled. The damaged-index registry no longer puts a damaged index back in service when it is full.
- **Maintenance workers are quieter.** A worker with nothing to do leaves after two looks, a request that arrives while one leaves is no longer dropped, the fold of the log is asked for only when a fold can clear marks, a failed or shut-down rewrite returns its blocks to the index, and the message that no background worker slot was free is logged once an hour for each job and names the jobs that hold them.

## New and changed settings

- **`sift.backend_cache_kb` (new, default 256 MB).** The total a backend keeps in its caches of parsed dictionaries, `sift` segment bytes, joined-table rows, the strings of shared value stores and the facts of partitions, dropping the least recently used entry of any of them. The separate limits added up to about 480 MB a backend, which a pool of connections multiplied. `-1` leaves each cache to its own setting; lower it on a server with many backends, raise it for a few backends that join large tables. No `REINDEX`: the setting is read when a cache admits an entry.
- **`sift.col_auto_rewrite_backoff` (new, default 10).** The automatic rewrite of a `sift_col` index waits this many times as long as the last one took before it starts again (at least the maintenance naptime), so rewriting takes under a tenth of the time whatever a rewrite costs. *Gain:* five rounds of a rebuilt parent index (a connected index due after each) made 5 automatic rewrites without the wait and 1 with it. *Impact:* none on size, builds or writes: only the next automatic rewrite is delayed, and the churn waits in the write buffer, the overlays and the reads that patch it. *Why 10:* a rewrite of ten hours or ten seconds ends with its reason due again, because the changes during it count against its own stamps; a tenth bounds the time spent rewriting at under 10%. *Off:* `0` removes the wait (`ALTER SYSTEM` or `ALTER DATABASE`; `sift.col_maintain(index)` is never held by it). `sift.col_maintenance_status` names the wait in `blocked_by`.
- **`sift.col_auto_rewrite_max_size` (new, default 2048 MB).** The automatic rewrite does not start a step that writes more than this size; the step is left to `sift.col_maintain(index)` in a quiet window, and one `LOG` line an hour names the command. *Gain:* a step over the size is not started (a 4 MB index with a size of 1 MB: no step, generation unchanged). *Impact:* a very large step of the automatic rewrite does not run on its own; it covers the steps that take every segment of an index, not the partitions of a rolling pass, the rewrite after a build or `sift.col_maintain`. *Why 2 GB:* one step is one transaction that holds back the blocks the last rewrite freed and the vacuum horizon until it ends, and a multi-hour step grew an index from 18 to 46 GB; 2 GB is about an hour at the rate the rewrite runs. *Off:* `0` removes the limit.
- **`sift.tomb_log_limit` (default 64 MB, was 8 GB).** The memory a backend keeps of the tombstone log of a `sift_table` (64 bytes for each row deleted or updated since the last `VACUUM`, the entries of its own statement included). The entries past the limit are kept in sorted runs on temp files, so a read of a log of any length and a `DELETE` or `UPDATE` of any number of rows complete (the error past the limit of 5.0.0 is gone); the cost is a block read for each run when an entry is not in memory, and temp files within `temp_file_limit`. A value you set yourself stays as you set it.

## Who is affected and what to do

- **Everyone on 5.0.0** gets the fixes by replacing the library.
- **Update (the steps):** install the files and restart the server (a standby too, in any order: the files of 5.0.0 and of 5.0.1 are read by both). `ALTER EXTENSION pg_sift UPDATE` is not needed and changes nothing: the extension SQL stays at 5.0. No `REINDEX`, nothing stored is wrong. Without a restart a session keeps the library it loaded first and says `Reconnect` when it meets the new file: reconnect pooled sessions.
- **Going back:** install the 5.0.0 files and restart; nothing has to be undone. 5.0.0 keeps the whole log in memory and fails with `54000` past `sift.tomb_log_limit`: raise the setting (its default there is 8 GB) if you lowered it for 5.0.1.

## If an index rewrites itself without end (operators)

- **Emergency stop:** `ALTER SYSTEM SET sift.col_auto_merge = off` and `SELECT pg_reload_conf()` (server or database level; a session `SET` is ignored by the worker). It stops the requests of `VACUUM` and of reads and the worker's next start; it does not stop a rewrite that is already running.
- **Cancel the running rewrite:** `pg_cancel_backend(pid)` of the `sift rewrite of ...` backend is safe. A rewrite is one transaction and the directory switches at the end of a step, so the index keeps serving from its old segments and is never wrong; the blocks the cancelled pass wrote are not listed and are returned by the next `VACUUM` of the table (or the next rewrite worker); `sift.col_space(index)` shows `used_blocks` against `relation_blocks`.
- **Then:** with 5.0.1 installed the index waits between rewrites and refuses a step over 2 GB; run `SELECT sift.col_maintain('<index>')` yourself in a quiet window when you want the full rewrite, then `ALTER SYSTEM RESET sift.col_auto_merge`. `ALTER INDEX .. SET (connect = 'off')` stops the refresh of the connection for good.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 5.0.0 with the install; extension SQL 5.0, no script to run; no column format minor and no BM25 metapage minor changes. The wait of the automatic rewrite is kept in a word of the metapage that 5.0.0 leaves at zero and does not read: 5.0.1 opens an index of 5.0.0 with the word at zero, and 5.0.0 opens, verifies and answers through an index of 5.0.1 whose word is set. The library opens the files of 5.0.0 as they are, on a primary and on a standby, and the files of this release are read by 5.0.0.

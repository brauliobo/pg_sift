pg_sift 5.0.1: a patch release of 5.0.0 that stops index builds and maintenance from blocking writers, bounds the memory of builds, merges, checks, caches and the tombstone log by the settings that name them, no longer rewrites a `sift_col` index by itself, and closes a set of crashes and wrong states that a dropped object, a cancel or an unusual argument could cause. The library only: the extension SQL stays at 5.0, no format changes, nothing is rebuilt.

## Highlights

- **Maintenance: nothing rewrites a `sift_col` index by itself any more.** A connected child index of tens of GB was rewritten in a single transaction that lasted ten hours, and the next rewrite began the moment it ended: a rewrite costs the whole index (and, for a connected child, a read of the keys of its parent), so no rule could tell when it paid. `VACUUM`, the maintenance worker, the reads that owe a rewrite and the re-decision of a key start none; rewriting a whole index is your decision, `REINDEX INDEX CONCURRENTLY`. What stays automatic is the incremental work: the promotion of the write buffer, the merge of the small segments and of the overlays, the fold of the log, `VACUUM`, and the release and compaction of the value store. `sift.col_maintenance_status` says when a `REINDEX` is worth it (below).
- **Locks: `CREATE INDEX CONCURRENTLY` and `REINDEX CONCURRENTLY` of a `sift_col` index with a `scope` or `track_changes` no longer block the writers of the table.** They hold nothing stronger than `ShareUpdateExclusiveLock`, except for a few milliseconds at the end of the build, wait for the writers that hold the table without queuing the ones that come after, and fill the scope segments in the validation pass. A concurrent build of a scope index over a relation of pairs without a journal does the same.
- **Locks: other waits that blocked every session behind them are gone.** `sift.col_value_store_compact` asks for its locks as `VACUUM` does and fails at once with `55P03` when one is held, instead of queuing every later statement behind a long transaction. Sessions that give codes to new strings in a shared value store no longer wait for each other's merge of the store's runs. A `DELETE` or `UPDATE` of a `sift_table` no longer waits for the rewrite of the tombstone log that `VACUUM` makes, and an `INSERT` whose write buffer fills no longer waits for a `COPY`.
- **Memory: the memory of builds, merges and checks follows the setting, not the rows.** `CREATE INDEX` and `REINDEX` of a `sift_col` index free the scratch of each sorted run and merge when it ends (a scope of three entries a row built with a 2 MB run budget peaked at 207 MB at 200,000 rows and now at 33 MB); a column merge no longer keeps a string dictionary for every input segment; `sift.col_verify` and `sift.check` with `heapallindexed` hold 6 bytes a row at 1 MB of `maintenance_work_mem` where they held 130; `count(DISTINCT x)` of a text column and the cache of an aggregate over an expression stay within hash memory; an aggregate scan of the write buffers of a `sift_table` reads them one superblock (2 MB) at a time.
- **Memory: caches and idle backends.** A backend no longer keeps the lookup keys of every write buffer it saw, the dictionaries of segments a merge retired, or the strings of the shared value store of an index that was dropped; a pooled backend that runs a mix of statements does not grow.
- **Crashes and wrong states closed.** A cancel or an error right after the last directory switch of a `sift` (BM25) promotion or merge no longer frees blocks the directory still lists (`Block N is referenced twice`). A relation, function or namespace dropped while a statement reads it ends with the error of a missing object, not a segmentation fault; the inspectors and functions that take a relation or a NULL argument raise an error that names it (`42P01`, `42809`, `22004`) instead of crashing or saying the index is corrupted. A grouped query over a table with a `sift_col` index joined to a subquery whose join key is computed over an outer join crashed the backend while it was planned (5.0.0 only), and a grouped partitioned query with `GROUPING SETS` and a `NOT IN` subquery failed with `PlaceHolderVar found where not expected`. A reader that built a write buffer's references from the heap and ended in an error left the slot owned until the backend exited; the other readers waited for it and polled. The damaged-index registry no longer puts a damaged index back in service when it is full.
- **Maintenance workers are quieter.** A worker with nothing to do leaves after two looks, a request that arrives while one leaves is no longer dropped, the fold of the log is asked for only when a fold can clear marks, a failed or shut-down merge returns its blocks to the index, and the message that no background worker slot was free is logged once an hour for each job and names the jobs that hold them.

## New and changed settings

- **`sift.col_auto_merge_max_active` and `sift.col_auto_merge_max_workers` (removed).** They bounded the automatic rewrites, which are gone. A configuration file or `ALTER SYSTEM` entry that still names them logs `invalid configuration parameter name ..., removing it` and the server starts; delete the entry. `sift.col_auto_merge` (default on) still controls the incremental work, and `sift.col_auto_merge = off` stops it.
- **`sift.backend_cache_kb` (new, default 256 MB).** The total a backend keeps in its caches of parsed dictionaries, `sift` segment bytes, joined-table rows, the strings of shared value stores and the facts of partitions, dropping the least recently used entry of any of them. The separate limits added up to about 480 MB a backend, which a pool of connections multiplied. `-1` leaves each cache to its own setting; lower it on a server with many backends, raise it for a few backends that join large tables. No `REINDEX`: the setting is read when a cache admits an entry.
- **`sift.tomb_log_limit` (default 64 MB, was 8 GB).** The memory a backend keeps of the tombstone log of a `sift_table` (64 bytes for each row deleted or updated since the last `VACUUM`, the entries of its own statement included). The entries past the limit are kept in sorted runs on temp files, so a read of a log of any length and a `DELETE` or `UPDATE` of any number of rows complete (the error past the limit of 5.0.0 is gone); the cost is a block read for each run when an entry is not in memory, and temp files within `temp_file_limit`. A value you set yourself stays as you set it.

## When to `REINDEX`

`sift.col_maintenance_due(index)` names the reason a rewrite would pay (`stale connection`, `stale scope`, `dirty units`, `fragmented units`, `key ranges overlap`, a value store with garbage) and `SELECT * FROM sift.col_maintenance_status('idx')` shows it in `rewrite_due`, with `blocked_by` saying `REINDEX recommended (reason)`. The reasons `write buffer rows`, `overlay units` and `scope segments` are met by the incremental work and recommend nothing. Nothing is logged, and nothing is wrong meanwhile: reads answer correctly from the rows of the units and the keys of the parent; they only cost more than a rewritten index would.

- Run `REINDEX INDEX CONCURRENTLY idx` in a window of your choosing, for example after the nightly `VACUUM`: the disk holds both files until the swap, and a connected child index reads the keys of its parent once. `sift.col_maintain(index)` rewrites in place and holds the maintenance lock meanwhile.
- A reason that stays on a large index is not an emergency: plan the `REINDEX` for the quietest hours, one index at a time, and watch the disk for twice the index.
- The metapage is that of 5.0.0: a 5.0.0 index opens and verifies unchanged, and 5.0.0 opens the indexes of this release.

## Who is affected and what to do

- **Everyone on 5.0.0** gets the fixes by replacing the library. An index that 5.0.0 would have rewritten by itself is now left as it is, and the status recommends the `REINDEX`.
- **Update (the steps):** install the files and restart the server (a standby too, in any order: the files of 5.0.0 and of 5.0.1 are read by both). `ALTER EXTENSION pg_sift UPDATE` is not needed and changes nothing: the extension SQL stays at 5.0. No `REINDEX`, nothing stored is wrong. Without a restart a session keeps the library it loaded first and says `Reconnect` when it meets the new file: reconnect pooled sessions.
- **Going back:** install the 5.0.0 files and restart; nothing has to be undone. 5.0.0 keeps the whole log in memory and fails with `54000` past `sift.tomb_log_limit`: raise the setting (its default there is 8 GB) if you lowered it for 5.0.1.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 5.0.0 with the install; extension SQL 5.0, no script to run; no column format minor and no BM25 metapage minor changes. The library opens the files of 5.0.0 as they are, on a primary and on a standby, and the files of this release are read by 5.0.0.

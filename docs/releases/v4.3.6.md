pg_sift 4.3.6: a patch release of 4.3.5 that makes a library read the index of a newer release for what it is. Every 4.x library checked the length of the metapage of an index against the struct it knows before it checked the format, so an index that a newer release had written (its metapage is longer) was reported as `ERROR: sift index "<name>" is corrupted` with the detail `Bad metapage (magic 0x53494654, N bytes)`, where the message about the format and its hint belong. The index was never damaged. It also fixes a bounds error in the dirty-bit tracking of the liveness pages that could overwrite page metadata of an index with large column segments, or leave deleted rows visible. Install 4.3.6 on every node (standbys first) before moving any node to a newer release. Extension SQL 4.3.6 (no new object, no format change): install the files and restart the server; `ALTER EXTENSION pg_sift UPDATE` runs an empty script.

## Highlights

- **Fixed: a bounds error in dirty-bit tracking could overwrite page metadata of an index with large column segments, or leave deleted rows visible.** The bit that marks a superblock as holding dead rows was set on the first liveness page whatever its number. For a segment of more than 65,151 superblocks the bit landed in the special space of that page (its type, flags and generation) or past it: the next read of the page failed with `sift index "<name>" is corrupted`, or the bit was lost and readers did not look at the dead rows. The bit is now set on the page of the bitmap that holds it, in a record of its own (a crash leaves a bit over rows that are still live, which readers take as a hint to look at the bits). No format change.
- **Fixed: a library of an older release that reads an index written by a newer release refuses it with the format message instead of reporting the index as corrupted (4.0.5 to 4.3.5).** The bytes of the metapage past the struct of the library belong to the newer release. The library now reads them as that: it accepts a longer metapage, keeps every byte past its own struct as it found it on each write, and never lowers `pd_lower` over them (generic WAL and full-page images drop what lies past it). A format it cannot read is refused with `sift index "<name>" has on-disk format M.N, this build (pg_sift X) reads formats ...` and the hint `Install the pg_sift release that wrote the index on every node that reads it, or REINDEX it.`

## Who is affected and what to do

- **Affected:** a node that runs 4.0.5 to 4.3.5 and reads an index that a newer release has written, for example a standby that stays behind while the primary moves to a newer release, or a server that is moved back to an older library.
- **Affected by the bounds error:** an index with a column segment of more than 65,151 superblocks (a very large segment) in which a `VACUUM` or a delete marked rows dead. **What to do:** after the update, `REINDEX` such an index (`sift.col_verify` of the index tells whether it is sound); an index whose segments are smaller is not affected.
- **What you saw:** `ERROR: sift index "<name>" is corrupted` with `Bad metapage (magic 0x53494654, N bytes)` for an index that is sound. No repair tool applies: nothing is damaged, the index is only newer than the library.
- **Update (the steps, in this order):** install the files and restart the server (a standby too: a running backend keeps the library it loaded), then `ALTER EXTENSION pg_sift UPDATE` in each database. Do this on every node, standbys first, before moving any node to a newer release.
- **What 4.3.6 does with such an index:** it reads an index of a format it knows as it reads its own, and refuses an index of a format it does not know with the format message and its hint. The newer release's own counters in the bytes past the struct are neither updated nor zeroed by the older library: a write by 4.3.6 changes the first 400 bytes of the metapage as before and leaves everything past them, and the length of the metapage, as they were. Counters of the newer release that 4.3.6 does not maintain stay as they were, so they are out of date, not reset.
- **Going back:** install the 4.3.5 files and restart after `ALTER EXTENSION pg_sift UPDATE TO '4.3.5'`; the message about a bad metapage is back with those libraries.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 4.3.5 with the install; extension SQL 4.3.6 (`pg_sift--4.3.5--4.3.6.sql`, empty); no column format minor and no BM25 metapage minor changes.

## Packages

x86-64 and arm64 packages for PostgreSQL 17, 18 and 19 are attached below (`SHA256SUMS` covers every asset); other versions build from source with `make USE_PGXS=1`.

- Debian 12 and 13, Ubuntu 22.04 and 24.04 (PGDG `postgresql-N`, N = 17, 18 or 19): `sudo apt install ./postgresql-N-pg-sift_4.3.6-1_amd64.deb` (`_arm64.deb` on arm64)
- RHEL, Rocky, Alma 9 and 10 (PGDG `postgresqlN-server`): `sudo dnf install ./pg_sift_N-4.3.6-1.el9.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Amazon Linux 2023 (the distribution's `postgresqlN-server`, N = 17 or 18): `sudo dnf install ./pg_sift_N-4.3.6-1.amzn2023.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Arch Linux: AUR `pg_sift`.

Every change: [CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.6/CHANGELOG.md).

## SQLite extension

pg_sift for SQLite 4.3.6 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 4.3.6 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-4.3.6-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v4.3.6/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.6/sqlite/CHANGELOG.md).

## MariaDB extension

pg_sift for MariaDB 4.3.6 (`sift`, a UDF library and two SQL files; a separate component from the extensions above). Rebuilt with the PostgreSQL 4.3.6 release: no change to the SQL files.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- One library per MariaDB series, because it calls the server's own symbols and refuses to load into another series: 10.11, 11.4, 11.8, 12.1 and 13.0; Linux x86-64. Each was built in the stock `mariadb:<series>` image against that server's headers and loaded into a server of the same image before release. `BUILD-INFO` in the tarball lists the server version and the glibc each library needs.
- Index format 2: an index of 3.4.0 to 3.7.0 opens as it is, nothing to rebuild.

Download `sift-mariadb-4.3.6-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it, copy `lib/<series>/libsift_udf.so` of your server's series
(`SELECT VERSION()`) into its `plugin_dir`, then `SOURCE sql/functions.sql` once per server and `sql/sift.sql` once per database (`sha256sum --ignore-missing -c SHA256SUMS`).
Documentation: [mariadb/README.md](https://github.com/brauliobo/pg_sift/blob/v4.3.6/mariadb/README.md).
Every change: [mariadb/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.6/mariadb/CHANGELOG.md).

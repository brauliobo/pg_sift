pg_sift 4.3.5: a patch release of 4.3.4 that stops a `VACUUM` from writing the catalog. A `VACUUM` (manual, autovacuum or a scheduled one) of a table with a `sift_col` index could leave the row of the index in `pg_class` twice, or lose an update of it, and later raise `dead heap-only tuple (N, M) is not linked to from any HOT chain` on every `VACUUM` of `pg_class`. It also stops `VACUUM`, `sift.col_merge` and the maintenance worker from failing with `Segment N is not in the order of the TIDs` on an index whose `key_cut` was switched. Extension SQL 4.3.5 (no new object, no format change): install the files and restart the server; `ALTER EXTENSION pg_sift UPDATE` runs an empty script.

## Highlights

- **Fixed: a `VACUUM` of a table with a `sift_col` index could damage the row of the index in `pg_class` (3.4.0 to 4.3.4).** The options the build chooses and keeps in the catalog (`key_cut`, `key_columns`, `order_array_columns`, `point_tid_columns`, when they are `'auto'`) are chosen again from the data when the segments are merged, and the merge of a `VACUUM` made that choice and wrote the options: an update of the index's row in `pg_class`, in the transaction of the `VACUUM`. PostgreSQL runs a lazy `VACUUM` with a flag that leaves its transaction id out of the snapshots of every other session (a `VACUUM` is not expected to update rows). A session that read the index's row while the `VACUUM` was still running took the `VACUUM`'s id for an aborted transaction and marked the old version of the row as not updated (`HEAP_XMAX_INVALID`, a hint that PostgreSQL trusts for good). When the `VACUUM` committed, the old version and the new one were both visible: the row was there twice, or the update was lost, and the first pruning of the page that ran after the id was older than every snapshot raised `ERROR: dead heap-only tuple (N, M) is not linked to from any HOT chain`, again for every later `VACUUM` of `pg_class`. The same row was updated two or more times for no change in the options (each decision wrote an option that already had the value). A `VACUUM` now writes no catalog row: its merge keeps the options as they are and asks for a maintenance worker, which chooses them in a transaction of its own and rewrites the segments with the new choice when an option changed (`sift.col_auto_merge` and `sift.async_maintenance`, both on by default; with either off the next `sift.col_maintain` or `sift.col_merge` call chooses). An option that already has the value a decision gives is not written again. Every write of an index option raises an error in a `VACUUM` or a parallel operation, so a later change cannot bring the damage back. Held by the TAP test `col_vacuum_catalog_xid`: it stops a `VACUUM` right after its merge, reads the index's row from a second session, lets the `VACUUM` end, and looks at the pages of `pg_class`; on 4.3.4 the `VACUUM` holds a transaction id and the old version of the row carries the wrong hint, on 4.3.5 it holds none and the page is intact.
- **Fixed: `VACUUM`, `sift.col_merge` and the maintenance worker failed for good with `ERROR: sift index "<name>" is corrupted` and `Segment N is not in the order of the TIDs` (3.4.0 to 4.3.4).** After `ALTER INDEX .. SET (key_cut = ..)` (or a rewrite that chose the cut again) the segments that were cut the old way stayed, and the merge read every keyed segment the way the index is cut now. A keyed segment now records in its directory entry whether it is cut by TID range or by a key (two spare flag bits, no format change) and the merge sorts the rows of an input cut the other way. No answer was wrong: the index only could not be merged, and a `VACUUM` stopped in its index cleanup after the heap pass.
- **Changed: the update of a row of a `sift_table`** takes a copy of the old row's `tid` before it writes the new version, so a caller that passes the address of the slot's own `tid` cannot make the tuple lock be released on another tuple. No caller does today; nothing changes for a statement.

## Who is affected and what to do

- **Affected:** 3.4.0 to 4.3.4 on PostgreSQL 17, 18 and 19 (the choice of `key_columns` is written from a `VACUUM` since 3.4.0, the choices of `key_cut`, `order_array_columns` and `point_tid_columns` since 4.0.0), where a `VACUUM` or autovacuum ran on a table with a `sift_col` index whose options are `'auto'` (the default of a build) while another session read the index's catalog row (any new connection that plans a statement on the table does). A table whose indexes hold explicit values for those options (a list or `off`, not `auto`), or one nobody `VACUUM`s while it is used, did not meet it.
- **What you saw:** `ERROR: dead heap-only tuple (N, M) is not linked to from any HOT chain` from `VACUUM`, autovacuum or any statement that prunes a page of `pg_class`; a `sift_col` index that is listed twice in `pg_class`, or the options of an index that went back to what they were. The user data and the index files are not damaged: only the catalog row is.
- **Update (the steps, in this order):** install the files and restart the server (a standby too: a running backend keeps the library it loaded, and the old one is the one that writes the catalog in a `VACUUM`); then `ALTER EXTENSION pg_sift UPDATE` in each database (4.3.4 to 4.3.5 runs an empty script: no object changes; no format change). Until then, an index whose `key_cut`, `key_columns`, `order_array_columns` and `point_tid_columns` hold explicit values (the list the index holds now, or `off`; not `auto`) is not written by a `VACUUM`: `ALTER INDEX name SET (key_cut = 'list', ...)`, no restart; `ALTER INDEX .. SET (key_cut = 'auto', ...)` gives the automatic choice back once 4.3.5 runs.
- **What changes for a `VACUUM`:** the options of an index that were chosen again inside a `VACUUM` are chosen by the maintenance worker the `VACUUM` asks for, a few seconds later, and the segments are rewritten with the new choice then (the log line says `options chosen again`). A server with `sift.col_auto_merge` or `sift.async_maintenance` off gets the new choice from the next `sift.col_maintain` or `sift.col_merge` call.
- **If an index already fails with `Segment N is not in the order of the TIDs`:** `REINDEX INDEX <name>` makes every segment new; with the 4.3.5 library installed the failure does not come back after a later `ALTER INDEX .. SET (key_cut ..)`. Segments written before 4.3.5 carry neither flag and are read as before; a merge of segments cut by two different keys still asks for a `REINDEX`.
- **Going back:** install the 4.3.4 files and restart after `ALTER EXTENSION pg_sift UPDATE TO '4.3.4'`; the cause of the damage is back with those libraries.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 4.3.4 with the install; extension SQL 4.3.5 (`pg_sift--4.3.4--4.3.5.sql`, empty); no column format minor and no BM25 metapage minor changes.

## Packages

x86-64 and arm64 packages for PostgreSQL 17, 18 and 19 are attached below (`SHA256SUMS` covers every asset); other versions build from source with `make USE_PGXS=1`.

- Debian 12 and 13, Ubuntu 22.04 and 24.04 (PGDG `postgresql-N`, N = 17, 18 or 19): `sudo apt install ./postgresql-N-pg-sift_4.3.5-1_amd64.deb` (`_arm64.deb` on arm64)
- RHEL, Rocky, Alma 9 and 10 (PGDG `postgresqlN-server`): `sudo dnf install ./pg_sift_N-4.3.5-1.el9.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Amazon Linux 2023 (the distribution's `postgresqlN-server`, N = 17 or 18): `sudo dnf install ./pg_sift_N-4.3.5-1.amzn2023.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Arch Linux: AUR `pg_sift`.

Every change: [CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.5/CHANGELOG.md).

## SQLite extension

pg_sift for SQLite 4.3.5 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 4.3.5 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-4.3.5-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v4.3.5/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.5/sqlite/CHANGELOG.md).

## MariaDB extension

pg_sift for MariaDB 4.3.5 (`sift`, a UDF library and two SQL files; a separate component from the extensions above). Rebuilt with the PostgreSQL 4.3.5 release: no change to the SQL files.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- One library per MariaDB series, because it calls the server's own symbols and refuses to load into another series: 10.11, 11.4, 11.8, 12.1 and 13.0; Linux x86-64. Each was built in the stock `mariadb:<series>` image against that server's headers and loaded into a server of the same image before release. `BUILD-INFO` in the tarball lists the server version and the glibc each library needs.
- Index format 2: an index of 3.4.0 to 3.7.0 opens as it is, nothing to rebuild.

Download `sift-mariadb-4.3.5-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it, copy `lib/<series>/libsift_udf.so` of your server's series
(`SELECT VERSION()`) into its `plugin_dir`, then `SOURCE sql/functions.sql` once per server and `sql/sift.sql` once per database (`sha256sum --ignore-missing -c SHA256SUMS`).
Documentation: [mariadb/README.md](https://github.com/brauliobo/pg_sift/blob/v4.3.5/mariadb/README.md).
Every change: [mariadb/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v4.3.5/mariadb/CHANGELOG.md).

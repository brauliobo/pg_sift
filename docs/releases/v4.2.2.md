pg_sift 4.2.2: a patch release of 4.2.1 that fixes a wrong answer of `sift_table` that is present since 4.0.0: a `VACUUM` of a table that waited for the table's maintenance lock could make the old versions of updated rows, or rows that were deleted, visible again. It adds `sift.table_find_stale_versions()` to find the copies of updated rows; extension SQL 4.2.2 (one new function, no format changes): install the files, restart the server (a standby too), then `ALTER EXTENSION pg_sift UPDATE` in each database. Updating fixes the cause; it does not repair rows that already came back (see "If a `sift_table` may be affected").

## Highlights

- **Fixed: a `VACUUM` of a `sift_table` could make old versions of updated rows, or deleted rows, visible again (4.0.0 to 4.2.1; `sift_table` only).** A `VACUUM` that waits for the table's maintenance lock went on with the list of segments it had read before the wait. When the holder of the lock promoted or merged write buffers in the meantime, the `VACUUM` did not mark the dead rows of the new column groups as removed, and then dropped the records of their deletion: every snapshot saw the old version of an updated row next to the new one, and the rows that a `DELETE` had removed. The `VACUUM` can be a manual one, autovacuum (also the one that prevents transaction ID wraparound), a pass of the background worker (`sift.table_auto_defrag`) or a second `VACUUM` of the same table; the holder can be a writer that closes a write buffer (`sift.table_inline_promote`), the worker, `sift.table_maintain()` or another `VACUUM`. Every maintenance entry now takes the lock and reads the list of segments in one step. `sift_col` and `sift` (BM25) indexes and the heap are not affected.
- **Added: `sift.table_find_stale_versions(tbl regclass, sample integer DEFAULT 10)`** returns one row: `duplicate_keys`, the number of primary key values that are on more than one row, and `sample_keys`, up to `sample` of them (`text[]`, each key written as a row: `(7)`, `(3,k1)`). It reads the table once (a sequential scan and a hash `GROUP BY` on the key, `work_mem` applies), takes only `ACCESS SHARE`, writes nothing and runs with the rights of the caller. It fails for a table without a primary key and returns 0 for a heap table; a partitioned table is read through all its partitions. It finds updated rows that came back; it cannot see deleted rows that came back.
- **Fixed: assert builds stop where a merge of a `sift` index finds none of the segments it replaces in the directory** (the maintenance lock and the claims rule it out). A build without assertions is unchanged.
- **Added: [docs/INDEX-RECIPES.md](https://github.com/brauliobo/pg_sift/blob/v4.2.2/docs/INDEX-RECIPES.md)**, which `sift_col` columns to create and what an index costs in size and writes.

## Who is affected and what to do

- **Update (the steps, in this order):** install the files and **restart the server** (a standby too), because a backend that already loaded the old library keeps it until its connection ends; then `ALTER EXTENSION pg_sift UPDATE` in each database (4.2.1 to 4.2.2 adds the function; a database at 4.2 goes through 4.2.1 by itself; nothing to `REINDEX`, no format change).
- **Everyone who has a `sift_table` that is updated or deleted from, and `VACUUM`ed or maintained while it is written:** update, then run the detector on each such table (below). A table that nothing ever updated or deleted from has no old versions to bring back.
- **Reduce the exposure until the update is installed:** `sift.table_auto_defrag = off` removes only the background worker's `VACUUM`s. A manual `VACUUM`, autovacuum (the anti-wraparound one cannot be disabled) and two `VACUUM`s of one table at once can still trigger it, and no maintenance setting removes the cause (it was reproduced with `sift.table_auto_defrag = off` and `sift.async_maintenance = off`). `autovacuum_enabled = false` on the table with no manual `VACUUM` avoids all but the anti-wraparound one, at the cost of dead space and stale statistics. `VACUUM` only while the table is not written, and never two at once.
- **The error `sift index "<name>" is corrupted ... expected page type/generation X, found Y`** was seen from `VACUUM` and `sift.table_maintain()` in the same race on 4.0.0 to 4.2.1: the call read a page of a segment that the lock holder had already released, and aborted. It is not seen on 4.2.2. Treat a table that raised it as exposed: update, run the detector and compare with your source of truth. A `REINDEX` or rebuild is not needed for the error itself as far as tested, but the table was not examined after it.

## If a `sift_table` may be affected

The update does not repair the rows that already came back.

1. **Detect updated rows that came back.** `SELECT * FROM sift.table_find_stale_versions('t')` (the table name is an example). A count above 0 means primary key values on more than one row. The function runs with `sift.enable_agg`, `enable_indexscan`, `enable_bitmapscan` and `enable_indexonlyscan` off for its own duration: with them on, the aggregate engine answers `count(*)` and `GROUP BY` as if the key were unique, and the primary key index no longer holds the old versions, so a plain `GROUP BY pk HAVING count(*) > 1` finds nothing. A query of your own needs the same four as `SET LOCAL`.
2. **Repair updated rows.** The copy that was visible before the `VACUUM` is the one with the highest `ctid` (tuple identifiers are never reused and promotion and merge keep them), so one transaction rebuilds the table with that copy per key:

   ```sql
   BEGIN;
   LOCK TABLE t IN ACCESS EXCLUSIVE MODE;
   SET LOCAL sift.enable_agg = off;
   SET LOCAL enable_indexscan = off;
   SET LOCAL enable_bitmapscan = off;
   SET LOCAL enable_indexonlyscan = off;
   CREATE TABLE t_new (LIKE t INCLUDING ALL) USING sift_table;
   INSERT INTO t_new SELECT DISTINCT ON (pk) * FROM t ORDER BY pk, ctid DESC;
   ALTER TABLE t RENAME TO t_old;
   ALTER TABLE t_new RENAME TO t;
   COMMIT;
   ```

   It was checked against a heap twin on three data sets with several updates per row: no row differed. It holds only if the table was not rewritten since the copies appeared (`VACUUM FULL` and `CLUSTER` assign new `ctid`s), and `xmin` cannot order the versions. If the table has a column that orders them (`updated_at`, a version number), order by it instead; otherwise choose the rows from `SELECT *, ctid ... ORDER BY pk, ctid` with the four settings. Foreign keys, views and grants move by hand, and the indexes and constraints of the copy are named after it.
3. **Deleted rows that came back have no duplicate.** SQL on the table alone cannot find them and the copy above does not remove them. Delete the keys you know were deleted again, or restore from a backup taken before the first `VACUUM` that could have been affected.
4. **Going back:** install the 4.2.1 files and restart; `ALTER EXTENSION pg_sift UPDATE TO '4.2.1'` runs the empty script back to 4.2 and then the 4.2.1 script. The function stays in the database and works with the 4.2.1 library; the cause of the wrong answer is back with that library.

- **Nothing else changes:** plans, speeds and answers outside the cases above are those of 4.2.1.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 4.2.1 with the install and a restart; extension SQL 4.2.2 (`pg_sift--4.2.1--4.2.2.sql`, and an empty `pg_sift--4.2.2--4.2.sql` back); no column format minor and no BM25 metapage minor changes.

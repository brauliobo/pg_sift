pg_sift 5.0.0: reads of a tenant or a group through a table of pairs (a scope index, experimental, and pair tables kept from a view), named projections, one store for the strings that several indexes of a table hold, reads of a table under concurrent writers that no longer fall back to the heap, a rewrite of `key_cut` indexes that rolls partition by partition and keeps to a WAL budget, and three index options ignored and one setting removed. Extension SQL 5.0 (`ALTER EXTENSION pg_sift UPDATE` in each database after the install and a restart); nothing has to be rebuilt.

## What 5.0 changes for you

Nothing is rebuilt: the update leaves every index as it is, and a query keeps PostgreSQL's plan unless an index proves it can answer the same rows. [docs/UPGRADING.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md) has the steps in full.

**To upgrade from 4.3**

1. **Install 4.3.6 on every node first, standbys first** (the preflight warns when the extension is older). 4.0.0 to 4.3.5 answer `sift index "x" is corrupted` (detail `Bad metapage`) for an index a 5.0 server has touched: the index is sound, do not repair it with `pg_surgery` or catalog edits, `REINDEX` with the old files rebuilds it. 4.3.6 reads the metapage and refuses a segment it cannot read with the format message and the hint `Use a newer pg_sift, or REINDEX.`, which is what a rollback or a standby that is not upgraded yet should show.
2. Before the update run the preflight of the 5.0 files (`scripts/upgrade-check.sh`, or `pg_sift_upgrade_check.sql`, installed with the extension files): each row is an index or setting to deal with, with its command.
3. **Update the standbys first.** A 4.3 library refuses an index whose metapage a 5.0 library has read, so a 4.3 standby cannot follow a 5.0 primary.
4. Install the files and **restart the server**, then `ALTER EXTENSION pg_sift UPDATE` in each database. The library writes the BM25 format before the update runs. The script adds five event triggers (`sift_col_build_lock`, `sift_col_value_store_sql_drop`, `sift_col_names_before`, `sift_col_names_follow` and `sift_col_names_sql_drop`), which `sift.ddl_hooks` lists.
5. Reconnect pooled sessions: a session keeps the library it loaded first and says `Reconnect` when it meets the new file.
6. `SELECT * FROM sift.upgrade_check()` (installed by the update) again, then `SELECT * FROM sift.check()` (no row means sound).

**What differs afterwards**

- `ALTER INDEX .. SET / RESET` of an option that changes what the segments hold (the analyzer options of a `sift` index; `paths`, `array_lengths`, `connect` and `scope` of a `sift_col` index) is refused with `0A000` once the index has a segment: build the replacement with `CREATE INDEX CONCURRENTLY`, then `DROP INDEX` the old one. A script that ran `ALTER INDEX` then `REINDEX` needs that change. `ALTER INDEX .. SET (key_cut = ..)` needs no `REINDEX`.
- `sift.col_auto_merge_dirty_pct` is removed, and `sift.table_auto_defrag_delay`, `sift.table_auto_defrag_max_active` and `sift.table_auto_defrag_wal_rate` are set in `postgresql.conf` (SIGHUP), not with `ALTER DATABASE .. SET`. Rename of columns, tables and schemas keeps every `sift_col` index working.
- The options `key_cut_rows`, `point_columns` and `order_columns` are ignored; the preflight lists each index that holds one with the `ALTER INDEX .. RESET` that clears it.
- **A damaged index leaves service** (`sift.on_corruption = quarantine`, the default): a `sift` or `sift_col` index that finds damage fails the statement that found it once, is listed in `sift.quarantine`, and statements then run on the heap with exact answers until `REINDEX`. `SET sift.on_corruption = error` keeps the behaviour of 4.3. Heap plans of a large table can be slow: alert on `sift.quarantine`.
- `shared_preload_libraries` is still not required; an aggregate workload is better with `session_preload_libraries`, and `CREATE EXTENSION` prints the command.
- New to run a server by: `sift.check`, `sift.workers`, `sift.progress`, `sift.col_index_status`, `sift.shared_memory()`, `sift.locks`, `sift.indexes`, `sift.ddl_hooks` and the cluster-wide `sift.stats()` (`local => true` for the session's own), `EXPLAIN (SIFT)` on PostgreSQL 18 and later, and the named waits `SiftMaintenanceNap`, `SiftArenaWait` and `SiftParallelLeader`. [docs/OPERATIONS.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/OPERATIONS.md) says what to watch and what to do. The SQL reference lists 96 functions, 12 views, 4 tables and 3 operator classes.

**Going back to 4.3** (from 4.3.6 on a refused index says so with the format message; before it, `corrupted`: nothing is damaged) takes more than installing the old files if you used a scope index or the shared value store: their segments (minors 45, 46, 49, 50 and 51) are refused by 4.3. Follow [Going back to 4.3](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#going-back-to-43): `sift.upgrade_check('4.3')`, `SET sift.col_value_store = off`, drop or rebuild the blocking indexes, disable the five event triggers above, install the 4.3 files and `REINDEX` every index a 5.0 server read. For a release before 4.3, `SET sift.col_format_minor = 14` and `REINDEX` stop change tracking too (the reads check the heap until a `REINDEX` under the default) and every structure of minors 15 and above.

## Highlights

Figures are those [CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/CHANGELOG.md) states, with the table they were measured on. Instructions are those of one backend.

### Reads through a scope (experimental)

- **A scope index (`CREATE INDEX .. USING sift_col (..) WITH (scope = '..')`).** It stores the rows of the index once for each scope key that a table of (member, scope key) pairs gives them, in `key_cut` segments of their own (column format minor 45), and a read of a key reads the units of that key less the members whose pairs changed since the segments were written; the statement makes the journal index that the relation of pairs lacks (a `NOTICE` names it, it goes with the last scope index that uses it). One key of the 100,000-row test table (5,000 members, 40 tenants) reads in 1.0 to 1.1 million instructions where the rows of the members cost 1.9 to 2.0; the index file grows from 1,368,064 to 2,383,872 bytes (+74%; a NOTICE says the growth of the segments, +67%). The planner reads the join forms of a scope from the units: `JOIN`, `IN (SELECT ..)`, `EXISTS`, `= ANY (ARRAY(SELECT ..))`, the union of two paths (a direct grant and a grant on a group), `GROUP BY` the key for every key at once, a parameter of a prepared statement as the key, and prices the join as written against them; `sift.explain_why` (slug `scope`) says why a statement keeps the join. The scope key may also be a `text`, `varchar` or `uuid` column of a deterministic collation (column format minor 50: its units are cut by the code of the key in the value store of the key column), with the same forms and a group by the key; in the 300,000-row test table the read of one key costs the same instructions as the integer key (1.0 million) and the build writes 3% more bytes (3.59 against 3.47 MB, plus a 152 KB store). The member may be a `text`, `varchar` or `uuid` column as well: a read costs 0.9 to 1.4 million instructions for one key as for an integer member (1.1 million), and with changed pairs or rows in the write buffer it is read from the units as an integer member is, within 3% of the integer member's instructions (22.5 million for text and 22.3 for uuid against 21.9 for an integer member at 375 changed pairs of 300,000 facts, 121 and 122 blocks hit against 122; an integer member read 82.5 million before). A scope of two paths takes a string key and member as well, with costs within 10% of the integer member's (1.4 against 1.7 million instructions for one key; 26.4 for text and 26.8 for uuid against 24.5 million at 375 changed pairs, 85.2 before), and a read of one string key patches the members of the pairs that changed in that key only. `sift.agg_scope = off` turns it off. What a scope does not do: `char(n)`, `citext`, a domain and a nondeterministic collation are refused at the declaration, with the reason; the group column that joins the two paths of a scope stays an integer; an `ORDER BY` or `LIMIT` over a group by a string key keeps the join (the codes are not in the order of the values); the copies of changed pairs and of rows of the write buffers are read by the leader alone; a list of five keys counted once costs 7.5 and 6.1 million instructions for a text and a uuid member against 2.1 for an integer. [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md).
- **A scope read does less work per key.** The scope segments hold the superunit summaries of the entity segments (an aggregate over a key of many units reads a group of 16 at a time), an aggregate decodes only the measures it reads, a latest N reads each unit from its end on several sort keys (the rows of a unit that tie on the first key are taken from the end where the best are: latest 20 of the largest tenant 10.3 to 5.8 million instructions), a scan checks its segments against the directory page it holds, not a buffer for each unit (252 to 207 buffer hits for a count by score of the largest tenant), the planning of a statement over a column index checks the statistics of the index against the version of its directory page (10 to 6 buffer accesses and 56,000 instructions fewer for the cheapest read), and an expression key over a wide range evaluates the values the unit holds. On the 2.4-million-event comparison with tuned stock PostgreSQL, a count by score of the largest tenant went from 8.6 to 2.5 million instructions and 1,092 to 252 blocks, a count by kind from 4.6 to 2.5, a sum by month from 9.2 to 7.7; the cells the scope read does not win against an incremental view (26 of 64), a denormalised copy (17 of 72) or a tuned semi join (5 of 72) are listed in `docs/COL-SCOPE.md` with the instructions that keep them: the selective filter reads its entries, and the cheapest read of any tenant is 1.8 million instructions, most of it the parsing and planning of the statement (0.2 million as a prepared statement with a generic plan). A heap with unvacuumed rows no longer prices the units of a scope cut by time as read row by row (a count by kind of the largest tenant with 10,000 inserted events 50.9 to 3.6 million instructions). The write cost is unchanged within 2% (10,000 inserts 146 million instructions; a promotion 179 to 182; a pair grant 0.19 million and 899 bytes). With `rollup_columns` declared, each run of units of a key also keeps the rollup of its rows, so a filter on two columns of the largest tenant (2.4 million events) reads 35.8 to 2.7 million instructions and 790 to 76 blocks hit, for +3% of the index.
- **A tenant of many units is one summary per run.** The scope segments summarise the units of a key as a group (column format minor 51), with the table of the members its units lack: count by member 17.57 to 5.27 million instructions (513 to 111 blocks) and the top 20 members 14.18 to 4.12 at the largest tenant of 600,000 events, for 7.7% more bytes in the scope segments. The groups also keep the id sets by month of their member columns, so the distinct members by month of a tenant read 83.2 to 8.6 million instructions (602 to 85 blocks) at the largest tenant of 2.4 million events, for 1.35% more bytes in the index.
- **A filter on two columns reads one rollup per key.** A scope index that declares `rollup_columns` keeps the rollup of the rows in each key group: the filter on two columns of the 2.4-million-event comparison reads 17.8 to 2.7 million instructions, 821 to 76 blocks hit and 987 to 56 read at the largest tenant, 3.8 to 2.3 million at the 6% tenants, for +3.2% of the index. A scope index writes none by default, since no statistic of the table says which pair its queries filter on (the pair `rollup_columns = 'auto'` chooses, `kind, score`, reads 13 to 21% fewer blocks for a count by score at the three largest tenants for 3.6 to 7.5% more instructions, moves no other class by more than 4 blocks and costs +0.9% of the index); `auto` works on a scope index now (its derived key column no longer fails the candidate list) and CREATE INDEX says what the rollup takes.
- **Pairs kept from a view (`sift.scope_follow_pairs`, `sift.scope_expire_pairs`).** A table of (member, scope key) pairs kept equal to a view over assignments and group membership, in the transaction of each change, with the pairs that expire by date applied by a sweep: what a scope index needs when its pairs are a view, depend on a condition on a third table or on time ([docs/INDEX-RECIPES.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/INDEX-RECIPES.md)).
- **The rewrite of a scope index has its own name.** `sift.col_scope_refresh_pct` (percent of the pairs of its relations, 10) decides when the automatic rewrite fills the scope segments again, and `sift.col_maintenance_due` says `stale scope`; `sift.col_connect_refresh_pct` and `stale connection` are the rule of connected indexes only. A scope index whose pairs churn on a table nobody writes is rewritten too: the reads that find the changed members add what they paid for them (the units and entries they ran and the blocks they took from the file) to a sum in the metapage of the index, which a restart and a crash keep, and ask for the rewrite once that is half of what it costs, its WAL counted (100 to 640 reads at 0.3 to 5% of the pairs of 300,000 events), so a busy index is refreshed after a few hundred reads and one nobody reads is not. The reads of a standby count for nothing, since a standby cannot write: it benefits from the rewrite when the primary does it.
- **A scope index does not need a scope segment to be read from.** The journal position its entries (and the rows that have none) are exact as of is kept in the metapage of the index, not in its scope segments, so a table whose pairs are empty or arrive after the facts is read from the units at once with the new pairs patched, the first scope segment that appears does not send the older entity segments to the join, and VACUUM dropping the scope segments of deleted rows loses no stamp.
- **Parallel workers.** A scope read runs under the `Gather` of a plan that has workers: the leader decides the read once (keys, changed members, patch) and the participants claim units of one directory. Measured on events fixtures of 2.4 and 10 million rows, a read of 25 to 50 ms in one process of a tenant of half the events ran 1.6 to 1.95x faster with two workers and 1.9 to 2.4x with four (instructions 4 to 12% more), and the reads under about 14 ms (83 million instructions) stay in one process, where the workers tied or lost: by price none of the 2.4 million events fixture's reads launches a worker, and a read that the pre-aggregates answer stays in one process. [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md) has the phases of a read with workers and the break-even.
- **Prior art.** [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md#prior-art-what-exists-and-what-differs) compares the scope index with join indexes, bitmap join indexes, indexed and materialized views, pg_ivm, copies kept by triggers, ClickHouse, Zanzibar's Leopard index, Elasticsearch and others, from their documentation. The idea of storing facts by a key reached through a join is not new there; the page says what is particular to the scope index and where the others are better.

### Named projections and shared strings

- **`sift.projection_create` and `sift.projection_index`** define once the columns, expressions, filter, roll-ups and options of an index and make the index from one or more of them (or record that an existing index with the same layout serves them); `sift.projection_status` says which are `ok` or `broken`. No format change; a restore and `pg_upgrade` need no order of creation. [docs/INDEX-RECIPES.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/INDEX-RECIPES.md).
- **The `sift_col` indexes of a table that hold the same text, varchar or uuid column with the same `key_order` and `key_cut` store its distinct strings once** (column format minor 46), in a relation `<table>_<column>_sift_values` that is never populated, so a publication of all tables does not list it. Builds take 1.0 to 1.45 times as long; `SET sift.col_value_store = off` before a build keeps the strings in the segments and makes no store, with change tracking and the other structures as usual (column format minor 44 at the most, which 4.3 reads); `sift.col_format_minor = 14` stops the store too, and with it change tracking and every structure of minors 15 and above. [docs/COL-VSTORE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-VSTORE.md).

### Reads under writers, and the rewrite

- **A table under concurrent writers is read without the heap more often.** A segment promoted while a transaction that inserted some of its rows was still open gets its stamp once that transaction has finished (before, until a rewrite); and the maintenance worker folds the marks of the tombstone log into the liveness runs as soon as the reads have paid for it, without waiting for a `VACUUM` that finds too few dead pages. On a churned lab table of 12 columns the mean of a group by goes from 22.4 to 5.5 million instructions, a range from 16.3 to 11.7, a list of 60 keys with `ORDER BY .. LIMIT` from 8.1 to 4.1; only these three classes were measured on that table.
- **A backend keeps the rows of a large write buffer for its next scan when it should:** the slowest read of a few keys on a table churned and vacuumed went from 160 to 5.2 million instructions.
- **The automatic rewrite of a `key_cut` index in partitions rolls.** Each step takes one partition and the overlays over its window of the key and writes into the blocks the step before freed, so a pass writes each partition once: on a 21 MB index grown to 76 MB in 400 batches, a pass takes 83 MB of index WAL (103 before) and the copy down after the overlay merges 44 bytes a row (105). Pieces that tier merges leave over one base partition wait for `sift.col_auto_merge_wal_pct` like any other churn: on the standard write-benchmark table the index WAL falls from 393.6 to 202.6 bytes a row (the wide table 1,423.5 to 545.1), and because that rewrite now comes later (batch 73 where it came at batch 42) a point or key read is 9% dearer around batch 54 and 3% dearer over 144 batches, 7 to 11% cheaper after the rewrite. **The rule that started the automatic rewrite when a share of the units held a dead row is gone** (see below): in heavy churn nothing changes, in light churn the rewrite is due as soon as the WAL budget allows, where it waited until the reads had paid for it, and `sift.col_maintenance_due` names any unit with a dead row as the reason.
- **`ALTER INDEX .. SET (key_cut = ..)` no longer needs a `REINDEX` (a defect since 3.4.0).** After the option was set to another key, to a list of other leaves or to `off` (or the rewrite chose the cut again), every `VACUUM`, `sift.col_merge` and maintenance step of the table failed with `Segment N is not in the order of the TIDs` or `segment N of a key_cut index is not in the order of the key`, because a segment did not say which leaves it was cut by. A segment cut by a key records them (a directory flag and a record in its header: no column format minor, and a library before 5.0 reads the segment as it did) and the merge sorts the rows of the inputs cut another way (in memory when they fit `maintenance_work_mem`, else with a sort that writes the rest to temporary files: no size of input stops it); a segment written by an older release is checked once, by the first merge that meets it. [docs/COLUMN-STORAGE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COLUMN-STORAGE.md#cutting-the-units-by-a-key).
- **A parallel `CREATE INDEX` with `key_cut` whose participants took unequal shares of the table merges its peers** (before, the index kept twice its size in the file until the first `VACUUM`).
- **Planner and reads:** a semi join on a `smallint`, `integer` or `date` key that the scan's key filter has tested builds no byte table; a lookup table that is only the keys of its rows reads them from the index entries; the groups of a row's entity over a link table are joined once; `ORDER BY ts LIMIT n` over a table cut by another column reads the ends of the order of each segment.

### Ignored and removed

- **The `sift_col` options `key_cut_rows`, `point_columns` and `order_columns`** (deprecated in 4.3) are ignored: they no longer change a build, and the names stay registered and accepted. **The setting `sift.col_auto_merge_dirty_pct` is removed**: a stored value is dropped with a `WARNING`, and a `pg_dumpall` that names it restores with one `ERROR` for that line. [docs/UPGRADING.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#what-50-removes).

### Fixed

- **Two `CREATE INDEX` statements of `sift_col` indexes that track changes on one table, run at the same time (a parallel `pg_restore`), failed with `deadlock detected`:** an event trigger before `CREATE INDEX` takes the stronger lock first.
- **`REINDEX` of two `sift_col` indexes of one table at the same time ended with `deadlock detected` for one of them (8 of 16 runs).** A `REINDEX` keeps the two change-tracking triggers of its index when they are what the option made, where it dropped and made them again (a lock stronger than the `ShareLock` the other `REINDEX` holds); one that has to make them (a disabled trigger, an index of an earlier release that has none yet) asks for that lock only when no other statement holds a lock that conflicts with it, and otherwise leaves the triggers (a `NOTICE` says so) for the maintenance worker, which makes missing triggers at the next read that checks the heap. The rules of a build read the other indexes of the table without locking them (the `REINDEX` of one holds it exclusively). Two `REINDEX CONCURRENTLY` of one table, and one beside a plain `REINDEX`, still deadlock in PostgreSQL itself, with any index type: run them one after the other.
- **`CREATE INDEX` and `REINDEX` of a scope index (new in 5.0) check that the role can read the pairs:** `SELECT` on the relation, or on its member, scope key and predicate columns, and no row-level security that applies to it; before, the owner of the indexed table could build over pairs it cannot read and learn how many match its rows from the `NOTICE` and the size of the index. Reads are checked as the join as written is (a role without `SELECT` on the pairs gets `permission denied` from the scope read too; one under row-level security reads the join as written).
- **A shortage of dynamic shared memory no longer fails a statement or ends a worker where the shared table is only a way to share.** A parallel lookup join, the dictionaries of the column indexes in a parallel operation, the arena of the write buffers' references under an `INSERT` or `UPDATE`, and the rollup refresh worker raised `could not resize shared memory segment` (and left a `dynamic shared memory leak` warning at the commit) when `/dev/shm` was full. Each now goes without the table and says so in the log: the parallel operations run unshared, a writing backend puts the values in its rows (as a buffer without `sift.col_wbuf_ref` does) and asks again a second later, the worker ends. The answers are the heap's in every case. That includes the first creation of the directory of the shared tables (72 kB, made by PostgreSQL's own registry, which would keep a broken entry for its name after a failure): the room is made sure of first, so no statement, parallel worker or background worker fails for it.
- **The shared tables of a server cannot be shared with a library that is not the same code, and no longer pile up (a package upgrade without a restart, or a setting that sets a size).** 4.3.4 stopped `requested DSM segment size does not match size of existing segment` by putting the size of the struct in the name of each entry of the server's dynamic shared memory registry. That left two things: a library whose shared struct has the same size and another layout (a field moved into padding, as the statistics of the leaves did between 4.2 and 4.3, where only a number in the name kept the two apart) asked the same name at the same size and shared the table with the older library without any error, and the registry never gives a segment back, so one entry for each name and size stayed until the server restarted (the arena alone is up to 128 segments of 1 MB, the leaf statistics 16 MB and the dictionary ring 64 MB by default, and `sift.col_leaf_cache_kb` and `sift.col_dict_shared_cache_kb` are superuser settings of any size). 5.0 keeps its shared tables in a directory, one registry segment whose name, size and layout never change (so it is the one name every library asks at the same size), by the name of the table, the identity of the library and the size; the identity is a hash of the sources and of the options that change them, made at build time (`scripts/code-id.sh`; the same sources give the same identity in a checkout, a tarball and a package), so there is no number to bump and no struct can change without it. The directory counts the backends that map each table, and the backend that makes a table gives back the tables of other libraries and other sizes that no backend maps: after an upgrade without a restart, the segments of the older library go with its last backend. No statement fails because the library or a size changed. The directory is checked when a backend attaches (a magic number this library does not know is an error that says so, and nothing is shared), and when all its 1024 entries are mapped a backend goes without its table (the same way a table goes unshared where a statement writes), with a message in the log: a full directory costs sharing, never a statement.
- Everything else in the changelog is new in 5.0 (the scope index and pair tables, projections and the shared store have no earlier release to fix), or an improvement.
## Also check

- **A table under concurrent writers on 4.0.0 to 4.3.2 read more of the heap than it had to** after a promotion that an open inserter overlapped: answers were never wrong; 5.0 stamps those segments again at the next maintenance step or merge, and a segment an older release promoted stays unstamped until its next rewrite (`REINDEX`) ([details](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#known-issue-of-400-to-432-a-concurrent-writer-at-a-promotion-left-reads-on-the-heap)).
- **If you set `order_columns`, `point_columns` or `key_cut_rows`:** reset them (`ALTER INDEX .. RESET (option)`; set `point_tid_columns` to the columns of `point_columns` first); the preflight lists each index with the command. **If `sift.col_auto_merge_dirty_pct` is set anywhere** (`postgresql.conf`, a role or database setting), remove it.
- **After the first start of 5.0 the entries that 4.3.x left in the registry stay until the next restart** (4.3.4 and older name their tables by name and size; 5.0 never joins them): a restart after the install, as above, leaves none. Later upgrades of 5.0 without a restart leave nothing behind.

## Known issues

- **The limits of the scope index are listed in [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md#limits):** a `SERIALIZABLE` or non-MVCC snapshot reads through the join; a generic plan keeps the join for a relation with a partial btree when a condition reads a parameter (a custom plan proves it). The answers are the join's in every case.
- **The planner can still choose the dearer of the scope read and the join after changes to the pairs.** The patch and the delta of changed members are priced from the units, rows and copies the journal expects, which over-counts for a tenant that lost members and for one whose changed members have few rows. In a 300,000-fact lab (nine requests, four tenants, five states of changed pairs and buffered rows, 180 cells) the join ran where the scope read cost less in 30 cells, by 0.5 to 7.7 million instructions (a tenant that lost members: a date range count 8.3 against 3.1, a latest 20 8.9 against 3.1; one that changed 20 members: a sum by month 9.2 against 7.2), and the scope read ran where the join cost less in 11 cells, all of the largest tenant (36 units read row by row after changes), by 1.0 to 5.7 million (`GROUP BY` member 20.8 against 15.2, top 20 members 16.6 against 10.9); 139 cells are within 0.35 million instructions of the cheaper arm. In the 2.4-million-event lab a latest or top 20 after a change of 20 pairs or members of the tenant of 0.1% reads 0.5 to 2.9 million instructions more than the join, and after 200 members of the tenant of 5% 5.6 million more (five cells, listed in [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md#where-the-gain-is-small)). No setting changes either; the answers are the join's.
- **A transaction that rolled back after a promotion that waited for it leaves its segment unstamped until a rewrite of the segment**, and so do transactions in doubt more than 63 transaction ids apart or more than 64 distinct ones; the rows a read returns are the heap's in every case.
- **The index WAL of a `key_cut` index under heavy churn is lower than in 4.3 and not at its floor;** the rewrite and the move of blocks still write more than the rows they carry.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 4.3.x with the install and a restart; extension SQL 5.0 (`pg_sift--4.3--5.0.sql`, built from `sql/5.0/`; 4.3.1 and 4.3.2 reach it through their empty scripts back to 4.3); the library reads `sift_col` column format minors 3 through 51. Minors 45 (the scope index), 46 (the shared value store), 49 (a scope of two paths), 50 (a scope with a `text`, `varchar` or `uuid` key or member) and 51 (key groups in the superunit block of a scope segment) are written only by the indexes that use those features; 47 and 48 are unused, and nothing writes either ([docs/FORMATS.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/FORMATS.md)). No BM25 metapage minor change.

## Packages

x86-64 and arm64 packages for PostgreSQL 17, 18 and 19 are attached below (`SHA256SUMS` covers every asset); other versions build from source with `make USE_PGXS=1`.

- Debian 12 and 13, Ubuntu 22.04 and 24.04 (PGDG `postgresql-N`, N = 17, 18 or 19): `sudo apt install ./postgresql-N-pg-sift_5.0.0-1_amd64.deb` (`_arm64.deb` on arm64)
- RHEL, Rocky, Alma 9 and 10 (PGDG `postgresqlN-server`): `sudo dnf install ./pg_sift_N-5.0.0-1.el9.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Amazon Linux 2023 (the distribution's `postgresqlN-server`, N = 17 or 18): `sudo dnf install ./pg_sift_N-5.0.0-1.amzn2023.x86_64.rpm` (`.aarch64.rpm` on arm64)
- Arch Linux: AUR `pg_sift`.

Every change: [CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/CHANGELOG.md).

## SQLite extension

pg_sift for SQLite 5.0.0 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 5.0.0 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-5.0.0-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/sqlite/CHANGELOG.md).

## MariaDB extension

pg_sift for MariaDB 5.0.0 (`sift`, a UDF library and two SQL files; a separate component from the extensions above). Rebuilt with the PostgreSQL 5.0.0 release: no change to the SQL files.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- One library per MariaDB series, because it calls the server's own symbols and refuses to load into another series: 10.11, 11.4, 11.8, 12.1 and 13.0; Linux x86-64. Each was built in the stock `mariadb:<series>` image against that server's headers and loaded into a server of the same image before release. `BUILD-INFO` in the tarball lists the server version and the glibc each library needs.
- Index format 2: an index of 3.4.0 to 3.7.0 opens as it is, nothing to rebuild.

Download `sift-mariadb-5.0.0-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it, copy `lib/<series>/libsift_udf.so` of your server's series
(`SELECT VERSION()`) into its `plugin_dir`, then `SOURCE sql/functions.sql` once per server and `sql/sift.sql` once per database (`sha256sum --ignore-missing -c SHA256SUMS`).
Documentation: [mariadb/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/mariadb/README.md).
Every change: [mariadb/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/mariadb/CHANGELOG.md).

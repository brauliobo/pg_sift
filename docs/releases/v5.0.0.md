pg_sift 5.0.0: reads of a tenant or a group through a table of pairs (a scope index and a scope copy, both experimental), named projections, one store for the strings that several indexes of a table hold, reads of a table under concurrent writers that no longer fall back to the heap, a rewrite of `key_cut` indexes that rolls partition by partition and keeps to a WAL budget, and three index options ignored and one setting removed. Extension SQL 5.0 (`ALTER EXTENSION pg_sift UPDATE` in each database after the install and a restart); nothing has to be rebuilt.

## Highlights

Figures are those [CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/CHANGELOG.md) states, with the table they were measured on. Instructions are those of one backend.

### Reads through a scope (experimental)

- **A scope index (`CREATE INDEX .. USING sift_col (..) WITH (scope = '..')`).** It stores the rows of the index once for each scope key that a table of (member, scope key) pairs gives them, in `key_cut` segments of their own (column format minor 45), and a read of a key reads the units of that key less the members whose pairs changed since the segments were written. One key of the 100,000-row test table (5,000 members, 40 tenants) reads in 1.0 to 1.1 million instructions where the rows of the members cost 1.9 to 2.0; the index file grows from 1,368,064 to 2,383,872 bytes (+74%; a NOTICE says the growth of the segments, +67%). The planner reads the join forms of a scope from the units: `JOIN`, `IN (SELECT ..)`, `EXISTS`, `= ANY (ARRAY(SELECT ..))`, the union of two paths (a direct grant and a grant on a group), `GROUP BY` the key for every key at once, a parameter of a prepared statement as the key, and prices the join as written against them; `sift.explain_why` (slug `scope`) says why a statement keeps the join. The scope key may also be a `text`, `varchar` or `uuid` column of a deterministic collation (column format minor 50: its units are cut by the code of the key in the value store of the key column), with the same forms and a group by the key; in the 300,000-row test table the read of one key costs the same instructions as the integer key (1.0 million) and the build writes 3% more bytes (3.59 against 3.47 MB, plus a 152 KB store). The member may be a `text`, `varchar` or `uuid` column as well: a read costs 0.9 to 1.4 million instructions for one key as for an integer member (1.1 million), and with changed pairs or rows in the write buffer it is read from the units as an integer member is, at about 1.3 times its instructions (112.6 against 87.6 million at 375 changed pairs of 300,000 facts). A scope of two paths takes a string key and member as well, with the same costs (1.4 against 1.7 million instructions for one key, 118 against 90 million at 375 changed pairs). `sift.agg_scope = off` turns it off. What a scope does not do: `char(n)`, `citext`, a domain and a nondeterministic collation are refused at the declaration, with the reason; the group column that joins the two paths of a scope stays an integer; an `ORDER BY` or `LIMIT` over a group by a string key keeps the join (the codes are not in the order of the values); a scope read has no parallel workers; a patch for the changed pairs of a string member reads the member leaf of every entity unit (no point directory, no zone), so it costs about 1.3 times an integer member's instructions, in a scope of two paths a read of one string key with any changed pair patches the changed members of every key (the journal records of a string key carry no tag), and a list of five keys counted once 7.5 and 6.1 million for a text and a uuid member against 2.1 for an integer. [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md).
- **A scope copy (`sift.scope_create`), the alternative to the index.** A copy of a fact table keyed by the scope key, kept exact in the transaction of each change by statement triggers (writers must be `READ COMMITTED`; a table averaging more than 1.8 copies per fact is refused, `max_copies` raises it). `sift.scope_verify` lists the rows that differ from the join, `sift.scope_read_keys` the condition for a read over several keys, and `sift.scope_follow_pairs` keeps the table of pairs equal to a view over assignments and group membership. Choose it over the index when the pairs are a view, depend on a condition on a third table or on time, or the request must be a plain query on a table of its own ([docs/INDEX-RECIPES.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/INDEX-RECIPES.md)).

### Named projections and shared strings

- **`sift.projection_create` and `sift.projection_index`** define once the columns, expressions, filter, roll-ups and options of an index and make the index from one or more of them (or record that an existing index with the same layout serves them); `sift.projection_status` says which are `ok` or `broken`. No format change; a restore and `pg_upgrade` need no order of creation. [docs/INDEX-RECIPES.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/INDEX-RECIPES.md).
- **The `sift_col` indexes of a table that hold the same text, varchar or uuid column with the same `key_order` and `key_cut` store its distinct strings once** (column format minor 46), in a relation `<table>_<column>_sift_values` that is never populated, so a publication of all tables does not list it. Builds take 1.0 to 1.45 times as long; `SET sift.col_value_store = off` before a build keeps the strings in the segments and makes no store, with change tracking and the other structures as usual (column format minor 44 at the most, which 4.3 reads); `sift.col_format_minor = 14` stops the store too, and with it change tracking and every structure of minors 15 and above. [docs/COL-VSTORE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-VSTORE.md).

### Reads under writers, and the rewrite

- **A table under concurrent writers is read without the heap more often.** A segment promoted while a transaction that inserted some of its rows was still open gets its stamp once that transaction has finished (before, until a rewrite); and the maintenance worker folds the marks of the tombstone log into the liveness runs as soon as the reads have paid for it, without waiting for a `VACUUM` that finds too few dead pages. On a churned lab table of 12 columns the mean of a group by goes from 22.4 to 5.5 million instructions, a range from 16.3 to 11.7, a list of 60 keys with `ORDER BY .. LIMIT` from 8.1 to 4.1; only these three classes were measured on that table.
- **A backend keeps the rows of a large write buffer for its next scan when it should:** the slowest read of a few keys on a table churned and vacuumed went from 160 to 5.2 million instructions.
- **The automatic rewrite of a `key_cut` index in partitions rolls.** Each step takes one partition and the overlays over its window of the key and writes into the blocks the step before freed, so a pass writes each partition once: on a 21 MB index grown to 76 MB in 400 batches, a pass takes 83 MB of index WAL (103 before) and the copy down after the overlay merges 44 bytes a row (105). Pieces that tier merges leave over one base partition wait for `sift.col_auto_merge_wal_pct` like any other churn: on the standard write-benchmark table the index WAL falls from 393.6 to 202.6 bytes a row (the wide table 1,423.5 to 545.1), and because that rewrite now comes later (batch 73 where it came at batch 42) a point or key read is 9% dearer around batch 54 and 3% dearer over 144 batches, 7 to 11% cheaper after the rewrite. **The rule that started the automatic rewrite when a share of the units held a dead row is gone** (see below): in heavy churn nothing changes, in light churn the rewrite is due as soon as the WAL budget allows, where it waited until the reads had paid for it, and `sift.col_maintenance_due` names any unit with a dead row as the reason.
- **A parallel `CREATE INDEX` with `key_cut` whose participants took unequal shares of the table merges its peers** (before, the index kept twice its size in the file until the first `VACUUM`).
- **Planner and reads:** a semi join on a `smallint`, `integer` or `date` key that the scan's key filter has tested builds no byte table; a lookup table that is only the keys of its rows reads them from the index entries; the groups of a row's entity over a link table are joined once; `ORDER BY ts LIMIT n` over a table cut by another column reads the ends of the order of each segment.

### Ignored and removed

- **The `sift_col` options `key_cut_rows`, `point_columns` and `order_columns`** (deprecated in 4.3) are ignored: they no longer change a build, and the names stay registered and accepted. **The setting `sift.col_auto_merge_dirty_pct` is removed**: a stored value is dropped with a `WARNING`, and a `pg_dumpall` that names it restores with one `ERROR` for that line. [docs/UPGRADING.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#what-50-removes).

### Fixed

- **Two `CREATE INDEX` statements of `sift_col` indexes that track changes on one table, run at the same time (a parallel `pg_restore`), failed with `deadlock detected`:** an event trigger before `CREATE INDEX` takes the stronger lock first.
- Everything else in the changelog is new in 5.0 (the scope index and copy, projections and the shared store have no earlier release to fix), or an improvement.

## Who is affected and what to do

- **Update, in this order:** install the files and **restart the server** (a standby too: a backend keeps the library it loaded until its connection ends), then `ALTER EXTENSION pg_sift UPDATE` in each database, then `scripts/upgrade-check.sh`. The 5.0 script adds the scope copy and projection tables and functions, the shared value store functions and two event triggers (`sift_col_build_lock` on `CREATE INDEX`, `sift_col_value_store_sql_drop` on `sql_drop`).
- **A table under concurrent writers on 4.0.0 to 4.3.2 read more of the heap than it had to** after a promotion that an open inserter overlapped: answers were never wrong; 5.0 stamps those segments again at the next maintenance step or merge, and a segment an older release promoted stays unstamped until its next rewrite (`REINDEX`) ([details](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#known-issue-of-400-to-432-a-concurrent-writer-at-a-promotion-left-reads-on-the-heap)).
- **If you set `order_columns`, `point_columns` or `key_cut_rows`:** reset them (`ALTER INDEX .. RESET (option)`; set `point_tid_columns` to the columns of `point_columns` first); the preflight lists each index with the command. **If `sift.col_auto_merge_dirty_pct` is set anywhere** (`postgresql.conf`, a role or database setting), remove it.
- **Going back to a release before 5.0:** an index with a `scope` and one that reads its strings from a shared store write segments (minors 45, 46, 49 and 50) that a library before 5.0 refuses; the preflight with `--to` lists the indexes an older release cannot read, and [docs/UPGRADING.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/UPGRADING.md#4-an-older-release) the steps: for 4.3, `ALTER INDEX x RESET (scope)`, `SET sift.col_format_minor = 14` and `REINDEX` for a scope, as the preflight advises, and `SET sift.col_value_store = off` and `REINDEX` for a shared store; for a release before 4.3, `SET sift.col_format_minor = 14` and `REINDEX` for both, which also stops change tracking (the reads check the heap until a `REINDEX` under the default) and every structure of minors 15 and above.

## Known issues

- **The limits of the scope index are listed in [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md#limits):** `CREATE INDEX CONCURRENTLY` of a scope index leaves its segments unfilled until a `REINDEX` or the maintenance rewrites them; a `SERIALIZABLE` or non-MVCC snapshot reads through the join; a generic plan keeps the join for a relation with a partial btree when a condition reads a parameter (a custom plan proves it); `REINDEX` of two indexes of one table at the same time is not covered by the build-lock event trigger; a scope read has no parallel workers. The answers are the join's in every case.
- **The price of a scope read with changed pairs is flat for every class of request, so the planner can run the join where the units would read less.** A tenant that lost members (pairs soft deleted after the segments were written) reads as the join until the segments are rewritten: in a 300,000-fact lab, a date range count took 8.3 million instructions as the join where the scope read takes 2.4, and a filtered count 7.8 against 4.4; and a tenant that received members can read the patch at 1.3 to 4 times the join's instructions. No setting changes either; the answers are the join's. [docs/COL-SCOPE.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/COL-SCOPE.md#where-the-gain-is-small).
- **A transaction that rolled back after a promotion that waited for it leaves its segment unstamped until a rewrite of the segment**, and so do transactions in doubt more than 63 transaction ids apart or more than 64 distinct ones; the rows a read returns are the heap's in every case.
- **The index WAL of a `key_cut` index under heavy churn is lower than in 4.3 and not at its floor;** the rewrite and the move of blocks still write more than the rows they carry.

## Compatibility

- PostgreSQL 17, 18 and 19; the packages below cover all three (other builds from source with `make USE_PGXS=1`). A replacement of 4.3.x with the install and a restart; extension SQL 5.0 (`pg_sift--4.3--5.0.sql`, built from `sql/5.0/`; 4.3.1 and 4.3.2 reach it through their empty scripts back to 4.3); the library reads `sift_col` column format minors 3 through 50. Minors 45 (the scope index), 46 (the shared value store), 49 (a scope of two paths) and 50 (a scope with a `text`, `varchar` or `uuid` key or member) are written only by the indexes that use those features; 47 is unassigned and 48 reserved, and nothing writes either ([docs/FORMATS.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/docs/FORMATS.md)). No BM25 metapage minor change.

## SQLite extension

pg_sift for SQLite 5.0.0 (`sift`, a loadable extension; a separate component from the PostgreSQL extension above). Rebuilt with the PostgreSQL 5.0.0 release: no change to the SQL interface or the shared format.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- Needs SQLite 3.38 or newer; Linux x86-64, glibc 2.34 or newer. Built on Debian 12, loaded into the SQLite of Debian 12, Ubuntu 24.04 and AlmaLinux 10 before release.
- Storage format 2: tables of 3.4.0 to 3.7.0 open as they are, nothing to rebuild.

Download `sift-sqlite-5.0.0-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it and `.load ./sift` from the `sqlite3`
shell (`sha256sum --ignore-missing -c SHA256SUMS`). Documentation: [sqlite/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/sqlite/README.md).
Every change: [sqlite/CHANGELOG.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/sqlite/CHANGELOG.md).

## MariaDB extension

pg_sift for MariaDB 5.0.0 (`sift`, a UDF library and two SQL files; a separate component from the extensions above). Rebuilt with the PostgreSQL 5.0.0 release: no change to the SQL files.

- **No change:** the changes of this release are in the PostgreSQL column index, which is not in this extension. No speed-up or slow-down is claimed.
- One library per MariaDB series, because it calls the server's own symbols and refuses to load into another series: 10.11, 11.4, 11.8, 12.1 and 13.0; Linux x86-64. Each was built in the stock `mariadb:<series>` image against that server's headers and loaded into a server of the same image before release. `BUILD-INFO` in the tarball lists the server version and the glibc each library needs.
- Index format 2: an index of 3.4.0 to 3.7.0 opens as it is, nothing to rebuild.

Download `sift-mariadb-5.0.0-linux-x86_64.tar.gz` (below, covered by `SHA256SUMS` with the packages), unpack it, copy `lib/<series>/libsift_udf.so` of your server's series
(`SELECT VERSION()`) into its `plugin_dir`, then `SOURCE sql/functions.sql` once per server and `sql/sift.sql` once per database (`sha256sum --ignore-missing -c SHA256SUMS`).
Documentation: [mariadb/README.md](https://github.com/brauliobo/pg_sift/blob/v5.0.0/mariadb/README.md).
